## 1. D1 · Agent 真实接入前置：API 登记直起进程，安装脚本不进矩阵

20 号 D7 要求 Agent「以真进程运行、走真实 token 接入、不预置任何行」，而片⑧ spec 的 Testing Decisions 明写「不新增 e2e——安装/升级/回滚冒烟与演练归片⑩」。两者的交界由本条划定。

**接入前置的执行形态**（`make acceptance` 的 setup 阶段，同时**就是** `AC-08-S1` 的执行）：

```text
INITIAL_ADMIN_PASSWORD 引导首启 admin
  → 经用户管理 API 建三档角色账号（20 号 D9）
  → 创建实例（创建即验：连接测试 + 版本门都过才落库）
  → 登记 Agent（enrollAgent）→ 一次性响应拿到 token 明文
  → token 落盘（专用路径、0600）
  → 起 cmd/monitor-agent 真进程
  → agent 上报 → 采集数据经业务 API 可见
```

**安装命令、CA 指纹钉扎、unit 写入、时钟自检不进矩阵**。理由不是省事：`compose.yaml` 里没有 systemd，跑真实安装脚本要么装不上，要么退化成「脚本里的一半步骤被跳过」的假动作——那正是 20 号 D4 要根除的形态。这三件的验证明确移交 [#110](https://github.com/liumingjian/dbs-monitor/issues/110)（交付物与候选留痕），并在本文 §19 点名，**不在矩阵里假装覆盖**。

**唯一被留下的一半**是 `downloadAgentBinary` 端点的鉴权面：它是 [19](../design/19-agent-distribution-and-upgrade.md) 新增的 HTTP 面，属 API 层，与安装演练无关。落成 `AC-08-S8`，见 D6。

**这条前置是其余三组的依赖**：A/B/C 三组的全部条目都跑在这套 setup 之上。执行序因此有一条硬约束——`AC-08-S1` 必须最先执行，`AC-08-S7`（主密钥轮换）必须最后执行（D14）。

## 2. D2 · 片⑧的 `S1` 主干与七条加深基线

片⑧的语义面是九片里最宽的：keyring / 凭据轮换 / Agent 四态 / 接入即验 / 移除三层分收 / 用户角色两页。而 S1 亲口拍板的验收判据只有一句：**「两笔迁移完成且旧路径删除；S2 定稿的两页语义全落地」**。按 21 号 D1「S1 拍板的验收判据一律落成 `baseline: true` 的加深条目」，这一句展开成六条，加上 D3 补回的 `F5`，共 **7 条加深基线**。

| 条目 | 内容 | 层 | 为什么不能并进 `S1` |
|---|---|---|---|
| `AC-08-S1` | 接入主干（上表全流程） | api | —— |
| `AC-08-S2`✦ | **迁移一**：明文列消失 | **db** | 唯一一条 DB 层只读断言：schema 无 `password` 列、全库查询无明文口令、密文列非空。API 层永远看不见这件事 |
| `AC-08-S3`✦ | **迁移二**：B7 例外迁移 + 一次性回显 | **browser** | 见 D13 |
| `AC-08-S4`✦ | Agent 四态可区分（吊销 ≠ 停用） | api | 四态是片⑦呈现的**读取契约来源**，一旦塌成 `agent_token_hash IS NULL` 猜，片⑦全线错但片⑦自己测不出 |
| `AC-08-S5`✦ | 用户管理两页语义 | api | 一次性口令回显 + 只停用不删除（历史仍可归因）+ 「启用态平台管理员 ≥1」并发守卫 + 禁自我停用/降级 |
| `AC-08-S6`✦ | 移除三层分收 | api | 配置立删、未恢复告警连带关闭并留痕、样本随 TTL 不同步删——三层各自都可能单独坏掉 |
| `AC-08-S7`✦ | 主密钥离线轮换 | api | 「主密钥遗失即不可恢复、轮换中断可重跑」的唯一验收面。见 D14 |

**`AC-08-S7` 不降级为普通加深**。它看起来最像「运维动作、可以 `pending`」，但 13 号 D7/D8 的整条承诺（备份不含 keyring、换机须迁 keyring、遗失即密文不可恢复、无后门）在自动化面上只剩这一条能证。允许它 `pending`，等于允许 v1 在「轮换命令从没跑通过」的状态下发布。

## 3. D3 · `F2` 记 `n-a`，由 `F5`✦ 补回

片⑧不产时序、无观测面。`VERSION_UNSUPPORTED` 是**接入即拒**（写操作的失败分类），不是空状态码。

**否决「把 `VERSION_UNSUPPORTED` 塞进 `F2`」**：13 码是**观测面的不可用性**，接入拒绝是写操作的失败分类。混起来会稀释「封闭 13 码」这个概念本身——一旦允许一次，后面每个 4xx 都可以自称空状态。`VERSION_UNSUPPORTED` 归 `F3`（D4）。

因此 `AC-08-F2` 记 `status: n-a`，`reason` 写「本片无时序读取面」。按 20 号 D2「留空 = 未覆盖，不是不适用」，条目仍在，并由 **`AC-08-F5`✦（`baseline: true`）** 补回保护：

> 新接入实例在**首个采集周期完成前**，观测面落 `NO_DATA`（或对应的封闭码）而非 `0`、而非空数组、而非 200 空对象。

这条补回是必要的，因为它是全矩阵唯一覆盖「**刚接入、还没有任何样本**」这个时刻的条目——A 组的 11 码逐码驱动（`AC-05-F2`）跑在已有数据的实例上，跑不到这个窗口。

## 4. D4 · `F3` = 创建即验的三类分类原因，且都不落库

`AC-08-F3` 读作**创建即验的三类分类原因**，三类各自拿到规定的拒绝语义、**且都不落库**：

| 分类 | 真实制造手段（20 号 D8） | 断言 |
|---|---|---|
| 网络不通 | 停目标库容器 / 指向不存在的 host:port | 分类原因 = 不可达类，非 500、非静默成功 |
| 认证失败 | 给错 username/password | 分类原因 = 认证失败类，错误映射服从 `13` D9 稳定映射 |
| 版本 <13 | **另起一个 `postgres:12` 容器** | 封闭码 `VERSION_UNSUPPORTED` |

**三类共同的第二组断言**：请求返回后库里**不存在**该实例行——「库里永远不存在从未连通过的实例」这条不变式的唯一验收面。

**`postgres:12` 容器进 `compose.yaml` 的独立 profile**，只在这条条目拉起，不进默认启动集。否则每次 `make acceptance` 都白拉一个绝大多数条目用不到的镜像。**否决「mock 版本号」**：那是 20 号 D8 明令禁止的，且版本门本来就是要证明「真的问了目标库的版本」。

**闭合 C 组留下的缺口**：23 号 D2 在 `AC-05-F2` 的 `reason` 里写死了「`VERSION_UNSUPPORTED` 无产生者」。本条使它**有了唯一产生者**，`AC-08-F3` 的 `reason` 显式记这句话，让读矩阵的人能把这条链两头对上。

## 5. D5 · `F4` = keyring 类故障不得降格

`AC-08-F4` 断的是 13 号「启动失败语义显式化」那一段，也是片⑧ spec User Story 9 的原话（「不去冤枉一个好好的数据库」）。

**真实手段**：把 `master-key-vN` 文件 `chmod` 成错误权限（或让 `current` 悬空）。不改代码、不注入错误。

**三组断言**：

1. 该实例的凭据读取被拒，诊断为**平台自身故障**；
2. 该实例**不产生** `DB_UNREACHABLE` 告警、**不计入** `NO_DATA`（T14 硬约束）；
3. **平台绝不静默生成新密钥**——恢复权限并重启后，keyring 目录内文件数与版本号与故障前完全一致。

第 3 点单列进 `asserts`，不与第 1 点合并。理由：静默生成新密钥是**无声的秘密丢失**——旧密文从此不可解，而平台表现得一切正常，直到某次采集才暴露。它一旦回归，前两点仍可能全绿。

暴露面（平台健康四态 / journal / 诊断 API）归片⑨（`AC-09-*` 已由 A 组定稿），本条只断「故障事实产生且不污染」，不越界。

## 6. D6 · `F1` 一条覆盖两类写面；`S8` 是全矩阵第二条 `pending`

片⑧的写权限有一条明确边界：**接触秘密的动作全归平台管理员**，唯一例外是**实例元数据编辑 = 告警管理员**。

`AC-08-F1` **一条**覆盖两类写面，`asserts` 内逐面列举：

- 平台管理员专属面（创建实例、更新 PG 凭据、Agent 五操作、移除实例、用户管理全部写操作）× 三档角色；
- 元数据编辑面（`updateInstance`）× 三档角色——告警管理员**成功**，只读运维被拒。

**否决拆两条**：20 号 D6.2 定的粒度是「一条条目 = 一次执行 + 一组断言」，而 D9 规定的 `F1` 形态本来就是「三种角色的会话各跑一遍」的同一次执行。拆开只涨条目数不涨覆盖。

**`AC-08-S8`（`downloadAgentBinary` 鉴权）= 普通加深，允许 `pending`**：断 Agent token 鉴权、无 token 401、`arch` 非法值被拒。它不在片⑧ spec 的 S1 验收判据里（是 19 号决策之后新增的面），按 21 号 D1 的准入不够格升基线。这是全矩阵**第二条**允许 `pending` 的条目（第一条是 B 组的 90 天清理），两条都进 Go/No-Go 报告的 `pending` 清单。

## 7. D7 · 横切组的挂载形态：新增 `rides_on` 字段

20 号 D5 定了两件事：横切七条**每条**必须有「一条 A 栏表驱动单测 + 一条端到端断言」，且横切**独立计分**——「各片条目可以引用横切 ID，但引用不计入横切组的达标」。B 组与 C 组各自留下了「`INV-x` 的端到端面可引用 `AC-yy-zz`」的提示。本条把「引用」这个词的两种读法拆开定死。

**三种候选形态**：

| 形态 | 判定 |
|---|---|
| (a) 横切七条各自**独立执行**一次，不共用任何别片的 run | 否决：成本极高且失真。`INV-2` 要重新造齐四类未恢复告警，正是 23 号 D13 说的「全矩阵准备成本最高」的现场；重造一遍不增加任何覆盖 |
| (b) 横切条目**自带断言集与 `test_ref`**，**搭在**别片条目的同一次执行现场上 | **采纳** |
| (c) 横切条目就是别片条目的别名 | 否决：直接违反 D5 的独立计分 |

**(b) 的纪律**：

1. 横切条目照常有自己的 `layer` / `asserts` / `test_ref`；
2. **达标由它自己的 `test_ref` 与 `asserts` 证明**，与承载它的那次执行是否绿**无关**——承载条目红了，横切条目也要能单独判定；
3. 新增字段 **`rides_on: [<条目 ID>, ...]`**，记账它搭在哪次（哪几次）执行上。搭车关系**显式记，不藏**。

`rides_on` 是对 20 号 D6.4 字段表的**扩展**（加字段），不是推翻（改语义），因此不需要新开决策记录推翻 20 号；但它是本文对骨架的一处增补，读矩阵的人在这里能查到出处。

**`rides_on` 与既有 `crosscut` 字段的分工**：`crosscut:` 写在**片条目**上，方向是「本片条目引用了哪条横切语义」（覆盖维，不计分）；`rides_on:` 写在**横切条目**上，方向是「本横切断言搭在哪次执行上」（执行编排）。两者不是互为反向索引——一个片条目可以 `crosscut: [INV-3]` 而不被 `INV-3` `rides_on`。

**纠正 23 号 §14 给本票的一条提示**。23 号写的是「`INV-2`（不补 0）的端到端面可引用 `AC-06-F2`」，其中两处需要纠正：`INV-2` 是「实例健康 = 未恢复告警最坏归并 + 已暂停 override，单一来源」，不是「不补 0」（不补 0 是 T2 的口径，不在四不变式内）；`AC-06-F2` 断的是 5 秒粒度下秒级空隙保持空隙，与健康归并无语义交集，**搭不上**。

**按纪律，23 号一字不动**（与 A/B/C 三组「不原地改写上游」的做法一致），纠正只落在本文与 `matrix.yaml` 的 `reason` 字段里。`AC-06-F2` 与横切的关系降为普通 `crosscut:` 引用，不作 `rides_on`。

## 9. D9 · `BUILTIN-1..3` 按三条规则切，不按受限语义切

骨架把它们预填成「内置采集状态规则 1 / 2 / 3」，本条确认这就是**按规则切**：

| 条目 | 规则 | 指标 ID | 默认 severity | 真实触发手段 |
|---|---|---|---|---|
| `BUILTIN-1` | 数据库不可达 | `pg.availability.reachable` | `critical` | 停目标库容器 |
| `BUILTIN-2` | Agent 离线 | `agent.status` | `critical` | kill agent 进程 |
| `BUILTIN-3` | 数据过期 | `collector.last_success_time` | `warning` | 停采集使新鲜度超阈值 |

**否决按受限语义切**（`BUILTIN-1` 不可删 / `BUILTIN-2` 不可停 / `BUILTIN-3` 下限 `warning`）：那与 `INV-4` 的三条断言**完全重复**，横切组会出现两条条目断同一件事，而 D5 独立计分的本意是覆盖七个**不同**的失效面。

按规则切补上的正是 `INV-4` 覆盖不到的那面：**这三条规则装机即存在，且在真实故障下真的会点着**。「规则在表里但从来没被评估过」是最典型的「改坏了没人看得出来」——`INV-4` 全绿（删不掉、停不了、改不成 `info`）与「它从来没触发过」可以同时成立。

代价：三次真实故障注入，其中 `BUILTIN-1`/`BUILTIN-2` 与片①/⑦ 的现场复用（`rides_on`），`BUILTIN-3` 单独执行一次。

## 10. D10 · A 栏新增 `A10` / `A11`；`B7` 退回结构守卫分工

20 号 D5 说横切的单测面「复用 / 扩展 A1–A5 与 A9 golden」。核对 [`10` §3.2](../design/10-ai-guardrails-and-verification.md) 的实际九条后，**`INV-3` 与 `INV-4` 在既有 A 栏里没有落点**：A1–A5 是状态机 / 滞回 / `NO_DATA` 计数 / 冻结 / 健康归并，A6–A8 是差分与字典，A9 是枚举码 golden。骨架预填的 `INV-3 → B7`、`INV-4 → A9` 都不成立。

**新增两行**（登记进 `10` §3.2 A 栏）：

| # | 内容 | 出处 | 兑现时机 |
|---|---|---|---|
| A10 | 三档角色 × 页面 × 写操作的**可见性 / 写能力判定表** | 不变式③、`03` §8.1 | 片⑧实现期 |
| A11 | 三条内置采集状态规则的**受限语义判定表**（存在 / 启用 / severity 下限） | 不变式④、`02` §6.1 | 片⑧实现期 |

**否决「用 B 栏结构守卫顶替」**（`B3` `x-required-role` 全覆盖、`B7` 秘密字段禁名单）：B 栏是**结构守卫**，扫的是 schema，证明的是「声明齐全」，不是「判定正确」。一份把所有端点都声明成 `viewer` 的 spec 能让 B3 全绿。

**否决「承认这两条只有端到端面、对 D5 记 `n-a`」**：那是直接把 D5 挖空——D5 的「两条腿」正是为这七条设的。

`10` §3.2 自己写着「表中没有的东西不必表驱动——清单的价值来自它短，不要往里加」。加这两行**付了理由**：它们不是「顺手多测点」，是 20 号 D5 的强制要求在 A 栏上的落点。这是本组**外溢到实现的第一条硬要求**（D15）。

**`matrix.yaml` 的 `unit_test` 字段随之改写**：`INV-3 → A10`、`INV-4 → A11`、`BUILTIN-1..3 → A11`（与 `INV-4` 共用同一张受限语义判定表，但端到端面不同——D5 的两条腿不要求一一对应到不同单测）。`B7` 从 `unit_test` 挪进 `INV-3` 的 `asserts` 说明，记为结构守卫侧的分工（D12）。这改的是骨架**预填值**，不动 20 号正文。

## 11. D11 · 角色 fixture：三个长期账号 + 一次性账号池

20 号 D9 定了「一律经用户管理 API 创建、初始 admin 由 `INITIAL_ADMIN_PASSWORD` 引导、不许直插 `user` 表」。本条定集合与生命周期：

- **三个长期账号**（`platform_admin` / `alert_admin` / `viewer`）在 setup 阶段创建一次，全矩阵所有 `F1` 复用同一组会话，**只读式使用**——不停用、不降级、不改口令；
- **一次性账号池**：凡是会改变账号自身状态的断言（停用、降级、重置口令、「管理员 ≥1」守卫、并发双写），一律用**当条条目自建的一次性账号**，命名带条目 ID 前缀（如 `ac08s5-admin-1`）。

**否决「全部复用三个长期账号」**：`AC-08-S5` 的停用/降级断言会把长期账号污染成跨条目耦合——片⑧一条停用能让片③的 `F1` 变红，且顺序相关、极难查。**否决「每条条目自建自清」**：每条重建三账号 + 三次登录，慢且零收益。

一次性账号带条目 ID 前缀是为排障：矩阵红了以后，从库里的用户名就能直接读出是哪条条目留下的现场。

## 12. D12 · 「凭据永不回显」：`B7` 管 schema，端到端管响应体全文

这条语义有三层面，分工定死：

| 面 | 归属 | 证明什么 |
|---|---|---|
| schema 里不许声明秘密字段 | **`B7` 结构守卫**（`make check`） | 契约层干净。含本片的例外迁移：唯一例外从创建实例 201 响应挪到 Agent 登记/轮换的一次性响应，**先红后绿** |
| 端点角色声明齐全 | `B3` | 声明存在（不证明判定正确，见 D10） |
| 真实响应体里确实没有 | **端到端**（`INV-3`，搭 `AC-08-S1`） | 运行层干净 |

**为什么端到端不可省**：schema 干净不等于 handler 不多塞字段。Go 结构体多一个 tag、中间件回显、错误响应体带上 DSN——`B7` 一概看不见。

**断言用响应体全文正则扫描，不用字段白名单**：要防的是**意料之外**的字段，白名单只能防意料之内的。扫描面 = 创建实例 201 / 实例详情 / 凭据更新响应三处，命中即红：口令明文、密文 base64、`password_key_version`、完整 DSN。

外加**一次性回显只出现一次**：同一个 token / 初始口令，第二次调用读取端点拿不到——只能换发新的。

这组断言集中写在 `INV-3` 上，不散落到片⑧各条里；片⑧各条通过 `crosscut: [INV-3]` 指过来。

## 13. D13 · 片⑧唯一一条浏览器条目：`AC-08-S3`✦

IA §6 的五条关键路径已被 A 组（§6.5 → `AC-01-F2`）、B 组（§6.4 → `AC-03-S3`）、C 组（§6.1/§6.2/§6.3）占满，片⑧没有 §6 路径可挂。片⑧ spec 自己把一次性回显弹窗归给了 **vitest**。

但 20 号 D3 的判据是「凡断言点是**用户看到什么**，必须上浏览器」，而**「关闭后不再显示、无二次读取路径」只有浏览器能证**——vitest 测的是组件在给定 props 下的渲染，证明不了真实的一次性响应被接进了那个弹窗，也证明不了刷新后确实拿不回来。

`AC-08-S3` 的 `layer` 因此定为 `browser`，一条覆盖两种秘密（Agent token 与用户初始口令，同一断言形状）：

1. 弹窗显示明文 + 复制按钮 + 「关闭后不再显示」警示；
2. 关闭后页面**无任何再次读取控件**；
3. 刷新后不再出现；
4. 再次调用登记端点只会**换发新 token**，不回显旧的；
5. PG 凭据区 password 字段掩码呈现、**无任何查看控件**。

**这不与片⑧ spec 冲突**：spec 的 vitest 那条仍然照做（快层，`make check` 内），矩阵这条是端到端面，两者不互相顶替。片⑧其余条目全部 api / db，**浏览器执行只此一次**。

## 14. D14 · `AC-08-S7` 主密钥轮换排在执行序最末

轮换是**离线维护窗口命令**（生成 `vN+1` → 原子切 `current` → 单个平台库事务内全量重加密 → 验证无旧版本引用 → 清理旧 key），而矩阵里 server 是常驻进程。

**执行形态**：排在矩阵执行序**最末** → 停 server → 跑轮换命令 → 重启 server → 断言。

断言四组：

1. 全部 `password_key_version` 已为 `vN+1`，旧版本零引用；
2. 密文**仍可解**——重启后采集正常恢复出点；
3. 旧 key 文件已清理，且**仍有引用时不得删旧 key**（反向断言）；
4. **中断可重跑**——轮换执行到一半 kill 掉，重跑后结果与一次跑完一致（13 号 D7 明写的承诺）。

**否决「不停 server 跑」**：轮换本就定义为维护窗口内动作，不停 server 跑等于验收一个产品不承诺的形态。

**排最末的代价是它污染后续状态**，所以顺序不是偏好而是约束：该顺序写进本文、写进 `matrix.yaml` 的 `reason`，并进 `acceptance-result.json` 的执行序，**不靠测试框架的默认顺序碰运气**。

对称地，`AC-08-S1`（接入前置，D1）必须**最先**执行。矩阵的执行序因此有且只有这两条硬约束，其余条目顺序自由。

## 15. D15 · 时间参数化、`exceptions`、外溢到实现的硬要求

**时间参数化**（A 组 D7 取值表的增补，本组只加一项）：

| 参数 | v1 默认 | 验收取值 | 理由 |
|---|---|---|---|
| 采集新鲜度阈值（`collector.last_success_time` 规则） | 产品默认 | **秒级** | `BUILTIN-3` 要它才跑得完；不参数化就只能直写历史样本，落进 D4 白名单 |

**`exceptions` 仍为 `[]`**。片⑧的全部现场都有真实手段：改文件权限（keyring 故障）、停容器（不可达）、给错口令（认证失败）、起 `postgres:12`（版本门）、kill agent（离线）、停 server 跑轮换命令。**没有一条需要直插业务表或直写历史样本**——四组条目定稿完毕，D4 白名单全程为空，这是矩阵最强的一条自证。

3. **主密钥轮换命令必须可被非交互调用**——不得只有交互式确认入口，否则矩阵跑不动 `AC-08-S7`。

## 18. 已接受的代价

1. **片⑧ 13 条是全九片最多的一片**。片⑧的语义面本来就最宽（两类秘密的完整生命周期 + 两页产品语义），且几乎每条都是「改坏了没人看得出来」。压缩条目数只会把断言点堆进 `S1`，一红查不出在哪。
2. **执行序有两条硬约束**（`S1` 最先、`S7` 最末）。这让矩阵不能完全并行执行，也让 `acceptance-result.json` 必须记录执行序。换的是「轮换命令真的跑过」这件事进自动门。
3. **`rides_on` 是本组对 20 号字段表的扩展**。读矩阵的人要多理解一个字段，且「搭车但独立计分」的心智模型不直观。对冲是本文 D7 把两种字段的方向写死，且 `rides_on` 为空的横切条目（`BUILTIN-3`）也合法。
4. **A 栏从九条变十一条**。`10` §3.2 自己写着「不要往里加」，本组加了两条。理由是 D5 的强制要求，但这确实动了一份既有登记表——若日后认为 A10/A11 名不副实，应回到 20 号 D5 重议「两条腿」，而不是悄悄删表行。
5. **安装命令与 CA 指纹钉扎不进矩阵**。v1 可以在「安装脚本从没被自动跑过」的状态下通过矩阵。对冲是它显式移交 #110 并写进本文，不藏在「没条目」里。
