## 0. 一句话结论

**平台只防“数据库或其备份单独泄露”，不防宿主机失陷；PG 密码用平台首次启动生成的版本化 AES-256-GCM 主密钥加密，Agent 令牌只存哈希且由显式登记动作签发；PG 密码、Agent 令牌和主密钥均采用人工触发、无长期双写的简单生命周期；备份与主密钥分开；吊销令牌不等于停用 Agent；除 Agent 签发/轮换的一次性响应外，任何秘密永不进入响应、日志或诊断出口。**

这不是一套通用秘密管理平台。它只为本产品已经存在的两类秘密提供足够窄、能解释、能恢复的生命周期。

## 1. D1 · 威胁模型先于加密方案

### 1.1 明确保护

加密只保护以下场景：

1. 控制面数据库备份、`pg_dump` 或数据目录快照单独泄露；
2. 攻击者只有平台数据库读取能力，能看到实例行但拿不到主密钥文件；
3. 运维误把数据库备份交给了不应接触目标库密码的人。

在这些场景中，实例 host、port、database 与 username 可以明文出现，password 不可被恢复。

### 1.2 明确不保护

以下场景在本系统的威胁模型之外：

- 宿主机 root 或平台运行用户失陷；
- 服务端进程被控制或进程内存被读取；
- 攻击者同时取得数据库密文与主密钥文件；
- 恶意平台管理员通过产品已有的连接能力滥用凭据。

主密钥与密文同机意味着无法防住整机失陷。引入外部 KMS、Vault、TPM、人工解锁或客户 PKI，都会与“整包自带、无人值守重启、不依赖客户环境”冲突；在以内网部署为主的 MVP 中不支付这笔复杂度。

**否决**：把同机加密描述成能防 root 或整机接管；随包内置固定主密钥；引入外部秘密管理依赖。

## 2. D2 · 主密钥来源与启动失败语义

### 2.1 首次生成

平台首次启动时用系统 CSPRNG 生成 32 字节主密钥，作为 AES-256 key。密钥放在 PostgreSQL 数据目录之外的平台私有配置目录中，按版本命名，例如：

```text
/opt/dbs-monitor/etc/credentials/
├── current
└── master-key-v1
```

- `master-key-vN` 归平台非 root 运行用户所有，权限固定为 `0600`；
- `current` 只记录新写入使用的密钥版本，并通过原子 rename 更新；
- 密钥不得打印、进入环境变量、命令行参数或数据库；
- 自带 PostgreSQL 与服务端同属一个 OS 用户的风险已落在 D1 的“宿主机失陷不保护”边界内，不额外制造第二运行用户和跨用户密钥代理。

只有在密钥环不存在且数据库中尚无加密凭据时才允许自动生成。R3 首次把 walking skeleton 的明文开发数据迁移为密文时，先生成初始密钥，再执行一次性迁移。

### 2.2 缺失或损坏必须显式失败

已有加密凭据时，出现以下任一情况，服务端必须拒绝相关凭据读取，并将其诊断为**平台自身故障**：

- 密钥文件缺失、长度错误或不可读；
- 属主或权限不符合要求；
- 密文引用未知密钥版本；
- AES-GCM 认证失败；
- `current` 指向不存在的版本。

绝不能悄悄生成新密钥，也不能把解密失败降格为目标实例 `DB_UNREACHABLE` 或 `NO_DATA`。后两者描述的是目标数据库事实，不可用来掩盖平台自己丢失密钥。

## 3. D3 · PG 凭据与密文格式

### 3.1 领域边界

**PG 凭据**是服务端连接一个被监控 PostgreSQL 实例时使用的 username + password。username 是连接身份的一部分但不是秘密；只有 password 加密。

host、port、database 与 username 继续明文存储。系统不保存完整连接串，不把这些字段重新拼成可记录或可回显的 DSN。

### 3.2 存储形状

walking skeleton 的：

```sql
password text NOT NULL
```

在 R3 替换为：

```sql
password_ciphertext bytea NOT NULL,
password_key_version integer NOT NULL CHECK (password_key_version > 0)
```

密文采用 Go 标准库 AES-256-GCM。每次写入使用独立的 12 字节随机 nonce，二进制 envelope 为：

```text
format_version(1 byte) || nonce(12 bytes) || ciphertext_and_tag
```

`password_key_version` 独立成列，供轮换、启动校验与旧密钥清理查询。AES-GCM 的附加认证数据固定绑定：

```text
dbs-monitor:instance:<instance_uuid>:pg-password:v1
```

因此把一行密文复制到另一实例，或把密码密文当作另一类字段解密，都会认证失败。

### 3.3 具体实现，不新增接缝

加解密代码属于实例凭据读写路径的内部实现。不得新增 `Sealer`、`SecretStore` 或通用 crypto interface；[T5 · 后端代码结构与模块边界](05-backend-code-structure.md) 已把架构接缝封闭为五个，一个本地实现不构成新接缝的理由。

凭据只在即将构造目标库连接配置时解密。凭据版本变化后，必须使 [T12 · 采集并发限流、超时与背压](12-collection-concurrency-timeouts-and-backpressure.md) 的旧普通查询连接池失效；下一次任务按新版本重建。

**否决**：整条连接串加密；username 一并加密；确定性 nonce；通用加密抽象；在数据库函数或触发器中解密。

## 4. D4 · PG 凭据写入与密码轮换

### 4.1 API 边界

创建实例时仍提交 username + password，但响应只返回实例公开字段。普通实例更新不得接受 username 或 password，也不得要求前端重新提交一个无法读取的密码。

PG 凭据使用独立的写操作更新：

```text
Update instance metadata: name / host / port / database / ...
Update PG credential:      username + password
```

OpenAPI 必须为凭据请求和实例响应使用不同 schema。凭据更新响应不包含 username/password 组合、password、密文、密钥版本或 DSN。具体 URL 继续服从 [T6 · API 契约组织与代码生成流水线](07-api-contract-and-codegen.md) 的实例嵌套规则，由 R3 落地；本票定死的是两种写操作不能重新合并。

### 4.2 更新流程

1. 平台管理员提交新的 username + password；
2. 服务端用目标实例当前 host / port / database 与新凭据执行完整连接测试；
3. 测试成功后，在平台数据库事务中写入新密文与密钥版本；
4. 提交成功后，使该实例旧连接池失效；
5. 测试或持久化失败时保留原凭据，不做部分更新。

### 4.3 轮换归客户 DBA，不跨系统造伪原子性

平台永不对被监控数据库执行 `ALTER ROLE`。客户 DBA 先改变目标 PG 密码，随后平台管理员立即提交新凭据。

目标 PG 与平台数据库是两个独立事务域，MVP 不保存新旧两套 PG 密码，也不建立跨系统轮换状态机。明确接受两个动作之间的短暂采集失败；它可能产生 `DB_UNREACHABLE` 或在持续两个评估周期后进入 `NO_DATA`，不能被静默吞掉。

**否决**：平台代客户修改目标 PG 角色密码；长期双凭据；为了隐藏短暂窗口而引入分布式补偿流程。

## 5. D5 · Agent 登记与令牌存储

### 5.1 无 Agent 实例不自动签发

创建实例不得自动签发 Agent 令牌。管理员明确选择安装 Agent 时，才执行独立的 **Agent 登记** 操作并签发令牌。

- `agent_expected = false`：从未登记或已明确停用，`host.*` 与 Agent 离线规则结构性不适用；
- `agent_expected = true`：平台期待该实例存在 Agent，令牌被吊销也不改变这项事实。

walking skeleton 为验证两条通路而在创建实例时自动返回令牌，那是已完成使命的切片行为，不是 R3 的产品先例。

### 5.2 令牌生成与服务端存储

每次签发生成 32 字节随机值，以无 padding 的 base64url 回显一次。服务端只保存：

```text
SHA-256(token)
```

随机令牌已经具有足够熵，不使用 bcrypt/Argon2 这类慢速密码哈希。`instance.agent_token_hash` 建唯一索引；身份查找只比较哈希，自报 hostname、OS、版本或 instance ID 都不参与鉴权。

实例至少持久化以下生命周期事实，具体列名由 R3 schema 定稿：

- 是否期待 Agent；
- 当前令牌哈希；
- 当前令牌签发时间；
- 当前令牌吊销时间；
- 首次登记时间。

这些事实用于区分“从未安装”“应在线但令牌已吊销”“已明确停用”，不能只靠 `agent_token_hash IS NULL` 猜测。

### 5.3 Agent 主机落盘

明文令牌保存在：

```text
/etc/dbs-monitor-agent/token
```

文件归 Agent 专用非 root 运行用户所有，权限 `0600`。Agent 启动时直接读取文件；不得把令牌放在命令行参数、systemd 环境变量、日志或诊断包中。

不做机器绑定。机器绑定无法防住已取得主机权限的攻击者，却会妨碍换机恢复；令牌本身只能上报绑定实例的 OS 指标与心跳，爆炸半径已经被 T1/T3 封闭。

## 6. D6 · Agent 令牌轮换、吊销与停用

### 6.1 轮换立即生效

轮换时生成新令牌、一次性回显，并立即用新哈希替换旧哈希。新旧令牌不共存；旧令牌从提交时起失效。

运维随后替换 Agent 主机的 token 文件并重启服务。明确接受这段人工窗口内 Agent 离线或进入 `NO_DATA`。内网 MVP 不为低频运维动作引入 pending token、宽限期、自动续签或双令牌表。

### 6.2 吊销令牌不等于停用 Agent

两项操作具有不同领域语义：

| 操作 | 令牌 | `agent_expected` | 产品表现 |
|---|---|---:|---|
| 吊销令牌 | 立即拒绝 | `true` | Agent 仍应在线，继续显示离线并触发既定采集状态规则 |
| 停用 Agent | 立即拒绝 | `false` | `host.*` 与 Agent 离线规则结构性不适用，历史样本保留 |

停用后重新启用必须重新登记并签发新令牌。吊销不使用黑名单：当前实例只有一个有效令牌槽，记录 `revoked_at` 并在鉴权时拒绝即可。

**否决**：吊销后把实例误判成“从未安装”；短有效期 + 自动续签；全局共享黑名单；停用时删除历史主机指标。

## 7. D7 · 主密钥轮换

主密钥不自动、不定期轮换。运维只在明确维护窗口执行离线轮换命令。

### 7.1 版本化 keyring

轮换过程允许新旧主密钥短暂共存：

1. 停止服务端或取得排他维护锁，禁止凭据写入；
2. 生成 `master-key-vN+1`，校验属主/权限并 fsync；
3. 原子更新 `current`，使后续新写入使用新版本；
4. 在一个平台数据库事务内读取全部实例密码，用旧版本解密、新版本重新加密，并更新 `password_key_version`；
5. 验证不存在仍引用旧版本的在线数据，执行连接测试并重启服务；
6. 从在线主机移除旧密钥。仍需恢复旧备份时，旧密钥只随对应备份单独归档。

服务端按每行的 `password_key_version` 选择密钥，因此在步骤 3 到步骤 4 之间中断也不会破坏已有密文。50 实例量级下使用单事务，不引入后台批处理、双写或轮换状态机。

### 7.2 失败恢复

- 新密钥未落稳前不得切换 `current`；
- 数据库事务失败则全部旧行保持原版本；
- `current` 已切换但重加密未完成时，keyring 同时保留两版，重跑命令即可；
- 不得在仍有在线行引用旧版本时删除旧密钥。

## 8. D8 · 备份、恢复与升级

### 8.1 两个独立制品

控制面数据库备份**不包含主密钥**。这是 D1 能成立的前提，不是可选的运维建议。

- 原机恢复：使用原有 keyring；
- 换机恢复：运维单独迁移与该备份匹配的 keyring，恢复正确属主和 `0600` 后再启动；
- 升级：原地保留 keyring，不重新生成；
- 主密钥遗失：密文不可恢复，只能重新录入实例 PG 凭据；不提供恢复口令、密钥托管或后门。

备份文档必须把数据库备份与 keyring 标成“两者缺一不可”，但不得默认把它们打进同一个 archive。旧数据库备份在过期前，其同期旧密钥也不能提前销毁。

### 8.2 Walking skeleton 迁移边界

T11 离线包已被明确标记为 walking skeleton，不是生产发布包；升级、控制面备份恢复与回滚原本就延期到 R3。因此 R3 可以把现有开发/验收数据视作可重建数据，不为 T11 明文密码设计一个面向客户的兼容升级承诺。

生产发布声明前必须满足：schema 中不存在明文 `password` 列，测试夹具与日志中不存在可恢复的实例密码，升级/恢复演练能带着独立 keyring 完成。

## 9. D9 · 解密、错误与回显边界

### 9.1 允许解密的内部操作

服务端只能在以下操作即将建立目标 PG 连接时解密：

1. 服务端直连采集与可用性探针；
2. 能力探测；
3. 管理员提交新凭据时的连接测试；
4. 未来已经被 T1 预留的 Agent 隧道 dialer。

代码把 password 直接设置到 `pgx.ConnConfig.Password`，不得构造完整 DSN。Go 无法可靠承诺字符串或进程内存立即清零，本设计不作虚假“内存擦除”保证；进程内存读取已在 D1 范围外。

### 9.2 永不出现秘密的出口

除 Agent 签发/轮换成功时专用的一次性响应外，以下出口不得包含 PG password、password ciphertext、主密钥、Agent token、Authorization header 或完整连接配置：

- 所有 API 响应；
- 结构化日志与 systemd journal；
- 错误信息；
- 诊断 API 与离线诊断包；
- 指标标签；
- 审计事件；
- 导出文件。

禁止记录实例写请求体、Agent report 的 Authorization header、Agent token 文件内容或 `pgx.ConnConfig`。目标 PG 错误对外只映射为稳定分类，例如 `AUTH_FAILED`、`NETWORK_UNREACHABLE`、`TLS_FAILED`、`TIMEOUT`；日志只记录 instance ID、阶段、分类和脱敏上下文。

[T9 · AI 开发护栏与验证闭环](10-ai-guardrails-and-verification.md) 的响应 schema 秘密字段禁名单继续作为结构守卫。Agent 签发/轮换的一次性响应必须作为窄例外显式登记；需要表达“是否已登记 Agent”时使用明确布尔/状态字段，不返回 token 本身。

## 10. 关键场景验算

### 10.1 数据库备份单独泄露

攻击者得到 host、database、username、密文和 key version，但没有 keyring。AES-GCM 密文不可恢复，符合 D1；若备份与 keyring 被一起取得，则属于明确不保护的场景。

### 10.2 密文被复制到另一实例

密钥版本存在，但 AAD 中的 instance UUID 不同，AES-GCM 认证失败。服务端报平台凭据损坏，不把它写成目标库认证失败。

### 10.3 DBA 改密后管理员输错新密码

连接测试失败，平台保留旧密文。目标 PG 已不接受旧密码，因此采集仍失败，直到管理员提交正确的新凭据；系统不伪造“轮换成功”。

### 10.4 Agent 令牌疑似泄露

管理员执行吊销，旧令牌立即拒绝。`agent_expected` 保持 true，实例继续显示 Agent 离线。若客户决定永久卸载，则另执行停用，不能拿吊销代替。

### 10.5 主密钥轮换中断

新旧 key 都在 keyring，行上有明确 key version。无论中断发生在切换 `current` 前后，旧行仍可解密；轮换命令重跑后再清理旧 key。

### 10.6 已有密文但 keyring 遗失

服务端拒绝启动相关凭据路径并给出平台自身故障诊断。它不生成新 key、不清空密码、不把所有实例变成 `NO_DATA`。

## 11. 实现守卫

R3 实现至少用自动化测试锁住以下性质：

1. AES-GCM round trip、随机 nonce 不复用、密文篡改失败；
2. 跨实例复制密文因 AAD 不同而失败；
3. 未知 key version、缺失 key、错误权限与错误长度均显式失败；
4. 全新 keyring 只生成一次，重启和升级不替换；
5. schema 与查询中不再存在明文实例 password；
6. 创建与普通更新响应永不含凭据，只有 Agent 签发/轮换专用响应可一次性包含新 token；
7. 新 PG 凭据连接测试成功才提交，失败保留旧密文；
8. 凭据版本变化使旧目标库连接池失效；
9. Agent token 明文只在签发/轮换响应出现一次，服务端只存 SHA-256；
10. 从未登记、已吊销、已停用三种 Agent 状态的适用性与告警行为不同；
11. 旧 Agent token 在轮换提交后立即拒绝；
12. 主密钥轮换中断后旧、新版本行均可恢复，仍有引用时不能删旧 key；
13. 日志、错误、诊断导出与响应 schema 的秘密扫描全绿；
14. 数据库备份不包含 keyring，换机恢复缺 key 时明确失败。

这些守卫进入 [T9 · AI 开发护栏与验证闭环](10-ai-guardrails-and-verification.md) 定义的既有两层命令，不新增第三条“安全检查”命令。

## 12. 否决记录

| 被否决 | 为什么 |
|---|---|
| 外部 KMS / Vault / TPM / 人工解锁 | 超出以内网为主的威胁模型，并破坏整包自带和无人值守重启 |
| 随包固定主密钥 | 所有客户共享同一秘密，等于没有加密 |
| 数据库备份内嵌主密钥 | 直接消灭“数据库备份单独泄露仍安全”的唯一保护目标 |
| 整条 DSN 加密 | 扩大秘密面，诱导代码到处拼接和记录连接串 |
| username 一并加密 | username 不是秘密，却会让列表、诊断和轮换都依赖解密 |
| 通用 `Sealer` / `SecretStore` 接缝 | T5 已封闭接缝清单；单实现抽象只增加间接层 |
| 平台执行 `ALTER ROLE` | 监控平台不应修改客户数据库安全状态，且无法与平台库原子提交 |
| PG 新旧密码长期并存 | 为低频人工动作增加双状态与恢复歧义 |
| Agent token 机器绑定 | 防不住主机失陷，却妨碍换机恢复 |
| Agent token 宽限期、自动续签 | 内网 MVP 的人工轮换可接受短暂离线，不值得引入第二令牌状态机 |
| 吊销 = 停用 | 混淆安全事件与部署形态，导致离线告警被错误关闭 |
| 自动定期轮换主密钥 | 增加持续失败面，而当前威胁模型没有对应收益 |
| 解密失败映射为 `NO_DATA` | 把平台自身故障伪装成目标数据库缺数 |
