# 告警规则配置模型 v1.0

> 目标：定义 PostgreSQL 监控平台 MVP 告警能力的最小领域模型、状态语义和行为边界。  
> 适用范围：首版基础阈值告警、当前告警、告警历史、恢复记录和通知记录。  
> 依赖文档：[`01-pg-mvp-metric-dictionary.md`](01-pg-mvp-metric-dictionary.md)。  
> 决策依据与否决记录：[`00-decision-index.md`](00-decision-index.md)。  
> 当前阶段：R1 产品 / 技术设计规格，不是最终数据库表结构。

---

## 1. 设计目标

告警模型需要支撑以下闭环：

```text
指标采集
→ 指标评估
→ 条件满足
→ 告警触发
→ 去重
→ 通知（受维护窗口 / 确认 / 已暂停压制）
→ 持续更新
→ 条件恢复
→ 恢复通知
→ 历史查询
```

首版目标不是建设完整通用告警平台，而是为 PostgreSQL MVP 提供稳定、可解释、低噪声的基础告警能力。

### 1.1 压制统一律

**压制只影响通知。不影响评估、不影响状态、不影响页面可见性。**

这条统一律贯穿本文档，是删除 `Silence` 与 `SuppressionPolicy`、以及把 `SUPPRESSED` 从状态机降为正交标记的共同依据。压制来源在 MVP 中仅三种：**维护窗口**、**确认**、**已暂停**（见 §3.8、§4.3、§4.4）。

## 2. 核心原则

### 2.1 指标字典是告警输入边界

告警规则不能重新定义指标口径，必须引用指标字典中的 `metric_id`。

告警模型依赖指标字典提供：

- 指标名称
- 单位
- 类型：gauge / counter / rate / state
- 维度
- 默认采集周期
- 聚合方式
- 是否可告警
- No Data 语义
- 权限、Agent、扩展依赖
- reset / 差分规则
- 主备角色适用性

### 2.2 首版只支持单指标单条件

MVP 告警规则建议限制为：

```text
一个规则
→ 一个监控对象范围
→ 一个指标
→ 一个条件
→ 一个持续判定
→ 一个恢复策略
→ 一个通知策略
```

暂不支持复杂 AND / OR、多指标计算、PromQL 类表达式或动态基线。

### 2.3 缺数不是 0

No Data 必须作为独立状态或策略处理，不得默认等同于：

- 正常
- 异常
- 0
- 已恢复

### 2.4 规则不等于告警实例

- `AlertRule` 表示用户配置或模板生成的规则。
- `AlertInstance` 表示某个资源上的一次持续异常。
- `AlertEvent` 表示状态变化、通知、确认等历史事件。

同一条规则可以在不同实例或维度上产生多个告警实例。

## 3. 领域对象

### 3.1 `AlertRule` — 告警规则

表示一条可启停、可评估的告警配置。

建议字段：

| 字段 | 说明 |
|---|---|
| `id` | 规则 ID |
| `name` | 规则名称 |
| `description` | 规则说明 |
| `enabled` | 是否启用 |
| `severity` | 严重级别，例如 critical / warning / info |
| `scope` | 监控范围，例如实例、实例组、节点、数据库 |
| `metric_id` | 指标字典 ID |
| `condition` | 条件表达 |
| `evaluation_interval` | 评估周期 |
| `window` | 评估窗口 |
| `consecutive_count` | 连续满足次数（MVP 唯一的持续判定手段） |
| `recovery_policy` | 恢复策略 |
| `no_data_policy` | 无数据策略 |
| `notification_policy_id` | 通知策略。**可空，空 = 继承全局默认策略**（§3.7） |
| `deduplication_policy` | 去重策略 |
| `created_by` | 创建人 |
| `updated_by` | 更新人 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |
| `version` | 规则版本 |

MVP 约束：

- 一条规则只绑定一个 `metric_id`。
- 一条规则只包含一个条件。
- 复杂表达式延后。
- 规则修改应增加 `version`，历史告警保留规则快照。
- **不含 `for_duration`**：持续判定只有 `consecutive_count` 一种（§3.2）。
- **不含 `maintenance_policy_id`**：维护窗口的作用域为实例级，规则不引用它（§3.8）。
- 严重级别固定为 `critical / warning / info` 三档，全序固定，用户不可增删改名重排（§4.4）。

**规则版本切换语义**（未恢复告警实例遇到规则修改）：

1. 保存规则修改时产生新的 `version`。
2. 未恢复的告警实例**保持同一生命周期、实例 ID 和首次触发时间**。
3. 从**下一次评估**开始采用新版本，并**重置尚未完成**的连续触发 / 恢复计数。
4. **不回放历史数据**，不在保存时立即重算、恢复或重新触发，也不拆分出重复告警实例。
5. 历史记录规则版本切换；分别保留首次触发、当前评估和最终恢复时使用的规则快照。

原因：新配置的用途通常正是纠正一条错误或无法恢复的旧规则；但立即重算会让一次「保存」直接制造状态变化与通知，用户不会预期一个配置动作产生这种后果。

### 3.2 `AlertCondition` — 条件表达

表示指标值如何触发告警。

建议字段：

| 字段 | 说明 |
|---|---|
| `metric_id` | 指标 ID |
| `aggregation` | `latest` / `avg` / `max` / `min` / `sum` / `count` |
| `operator` | `>` / `>=` / `<` / `<=` / `=` / `!=` |
| `threshold` | 阈值 |
| `unit` | 阈值单位，必须与指标字典一致 |
| `window` | 统计窗口，例如 5m |
| `consecutive_count` | 连续触发点数 |

示例：

```text
metric_id: pg.connection.active
aggregation: latest
operator: >=
threshold: 90
unit: count
window: 5m
consecutive_count: 3
```

语义说明：

- `evaluation_interval` 是告警引擎多久评估一次。
- `window` 是每次评估时回看多长时间的数据。
- `aggregation` 是对窗口内样本的聚合方式。
- `consecutive_count` 表示连续多少次评估满足条件后进入告警。

**MVP 只支持 `consecutive_count`，不支持 `for_duration`。** `window` 负责样本聚合、`consecutive_count` 负责持续判定，职责已经清晰；两套持续语义并存必须回答「同时配了怎么办」，而它对首版毫无收益。

UI 必须**同时展示连续次数、评估周期及约合时长**（如「连续 3 次 × 30 秒 ≈ 1 分 30 秒」），避免只显示次数而缺少时间感知。修改评估周期属于规则版本变化（§3.1）。

### 3.3 `RecoveryPolicy` — 恢复策略

表示告警如何恢复。

建议字段：

| 字段 | 说明 |
|---|---|
| `auto_recover` | 是否自动恢复 |
| `recovery_operator` | 恢复比较符 |
| `recovery_threshold` | 恢复阈值 |
| `recovery_consecutive_count` | 连续恢复次数，默认继承触发连续次数 |
| `send_recovery_notification` | 是否发送恢复通知，默认开启 |

**每条规则必须具有明确的恢复条件。** 按指标类型分两种形态：

**有序数值告警 —— 必须显式配置独立恢复阈值**，形成滞回区间：

```text
CPU >= 80% 连续 3 次触发
CPU <  70% 连续 3 次恢复
```

**不允许留空后按触发阈值隐式反向恢复。** 原因：指标在单一阈值附近波动会造成反复触发和恢复——这是告警系统最常见的失败模式，且用户往往察觉不到是配置问题。强制滞回把这个坑堵死在配置阶段。

**布尔 / 枚举状态告警 —— 使用明确的反状态恢复**，例如 `reachable = false` 触发、`reachable = true` 恢复。不把并不适用数值阈值的状态告警强行套入 `recovery_threshold` 字段约束。

恢复同样采用连续次数判定。

### 3.4 `NoDataPolicy` — 无数据策略

No Data 来源可能包括：

- 数据库不可达
- Agent 离线
- 无权限
- 扩展未安装
- 指标不适用
- 采集超时
- 采集延迟
- 首个样本无法差分
- 主备切换期间指标暂不可用

**No Data 是已有告警实例的一个状态，不是独立的告警实例。** 去重键仍为「规则 × 资源」——独立实例会在同一规则同一资源上制造两条记录，破坏去重与实例健康归并。

**策略只保留两档：**

| 策略 | 含义 | MVP |
|---|---|---|
| `ignore` | 忽略本次评估，不改变告警状态 | 支持，默认用于短暂缺数 |
| `mark_no_data` | 告警实例进入 `NO_DATA` 状态 | 支持 |
| ~~`fire_no_data`~~ | 缺数本身触发告警 | **不做** —— 缺数的告警通路由采集状态指标的普通规则承担（§6），从而复用完整的严重级别、滞回恢复与通知策略语义，而不另开旁路 |
| ~~`recover_on_no_data`~~ | 缺数视为恢复 | **不做** —— 会把「数据库挂了」表现成「告警恢复了」 |

**进入 `NO_DATA` 的门槛：连续 2 个评估周期缺数，平台固定，规则级不可配。**

不复用 `consecutive_count`：后者定义为「异常持续」语义，而「几次缺数算缺数」是采集健壮性参数，用户没有判断依据。

**统一流转原则：缺数不推进任何状态转换，并清零正在累计的未完成计数。**

| 当前状态 | 缺数未达门槛 | 缺数达门槛 |
|---|---|---|
| `OK` | 保持 `OK`，不累计 | → `NO_DATA` |
| `PENDING` | 保持 `PENDING`，**触发计数清零** | → `NO_DATA` |
| `FIRING` | 保持 `FIRING`，**恢复计数清零** | → `NO_DATA`，**告警实例不恢复、不关闭** |

「清零」使 `consecutive_count` 的「连续」保持字面成立。代价是宁可晚告警也宁可晚恢复——方向一致，且一句话可解释。

**其他约束：**

- `FIRING → NO_DATA` 时告警实例 ID、`first_triggered_at` 与生命周期全部保留，**仍计为一条未恢复告警**。不得让「数据库不可达」把已知问题从实例健康状态里擦掉。
- 告警实例记录 `state_before_no_data`；数据恢复后回到进入前的状态，连续计数从零重新累计。由 `FIRING` 进入的，恢复后须重新累计恢复连续次数才能 `RECOVERED`。
- 长期挂起的 `NO_DATA` **不做基于时长的自动关闭**；仅在实例从平台移除时连带关闭其全部告警实例。
- **`NO_DATA` 本身不产生通知**（见 §3.7），其代价由 §6 的三条内置采集状态规则对冲。
- 告警详情**必须**显示 No Data 原因（不可达 / Agent 离线 / 无权限 / 扩展未装 / 不适用 / 采集超时等）。
- **结构性「不适用」不产生 `NO_DATA`**，也不产生告警实例：`NO_DATA` 的定义是「无法判定」，隐含「本应能判定」；不适用是「没有可判定的东西」。混同会让 No Data 原因列表失去区分度，也会让每台主库永久挂着一批「无数据」标记。

### 3.5 `AlertInstance` — 告警实例

表示某条规则在某个资源上的一次持续异常。

建议字段：

| 字段 | 说明 |
|---|---|
| `id` | 告警实例 ID |
| `rule_id` | 规则 ID |
| `rule_version` | 触发时规则版本 |
| `resource_id` | 实例、节点、数据库、slot 等资源 ID |
| `metric_id` | 指标 ID |
| `state` | 当前状态 |
| `severity` | 严重级别快照 |
| `first_triggered_at` | 首次触发时间 |
| `last_evaluated_at` | 最近评估时间 |
| `last_state_changed_at` | 最近状态变化时间 |
| `recovered_at` | 恢复时间 |
| `current_value` | 当前值 |
| `trigger_value` | 触发值 |
| `threshold_snapshot` | 阈值快照 |
| `trigger_summary` | 触发摘要 |
| `dedup_key` | 去重键 |
| `state_before_no_data` | 进入 `NO_DATA` 前的状态（§3.4） |
| `disposition` | **当前处置状态**：未处置 / 已确认 / 已忽略 |
| `disposition_by` | 最近处置人 |
| `disposition_at` | 最近处置时间 |
| `disposition_note` | 最近处置的可选备注 |
| `ignore_reason_code` | 忽略原因码（忽略时必填） |
| `ignore_reason_detail` | 忽略补充说明（原因码为「其他」时必填） |
| `orthogonal_marks` | **正交标记集合**（见下） |

`AlertInstance` 只展示**最后一次**处置摘要；历次操作由 `AlertEvent` 永久保留，不覆盖旧记录（§3.6）。

**MVP 不设 `owner` / `assignee` / 责任人字段** —— 会引入完整的工单分派语义，超出基础告警 MVP。

#### 正交标记

标记与状态正交，可与**任意**状态共存，不改变状态、不改变页面可见性：

| 标记 | 含义 | 来源 |
|---|---|---|
| `维护中` | 告警所属实例当前落在维护窗口内 | §3.8 |
| `已确认` | 已被确认，重复通知停止 | §4.3 |
| `已暂停` | 所属实例采集已暂停，本实例被**冻结** | §4.4 |

三者都是**压制来源**，均只影响通知（§1.1）。

> **为什么压制不是状态**：`NO_DATA` 表示「无法判定」，状态机确实走不下去，故为真状态；压制表示「判定了，只是不打扰」，判定结果完好，没有理由动状态。若做成状态，`FIRING` 被压制后即丢失「它还在烧」这一事实——实例健康无从计算，解除后回到何处亦无定义。

### 3.6 `AlertEvent` — 告警事件 / 历史

表示告警实例生命周期中的事件记录。

事件类型建议：

| 事件类型 | 说明 |
|---|---|
| `PENDING_STARTED` | 条件开始满足，但未达到持续判定 |
| `FIRED` | 告警触发 |
| `UPDATED` | 告警持续中，值或摘要更新 |
| `RECOVERED` | 告警恢复 |
| `NO_DATA_ENTERED` | 进入无数据状态 |
| `NO_DATA_EXITED` | 退出无数据状态 |
| `ACKED` | 用户确认 |
| `IGNORED` | 用户忽略 |
| `MAINTENANCE_SUPPRESSED` | 被维护窗口压制通知 |
| `FROZEN` | 所属实例采集暂停，本实例冻结（§4.4） |
| `UNFROZEN` | 采集恢复，本实例解冻 |
| `NOTIFICATION_SENT` | 通知发送成功 |
| `NOTIFICATION_FAILED` | 通知发送失败 |

处置事件的字段要求（刻意不对称）：

- `ACKED` 与 `IGNORED` 均记录**操作人、操作时间、操作前后的处置状态**；
- `ACKED` 记录**可选**备注；
- `IGNORED` 记录**必填**原因码和补充说明；
- 告警恢复后仍保留全部处置事件。

事件应保存关键快照：

- 规则版本
- 指标值
- 阈值
- 数据时间
- 采集时间
- 评估时间
- No Data 原因
- 通知渠道和结果

---

### 3.7 `NotificationPolicy` — 通知策略

建议字段：

| 字段 | 说明 |
|---|---|
| `id` | 通知策略 ID |
| `name` | 策略名称 |
| `is_default` | 是否为全局默认策略。**有且仅有一个，不可删除**，内容可编辑、可改名 |
| `contacts` | 联系人 |
| `contact_groups` | 联系人组 |
| `channels` | 通知渠道，**仅邮件（SMTP）与 Webhook** |
| `severity_filter` | 哪些严重级别触发通知（**过滤**，不是路由） |
| `notify_on_fire` | 触发时通知 |
| `notify_on_recovery` | 恢复时通知，**默认开启** |
| `repeat_interval` | 重复通知间隔。**必填**，默认 1 小时，范围 15 分钟 – 24 小时 |
| `template_id` | 通知模板 |

**平台自管「谁收」，不自管「怎么送」。**

**渠道只做两个：**

- **Webhook** —— 通用出口。客户已有告警中台的从此接出，平台不参与投递细节。
- **邮件（SMTP）** —— 唯一原生渠道，保证平台不依赖任何外部系统也具备独立告警能力。

短信 / IM / 电话**不做原生适配**，一律走 Webhook：私有化环境下各家网关与 IM 差异过大，逐个适配是无底洞。

**联系人模型仅一层**：联系人（姓名 + 邮箱 + 可选外部 ID）、联系人组（**无嵌套**）。通知策略绑定联系人组与渠道。

**规则与策略的绑定：全局默认 + 规则覆盖**

1. 默认策略有且仅有一个，不可删除；
2. 规则级**单选**一个策略，不做多绑、不做路由；
3. **覆盖即替换**，非叠加——规则绑了 X 就完全走 X，默认策略不再参与；
4. 规则列表与编辑页**必须回显生效策略名**，继承者显示「默认策略（继承）」。这是覆盖模型唯一的真代价，用显式回显消掉。

> 采用默认策略而非「规则必选」的决定性依据是 §6 的三条内置规则：它们不可删除、不可停用，若采用必选模型，装机瞬间这三条规则要么无通知归属（正是要堵死的静默事故），要么被强绑一条系统预置策略——那已经是默认策略，只是模型上不承认。

**重复通知：`repeat_interval` 必填，不提供「不重复」选项，不做 `max_repeat_count`。**

两者都会造成未恢复告警永久静音，抽掉 §3.8「维护窗口结束不补发」所依赖的前提。**吵是设计的一部分，止吵的唯一正确动作是「确认」**（§4.3）。

**通知记录与失败可见性：**

- 每一次通知尝试留痕：告警实例、事件类型（触发 / 恢复 / 重复）、渠道、目标、发送时间、结果、失败原因、重试次数。
- 重试固定 **3 次指数退避**后放弃并记为终态失败，不可配。
- 三层可见性：告警详情页展示该告警的通知记录列表；通知渠道配置页展示各渠道最近失败次数与最后一次失败原因；「告警设置 → 通知渠道」页签上显示**导航角标**。
- **不做**「通知失败本身产生告警」—— 递归：该告警的通知同样可能失败。

**不做**：值班排班、轮值、升级路由、按严重级别分渠道路由、通知聚合 / 分组、全局通知记录查询页。

### 3.8 `MaintenanceWindow` — 维护窗口

MVP 中**唯一的压制类领域对象**。`Silence` 与 `SuppressionPolicy` 已删除，理由见本节末尾。

**字段（削到最小）：**

| 字段 | 说明 |
|---|---|
| `id` | 维护窗口 ID |
| `instance_ids` | **实例级作用域**，可多选实例 |
| `starts_at` | 开始时间 |
| `ends_at` | 结束时间 |
| `reason` | 原因 |
| `created_by` | 创建人 |

**不做** `repeat_rule`，**不做**规则级 / 标签级 / 实例组级作用域——作用域维度是复杂度的主要来源，削到实例级已覆盖真实场景。

**行为：**

- 窗口期间**继续评估**，正常生成和更新告警实例与历史，**只压制通知**。
- **不提供「是否生成告警」开关**——固定为「生成」。一个没人能说清后果的开关不是灵活性。
- 窗口结束**不补发**被压制的通知、不排队重放、不发「维护结束摘要」；仍未恢复的告警交由重复通知在下一个 `repeat_interval` 自然接管。
  - **硬约束**：由此要求 §3.7 的重复通知**必须存在且不可关闭**，否则「不补发」退化为「维护期间起的火永久静音」。
- 窗口内产生或更新的告警实例与历史事件带**维护窗口标记与窗口引用**，使告警历史可区分「维护造成的」与「真出事的」。
- **不影响页面可见性**：当前告警页照常显示这些告警，仅带标记。

> 否决「暂停评估」的理由：它需要回答三个问题——冻结在哪个状态、结束后计数从零起步造成多长的发现延迟、窗口内数据缺失导致事后无法复盘。「继续评估 + 压通知」全部规避，且窗口内数据完整可查。

**管理面归属**：平台级「告警设置 → 维护窗口」页为**唯一管理面**（列表 / 创建 / 编辑 / 提前结束 / 删除）；实例工作台只有只读维护状态标记和一个预填当前实例的「新建维护窗口」快捷入口，**不承载列表、编辑、删除**。详见 [`03-monitor-platform-ia-draft.md`](03-monitor-platform-ia-draft.md) §3。

#### 已删除：`Silence`（静默）

止吵收敛到两个已有机制：

- **计划内、尚未发生** → 维护窗口；
- **已经发生、正在处理** → **确认**（§4.3，正式定义为「停止该告警实例的重复通知」）。

保留 `Silence` 等于让「确认」和「静默」两个作用相同的按钮并存，还要维护两套过期与解除语义。

**代价与缓解**：确认无到期时间，等同一次无限期止吵。缓解措施是——告警恢复后若再次触发，是**新的告警实例，不继承确认状态**。

#### 已删除：`SuppressionPolicy`（根因抑制）

原草案举的两个例子在本模型下已被提前解决：实例不可达 / Agent 离线时，派生规则**采不到数**，进入的是 `NO_DATA` 而非 `FIRING`——本就没有通知可抑制（且 `NO_DATA` 本身不通知）。

真正需要根因抑制的是**指标间因果**（CPU 打满 → 连接堆积 → TPS 跌 → 复制延迟涨），需要因果图或表达式，而 §8 已明确首版不做。

### 3.9 `AlertTemplate` — 内置告警模板

内置模板是“一键告警”的基础，不应只是 UI 按钮。

建议字段：

| 字段 | 说明 |
|---|---|
| `id` | 模板 ID |
| `name` | 模板名称 |
| `metric_id` | 适用指标 |
| `default_severity` | 默认严重级别 |
| `default_threshold` | 默认阈值 |
| `default_aggregation` | 默认聚合 |
| `default_window` | 默认窗口 |
| `default_consecutive_count` | 默认连续次数 |
| `default_recovery_policy` | 默认恢复策略 |
| `required_capability` | 所需能力，例如 Agent、扩展、权限 |
| `applicable_pg_versions` | 适用 PG 版本 |
| `version` | 模板版本，随平台升级 |

**模板与规则的关系：**

- **内置模板只读**，可由平台版本升级；用户不能直接覆盖。
- 基于模板创建规则时**复制默认值形成独立规则**；创建时允许修改触发阈值、恢复阈值、连续次数、严重级别、作用范围和通知策略。
- 创建后的规则**不自动跟随**模板更新，并记录来源模板及模板版本。
- **不支持**「另存为自定义模板」、自定义模板库或模板共享——会引入模板所有权、权限、版本传播、删除引用、升级冲突一整套第二资产管理问题。首版复用需求通过**复制已有规则**满足。

### 3.10 `AlertTriggerSnapshot` — 触发现场快照

告警触发时的会话 / 阻塞现场，**从属于告警实例的只读证据**，不是通用会话历史。

**采集时机与范围：**

- 只在告警实例**首次进入 `FIRING`** 时采集**一次**。持续评估、数值更新和处置变化均不重复采集。
- 只对**会话/阻塞现场能直接解释原因**的告警采集：

  | 告警类型 | 快照范围 |
  |---|---|
  | 锁等待 / 阻塞会话过多 | 触发时全部等待会话及完整阻塞链（含直接与递归阻塞源） |
  | 长事务 | 达到规则阈值的长事务会话，以及相关等待 / 阻塞关系 |
  | `idle in transaction` 过多 | 达到阈值的会话，以及它们持锁所阻塞的会话 |
  | 活跃连接数过高 | 按查询持续时间降序保存活跃会话 Top 50 |

- **不采集**：实例不可达、Agent 离线、主机资源、复制 / WAL / slot 等与会话现场无直接诊断关系的告警。
- 每份快照最多 **100 个会话**；超限时优先保留直接命中对象和完整阻塞链，并记录原始匹配数量与截断状态。
- 字段沿用会话与阻塞页面的诊断字段，**不含 SQL 文本**（平台不承载 SQL，见 [`00-decision-index.md`](00-decision-index.md) ADR-06）。
- 采集失败**不影响告警触发**，但须记录并展示失败 / 缺失原因。

**对象与留存边界：**

- 一个告警实例最多关联**一份**首次触发快照；`FIRED` 事件可引用它。
- 告警详情与关联性能事件详情**引用同一份**快照，不复制数据；性能事件详情中必须标注为「告警触发时现场」，不得误呈现为当前状态。
- 产品上至少表达：捕获时间、成功 / 失败、适用告警类型、会话条目、阻塞关系、原始匹配数、是否截断、失败 / 缺失原因。
- 生命周期跟随告警历史；告警历史清理时关联快照同步清理。
- **不提供**独立保留期限、手动删除、归档或导出配置。

> 这是 MVP 唯一的触发式历史子集，**不形成通用会话历史能力**——会话与阻塞页只展示当前瞬时状态。全量周期性保存会同时增加数据库查询压力、高基数存储量和敏感数据暴露面，而排障价值集中在告警触发那一刻。

## 4. 告警状态机

### 4.1 状态定义

| 状态 | 含义 |
|---|---|
| `OK` | 当前未触发 |
| `PENDING` | 条件满足，但尚未达到连续次数或持续时间 |
| `FIRING` | 告警已触发且未恢复 |
| `NO_DATA` | 评估所需数据不可用或过期 |
| `RECOVERED` | 告警已恢复，进入历史 |

**状态就是这五档，没有第六档。** `SUPPRESSED` **不是状态**——压制是告警实例上的正交标记（§3.5），可与任何状态共存。UI 中「维护中 / 已确认 / 已暂停」显示在状态**旁边**，不是状态标签本身。

### 4.2 推荐状态流转

```text
OK
 ├─ 条件满足但未持续足够久 → PENDING
 ├─ 连续 2 周期数据缺失 → NO_DATA

PENDING
 ├─ 连续满足达到阈值 → FIRING
 ├─ 条件不满足 → OK
 ├─ 数据缺失未达门槛 → 保持 PENDING，触发计数清零
 ├─ 连续 2 周期数据缺失 → NO_DATA

FIRING
 ├─ 恢复条件连续满足 → RECOVERED
 ├─ 数据缺失未达门槛 → 保持 FIRING，恢复计数清零
 ├─ 连续 2 周期数据缺失 → NO_DATA（实例不恢复、不关闭，仍计一条未恢复告警）

NO_DATA
 └─ 数据恢复 → 回到 state_before_no_data，连续计数从零重新累计

RECOVERED
 └─ 新一轮条件满足 → 新 AlertInstance（不继承确认状态）
```

**压制不出现在这张图里**——维护窗口、确认、已暂停都不产生状态迁移（§1.1）。「已暂停」是唯一会**冻结**迁移的标记，见 §4.4。

### 4.3 确认 / 忽略的语义

确认与忽略**共享一个当前处置状态，可相互切换**，均不自动恢复告警。

| | 确认（`ACKED`） | 忽略（`IGNORED`） |
|---|---|---|
| 含义 | 有人知道了，正在处理 | 这不该算作实例的健康问题 |
| 操作人 / 时间 | 自动记录 | 自动记录 |
| 备注 | **可选** | —— |
| 原因 | —— | **必填**原因码 |
| 对通知的影响 | **停止该告警实例的重复通知**；恢复通知照发 | 不停止通知 |
| 对实例健康的影响 | 无，仍按级别染色 | **退出健康归并** |

**忽略原因码**：`已知问题，暂不处理` / `误报` / `重复告警` / `影响可接受` / `其他`。补充说明默认可选，选「其他」时必填。

字段要求的不对称是刻意的：**确认应当足够快捷**，否则值班人员不会用；**忽略会降低关注度**，必须留下可审计依据。

**两种处置的共同边界：**

- 均**不触发恢复、不停止评估、不等于静默、不停用规则**；告警是否恢复仍由恢复条件决定。
- `AlertInstance` 只展示最后一次处置摘要，历次操作由 `AlertEvent` 永久保留，不覆盖旧记录。
- 告警恢复后再次触发是**新的告警实例，不继承处置状态**。

> **两者作用面互不重叠**：确认 = 别再通知我；忽略 = 这不该算作实例的健康问题。忽略的告警仍在告警列表可见、仍继续评估、仍走重复通知，只是退出实例健康归并。防滥用护栏见 [`03-monitor-platform-ia-draft.md`](03-monitor-platform-ia-draft.md) §7.1。

### 4.4 采集暂停下的冻结语义

实例采集被暂停时（`03` §4.8.2），该实例下的**存量未恢复告警实例被冻结**：

- 状态**原地保留**在按下暂停的那一刻，不再迁移，**不发任何通知**；
- 仍在告警列表可见，带 `已暂停` 正交标记；全局筛选默认将其排除在「当前告警」之外；
- 暂停期间的空窗**不产生 `NO_DATA`**（评估已停）；
- **解冻不回放**：按解冻后下一次评估的实际结果重新判定——条件仍满足则**延续同一条告警实例**继续 `FIRING`（**不新建**，避免解冻瞬间制造假的「新告警」风暴）；不满足则走正常 `RECOVERED` 流程并通知；
- **暂停实例永不产生新的告警实例**。

> 否决「暂停时把存量告警强制关闭为 `RECOVERED`」：这是谎报——条件根本没恢复，只是不看了。连带两个错误后果：恢复通知会发出一批假恢复；实例列表的「近期恢复(24h)」标记会给这台实例挂上「刚刚好转」的暗示。历史被污染，事后复盘看不出真相。

## 5. 去重策略

MVP 默认去重键：

```text
rule_id + resource_id + metric_dimension
```

示例：

- CPU 高：`rule_id + instance_id + node_id`
- 连接数高：`rule_id + instance_id`
- replication slot 积压：`rule_id + instance_id + slot_name`

同一去重键在未恢复前不得每次评估都创建新的告警实例，只更新已有实例。

## 6. MVP 内置告警

### 6.1 三条内置采集状态规则（不可删除、不可停用）

| 告警 | 指标 ID | 默认严重级别 | 建议条件 |
|---|---|---|---|
| **数据库不可达** | `pg.availability.reachable` | `critical` | 连续 N 次失败 |
| **Agent 离线** | `agent.status` | `critical` | offline 持续 N 次 |
| **数据过期** | `collector.last_success_time` | `warning` | 采集新鲜度超阈值 |

它们是**普通规则**，走本文档全套语义（连续次数、滞回恢复、通知策略），阈值、严重级别、通知策略均可修改；**受限的只有「存在与启用」**——不可删除、不可停用。

**严重级别下限为 `warning`**（取值仅 `warning` / `critical`）。原因：实例健康模型中 `info` 不改变主状态，若允许把「数据库不可达」改成 `info`，数据库挂了实例列表仍全绿，而 `NO_DATA` 本身按 §3.4 不通知——这正是本设计要堵死的静默事故换了个入口。

> 这是本文档唯一一处限制用户自由的地方，用以堵死「`NO_DATA` 不通知 + 采集状态规则被关掉 = 数据库挂了平台一声不吭」这一唯一可能造成静默事故的组合。

### 6.2 其余内置告警模板

| 告警 | 指标 ID | 建议条件 | 说明 |
|---|---|---|---|
| 主动探针延迟过高 | `pg.probe.latency_ms` | max 或 avg 超阈值 | 必须配置恢复阈值 |
| CPU 高 | `host.cpu.usage_percent` | avg >= 80% 持续 | 可用 70% 恢复 |
| 内存高 | `host.memory.usage_percent` | avg >= 85% 持续 | 需固定内存口径 |
| 磁盘不足 | `host.disk.usage_percent` / `host.disk.free_bytes` | 使用率高或剩余空间低 | 推荐同时支持百分比和剩余空间 |
| 连接数过高 | `pg.connection.total` | latest 或 max 超阈值 | 可参考 max_connections |
| 活跃连接数过高 | `pg.connection.active` | max 超阈值 | 关联会话列表 |
| idle in transaction 过多 | `pg.connection.idle_in_transaction` | latest 超阈值 | 关联长事务 |
| 长事务 | `pg.transaction.max_duration_sec` | max 超阈值 | 关联会话详情 |
| 锁等待 | `pg.lock.waiting_count` | latest > 0 持续 | 关联阻塞链 |
| 阻塞会话 | `pg.session.blocked_count` | latest > 0 持续 | 关联阻塞链 |
| 长查询数量过多 | `pg.query.long_running_count` | latest 超阈值持续 | 关联长查询采样记录 |
| 复制延迟过高 | `pg.replication.wal_lag_bytes` | 超阈值持续 | **仅 WAL 字节口径**；时间延迟不可作告警指标 |
| Slot WAL 积压 | `pg.replication_slot.retained_wal_bytes` | 超阈值持续 | 关联磁盘风险 |
| 临时文件写入过高 | `pg.temp.bytes_per_sec` | avg 或 max 超阈值 | 关联 SQL / 会话候选 |
| 2PC 数量异常 | `pg.prepared_xacts.count` | latest > 0 或超阈值 | 视业务是否使用 2PC |

## 8. 应避免过度设计

首版不建议实现：

1. 任意多层嵌套 AND / OR。
