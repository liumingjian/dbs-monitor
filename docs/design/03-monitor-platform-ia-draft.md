> 目标：定义 PostgreSQL 监控平台 MVP 的页面结构、页面职责、导航关系和排障路径。  
> 产品定位：私有化 PostgreSQL 运维排障工作台。  
> 参考依据：[`../research/aliyun-rds/aliyun-rds-pg-monitor-feasibility-report.md`](../research/aliyun-rds/aliyun-rds-pg-monitor-feasibility-report.md)、[`01-pg-mvp-metric-dictionary.md`](01-pg-mvp-metric-dictionary.md)、[`02-alert-rule-model-draft.md`](02-alert-rule-model-draft.md)。  
> 决策依据与否决记录：[`00-decision-index.md`](00-decision-index.md)。  
> 当前阶段：R1 信息架构规格，不是完整 PRD、交互原型或视觉设计。

## 1. 设计原则

### 1.1 阿里云优先，差异驱动澄清

对调研中有可靠证据的**功能范围、信息架构、页面划分、指标组织、控件与交互**，第一版默认复刻——已被验证过的设计不需要重新发明，用户的既有习惯也是资产。只重点讨论以下三类偏离：

1. 私有化部署带来的限制（无云管控面、无法重启数据库、权限受限）；
2. PostgreSQL 自身的能力差异；
3. 明显超出 MVP 成本或与产品目标冲突的部分。

**不复刻的部分**：云厂商特有的计费、套餐、DAS 品牌概念和内部技术实现；以及服务于云产品全家桶的那部分导航层级——本平台聚焦私有化 / AP 场景下的数据库运维排障，顶层结构按 §3 收敛为四个节点。

### 1.2 以实例为核心对象

首版围绕 PostgreSQL 实例组织信息：

```text
实例
→ 指标
→ 会话 / 阻塞
→ 性能事件
→ 告警
→ 采集状态
```

用户进入平台后的主要任务不是浏览产品功能，而是判断某个实例是否健康、异常从何而来、下一步看哪里。

### 1.3 以排障路径组织页面

页面应支持以下连续问题：

1. 实例是否可用？
2. 数据是否新鲜可信？
3. 主机资源是否异常？
4. 数据库负载是否异常？
5. 是否有慢 SQL、长事务、锁等待、阻塞链？
6. 是否有复制延迟？
7. 是否有性能事件？
8. 是否触发告警？
9. 下一步应该看哪个证据？

### 1.4 空状态必须解释原因

所有页面必须区分：

- 加载中
- 暂无样本
- 当前时间范围无数据
- 数据过期
- 数据库不可达
- 无权限
- Agent 离线
- 扩展未安装
- 功能未启用
- 当前版本不支持
- 当前实例角色不适用
- 采集异常

不要只显示空图表或空表格。

## 2. 信息层级

建议采用三层结构。

```text
平台级
├── 实例列表（= 平台首页）
├── 全局告警
└── 告警设置

实例级（实例工作台）
├── 实例总览
├── 标准监控
├── 增强监控
├── 会话与阻塞
├── 性能事件
├── 告警
└── 采集管理

详情级
├── 指标详情
├── 会话详情
├── 阻塞链详情
├── 长查询采样记录
├── 性能事件详情
├── 告警详情
└── 采集能力详情
```

**平台级不做**：独立 Dashboard / 聚合大盘（首页即实例列表）、全局性能事件（事件仅实例级）、跨实例的采集管理视图。

必须保留实例列表和实例工作台的清晰边界。

顶层四个节点。

```text
数据库监控平台

│   ├── 实例健康（主状态 + 归因行 + 计数与标记，见 §4.1）
│   ├── Agent 状态｜最近采集时间｜数据新鲜度（独立列，不参与健康计算）

├── 实例工作台

│   │   ├── 核心资源摘要
│   │   ├── 数据库负载摘要
│   │   ├── 复制状态摘要
│   │   ├── 近期性能事件
│   │   ├── 维护状态只读标记 +「新建维护窗口」快捷入口
│   │   └── 快速排障入口
│   │
│   ├── 监控与报警
│   │   ├── 标准监控（页签）
│   │   │   ├── 资源指标
│   │   │   ├── 数据库指标
│   │   │   ├── 复制指标

│   │   │   └── 指标详情

│   │       ├── 短窗口高频指标（数据库 / IO / 复制）
│   │       ├── 指标管理｜时间选择｜聚合方式｜布局切换
│   │       └── 指标含义与详情
│   │
│   ├── 会话与阻塞
│   │   ├── 活跃会话
│   │   ├── 长事务
│   │   ├── 锁等待
│   │   ├── 阻塞链
│   │   ├── 长查询采样记录
│   │   ├── 查询统计排行（pg_stat_statements 可用时）
│   │   └── 会话详情
│   │
│   ├── 性能事件
│   │   ├── 触发中
│   │   ├── 已恢复
│   │   ├── 已确认 / 已忽略（反映底层告警的处置状态）
│   │   └── 事件详情
│   │
│   ├── 告警
│   │   ├── 告警规则
│   │   ├── 当前告警
│   │   ├── 告警历史
│   │   └── 告警详情
│   │
│   └── 采集管理
│       ├── 配置缺失待办（置顶，唯一可执行模块）
│       ├── 采集总状态
│       ├── Agent 状态
│       ├── 数据库连接与权限检查
│       ├── 扩展 / 插件能力
│       ├── 指标采集状态

    ├── 通知策略
    └── 维护窗口（唯一管理面）
```

### 3.1 顶层区「告警设置」的边界

命名刻意收窄为「告警设置」而非「系统管理」，把该区边界钉死在告警域的四类对象上，挡住实例接入、用户管理、License 等无关物往里堆。

理由：通知渠道与联系人是**跨实例单例**，挂进实例工作台会让「实例 A 的通知渠道」这种读法成立，而它不成立（改一次影响全平台），违背 §1.2「以实例为核心对象」；挂进「全局告警」则把纯观察面变成观察 + 配置混合体。

### 3.2 导航角标

两处**非告警**的视觉信号，均不进入状态机、不产生告警实例、不发通知、不影响实例健康：

| 角标 | 位置 | 含义 |
|---|---|---|
| 通知失败 | 告警设置 → 通知渠道 | 存在近期未清除的渠道失败 |
| 已暂停实例数 | 实例列表 | 当前有多少实例处于暂停采集状态 |

角标是「要可见但不要状态化」的统一表达方式。**残留风险显式接受**：角标仅在有人登录时起作用；真正兜底的是邮件与 Webhook 双通道并存（`02` §3.7）。

## 4. 页面职责

### 4.1 实例列表

#### 页面目标

帮助用户从多个 PostgreSQL 实例中快速发现需要关注的对象。

#### 主要问题

- 哪些实例异常？
- 哪些实例正在告警？
- 哪些实例采集不正常？
- 哪些实例最近没有数据？

#### 三层信息契约

列表行 / 卡片的信息层级**固定为三层**，其余一概不进列表：

```text
[● 严重]  pg-prod-01   10.0.1.21:5432 · prod · PG14 · 主库
          复制延迟超阈值 (WAL 512MB)                        ← 归因行
          C1  W3  I2    ⟨无数据⟩ ⟨维护中⟩ ⟨已忽略2⟩ ⟨配置缺失3⟩ ← 计数 + 正交标记
```

1. **主状态** —— §7.1 的四档之一或「已暂停」override，色块 + 文字（色盲可辨），决定排序与默认筛选。
2. **归因行** —— **最坏那条参与归并的未恢复告警**的规则名 + 当前值。同级并列时取首次触发时间最早者（最久未处理优先），不做多行堆叠。跳过已忽略告警；**不跳过 info**——当主状态为「正常」且仅有 info 告警时，归因行展示最早的那条 info，使绿色实例也有一句话交代。
3. **计数与正交标记** —— `C / W / I` 三档未恢复告警计数（**不含已忽略**，与健康归并同口径）+ 标记集合。

#### 独立展示列（不参与健康计算）

- Agent 状态
- 最近采集时间
- 数据新鲜度

这三项经 `02` §6 的三条内置规则进入告警、再进入健康，**不作为独立健康输入**——否则会双重计数同一事实（§7.1）。

#### 「已暂停」的展示

- 显示**暂停时长**（`已暂停 3 天` / `已暂停 92 天`），超过 **7 天**阈值时长文字转警示色。
- 实例列表**只读不可操作**暂停；操作入口唯一在采集管理页（§4.8）。

#### 筛选与排序

- 主状态（多选）
- 正交标记（多选）：`无数据` / `维护中` / `近期恢复(24h)` / `已忽略 N` / `配置缺失 N`
- 「至少有一条 X 级告警」
- 「存在 info 告警」
- 「存在配置缺失」

默认视图按主状态严重度倒序，**不隐藏任何实例**。

#### 主要入口

- 平台首页
- 全局搜索
- 告警通知回跳

#### 主要出口

- 实例总览
- 当前告警
- 采集管理

---

### 4.2 实例总览

#### 页面目标

回答“这个实例现在是否健康，下一步应该看哪里”。

#### 置顶：主状态与归因行

实例总览**复用实例列表的同一模型**——同一主状态 + 同一条归因行置顶，其下才是各摘要模块。列表与总览由此永不打架。

同时置顶展示（若适用）：**维护状态只读标记**（「维护中，至 14:00，原因：…」）与**已暂停标记**（含时长）。二者均只读，操作入口分别在「告警设置 → 维护窗口」和本实例的采集管理页；总览另提供一个**「新建维护窗口」快捷入口**（打开同一张表单，仅预填当前实例）。

#### 核心模块

1. 可用性与采集状态
   - 实例连通性
   - 主动探针延迟
   - 最近采集时间
   - Agent 状态

   > 本模块**只陈述事实，不自行判定健康**。健康由置顶主状态统一表达。

2. 当前告警摘要
   - critical / warning 数量
   - 最近触发告警
   - 未恢复告警

3. 核心资源摘要
   - CPU
   - 内存
   - 磁盘
   - IO
   - 网络

4. 数据库负载摘要
   - 总连接数
   - 活跃连接数
   - TPS
   - 临时文件写入
   - 长事务
   - 锁等待

5. 复制状态摘要
   - 当前角色
   - 复制连接状态
   - 复制延迟
   - Replication slot 积压

6. 近期性能事件
   - 触发中事件
   - 最近恢复事件
   - 建议动作摘要

7. 快速排障入口
   - 查看标准监控
   - 查看会话与阻塞
   - 查看告警详情
   - 查看采集状态

#### 注意

实例总览不应承载完整图表大盘。它应以摘要、异常和入口为主。

### 4.3 标准监控

> 标准监控与增强监控（§4.4）是「监控与报警」下的**两个并列页签**，复刻阿里云已取证的设计。两者的边界不是采样频率——阿里云标准监控本身也有 5 秒粒度——而是**页面角色、指标组织和诊断控件**共同构成的。

#### 页面目标

回答“指标趋势如何，异常从什么时候开始”。

#### 核心模块

- 时间范围选择
- 数据粒度选择
- 图表列数 / 布局
- 光标联动
- 资源指标区
- 数据库指标区
- 复制指标区
- 指标详情说明

#### 指标分组

```text
资源指标
├── CPU
├── 内存
├── 磁盘空间
├── 磁盘 IO / IOPS
└── 网络流量

数据库指标
├── 连接数
├── 活跃连接数
├── idle in transaction
├── TPS
├── 提交 / 回滚
├── 读写行数
├── 临时文件
├── 长事务
├── 锁等待
├── 阻塞会话
├── 长查询数量
└── 2PC

复制指标
├── 实例角色
├── 复制连接状态
├── WAL 延迟（告警口径）
├── 复制回放时间延迟（仅辅助展示）
└── Replication slot 积压
```

#### 图表布局

按已取证的阿里云基线执行：时间范围选择、数据粒度选择、图表列数切换、光标联动、指标管理。**MVP 不做用户自定义图表布局的持久化**（拖拽排布、个人布局方案保存）——列数切换已覆盖主要诉求，其余属实现层细节。

#### 页面出口

- 指标详情
- 会话与阻塞，继承实例和时间范围
- 长查询采样记录（从慢查询趋势图下钻）
- 性能事件，查看相关事件
- 告警详情，查看触发记录
- 采集管理，查看数据不可用原因

### 4.4 增强监控

#### 页面目标

回答“最近这一小段时间里，数据库、I/O、复制发生了什么”——短窗口、高频诊断。

#### R1 基线（复刻已取证的阿里云配置）

| 项 | 基线 |
|---|---|
| 时间窗口 | 最近 30 分钟 |
| 数据粒度 | 5 秒 |
| 聚合方式 | 平均值 |
| 布局 | 两列 |
| 控件 | 指标管理、时间选择、聚合方式、布局切换、指标含义与详情 |

#### 产品语义

- **页签始终可见**，不设置用户手动启停增强监控的产品状态。
- 能力不足时**局部降级并显示原因**，不隐藏整个模块。
- 页面须说明高频监控的**资源代价**。
- **不引入**阿里云的计费、套餐或 DAS 品牌语义。

> 持续采集 vs 按需采集、自动到期、底层采集管线共用还是独立——均属实现层，不在本文档决定。

#### 慢查询在两页的分工

- **标准监控**：慢查询数量趋势（`pg.query.long_running_count`）。
- **增强监控**：5 秒粒度的慢查询数量趋势。
- 两者均支持从图表**下钻到长查询采样记录**（§4.5）。
- **不新增独立的「慢 SQL 分析」模块。**

---

### 4.5 会话与阻塞

#### 页面目标

回答“当前哪些会话、事务或锁等待正在影响数据库”。

#### 核心模块

1. 活跃会话列表
2. 长事务列表
3. 锁等待列表
4. 阻塞链视图
5. **长查询采样记录**
6. **查询统计排行**（`pg_stat_statements` 可用时）
7. 会话详情

#### 典型字段

- PID
- 用户名
- 数据库名
- 客户端地址
- 状态
- 查询开始时间
- 事务开始时间
- 查询持续时间
- 事务持续时间
- 等待事件类型
- 等待事件
- 阻塞源 PID
- 阻塞链摘要

#### SQL 文本边界

**MVP 不承载 SQL 文本。** 平台不展示原始 SQL、脱敏 SQL、归一化 SQL 或截断摘要；不提供「查看原文」、SQL 复制、SQL 内容搜索或 SQL 导出；**不保存 SQL，也不维护平台标识到 SQL 文本的映射**。

改为使用 PostgreSQL 原生定位信息：

| 页面 | 展示的定位信息 |
|---|---|
| **长查询采样记录**（`pg_stat_activity` 下钻） | 会话 **PID**、`query_start`、`sampled_at`、数据库、数据库用户 |
| **查询统计排行**（`pg_stat_statements`） | **queryid**、数据库、数据库用户、统计区间 |

- 两类标识**语义独立**，不用「SQL ID」「SQL 编号」统称，也不承诺二者可关联。
- 定位字段可复制；若页面已有记录导出能力，可随该条记录导出。**不新增**按 PID / queryid 的专门搜索能力。
- 平台**不生成后台查询 SQL、不代查、不跳转数据库**；用户凭自身数据库权限自行排查。
- **时效语义必须说明**：PID 和 queryid 都只是**尽力而为的后台排查线索**，不是永久引用，也不保证能恢复 SQL——可能因查询结束、PID 复用、统计重置、条目淘汰、扩展状态或 PG 大版本变化而失效。

#### 命名与降级表达

- `pg_stat_activity` 下钻命名为**长查询采样记录**；趋势图入口使用「查看采样记录」。
- `pg_stat_statements` 页面命名为**查询统计排行**。
- **不使用**「慢 SQL 明细」「Top SQL 明细」等暗示可查看 SQL 内容或完整执行历史的名称。
- 查询统计排行**保留入口**，并区分：未启用 / 权限不足 / 暂时不可用 / 统计已重置 / 区间内无记录。**不可用不得表现为空表或「暂无数据」**。
- 页面只说明能力状态和排查方向，**不提供**启用扩展、提升权限或执行 SQL 的按钮。长查询采样记录**独立可用**，不依赖扩展。

#### 时间语义

**只展示最近一次成功采集的当前瞬时状态**，并显示采集时间和数据新鲜度。

**不提供**任意历史时间点、周期快照回放或历史会话搜索。唯一的历史子集是告警触发现场快照（`02` §3.10），且只能从告警详情或关联性能事件详情进入。

#### MVP 操作边界

首版默认只读排障，不开放：

- kill session
- cancel query
- 批量终止会话
- 自动处理阻塞

如未来开放，必须增加权限、二次确认、审计和风险提示。

### 4.6 性能事件

#### 页面目标

回答“平台识别出了哪些异常、原因摘要和建议动作”。

#### 事件来源：告警派生，仅实例级

性能事件不是 PostgreSQL 原生事件，也**不是第二套评估引擎**。R1 的事件来源**只有一条**：

> 选定类型的告警（锁等待 / 阻塞链、长事务、复制延迟、临时文件突增等）进入 `FIRING` 时，**顺带派生**一条**实例级**事件。

事件在告警之上只叠加三样告警模型没有的东西：

1. **原因摘要 + 建议动作**（按事件类型的知识模板）；
2. **证据链聚合**（关联指标图 + 告警触发现场快照）；
3. **事件类型分类**。

**v1 不做**：独立事件规则、事件规则编辑 UI、日志派生事件、全局（跨实例）性能事件。

#### 核心模块

- 触发中事件
- 已恢复事件
- 已确认 / 已忽略事件
- 事件详情

#### 事件字段

- 事件 ID
- 实例
- 级别
- 类型
- 状态
- 首次发生时间
- 最近发生时间
- 持续时长
- 触发指标
- 原因摘要
- 建议动作
- 关联指标图
- 关联会话 / 阻塞快照
- 关联告警

#### 确认 / 忽略：共享单一状态，归属告警

处置状态**只有一份，归属告警**（`02` §4.3）。事件继承并展示它——「已确认 / 已忽略事件」页签反映的是底层告警的处置状态。事件页即便提供确认动作，也是**写回那条告警**，状态永远只有一份，不会分叉。

#### 与告警的区别

| 对象 | 重点 |
|---|---|
| 告警 | 用户配置规则、通知、确认、恢复、审计 |
| 性能事件 | 平台识别异常、原因摘要、建议动作、证据链 |

可能出现：

- 有告警但没有性能事件（该告警类型不在派生清单内）。
- 同一异常同时关联告警和性能事件。

**不会出现**：有性能事件但没有对应告警——该场景是独立事件规则的唯一理由，随之推后至 post-MVP。

#### 引用快照的表达要求

若关联告警具有触发现场快照，事件详情**引用同一份证据**（不复制数据），并必须标注为**「告警触发时现场」**，不得误呈现为当前状态。

### 4.7 告警

#### 页面目标

回答“哪些规则触发了通知，是否恢复，是否有人处理”。

#### 子页面

```text
告警
├── 告警规则
├── 当前告警
├── 告警历史
└── 告警详情
```

#### 告警规则

- 规则名称

- 作用范围
- 条件
- 周期 / 窗口 / 连续次数（及约合时长）
- 严重级别

#### 当前告警

展示：

- 当前状态（五档之一）
- **正交标记**：`维护中` / `已确认` / `已忽略` / `已暂停`
- 严重级别
- 实例 / 资源
- 规则名称
- 触发值
- 阈值
- 首次触发时间
- 持续时间
- No Data 原因

#### 告警历史

展示：

- 触发时间
- 恢复时间
- 持续时长
- 触发值
- 阈值
- 规则快照与规则版本切换记录
- 通知结果
- 处置记录（确认 / 忽略的完整历史）
- 是否落在维护窗口内

#### 告警详情

应关联：

- 触发指标图
- 规则快照
- 通知记录
- **当前处置摘要 + 完整确认 / 忽略历史**（含忽略原因码）
- **No Data 原因**（不可达 / Agent 离线 / 无权限 / 扩展未装 / 不适用 / 采集超时）
- 采集状态
- 性能事件
- **触发现场快照**（适用时）：须明确采集时间、完整性、截断状态或失败原因

### 4.8.1 配置缺失待办

**独立模块，置于采集管理页最顶部**——`03` §4.8 的页面目标是「回答数据是否可信、为什么某些指标或功能不可用」，本模块是该问题的**直接答案**，且是全页**唯一可执行**的模块（其余五个都在陈述事实）。

#### 条目粒度 = 能力，不是指标

条目形如 `缺少 pg_monitor 角色 —— 影响 6 项指标`：

- **一行对应一个可执行的动作单元**（装一个扩展、授一次权）；
- 可展开列出具体受影响指标，展开项**链接回「指标采集状态」模块的对应行**，不重复造数据；
- 每条带一句**文字修复指引**（如 `GRANT pg_monitor TO <监控账号>`），**不带一键修复按钮**——平台没有、也不该有目标库的 DDL / DCL 权限。

> 否决指标粒度：它会把同一个修复动作重复若干遍，用户看到 3 行却只需做 1 件事；而「影响几项指标」这个说服力最强的数字，恰恰只有聚合之后才存在。
>
> 「数据库连接与权限检查」「扩展 / 插件能力」两个模块**保留原样**，仍是完整能力清单（含正常项，用于诊断）。待办清单只收其中「缺失且可修复」的子集——一个是体检报告，一个是待办事项，轻微重复是有意的。

#### 三态展示契约：绝不报假绿

§1.4 立了硬规矩——空状态必须解释原因。待办清单是这条规矩最容易被违反的地方：**一个空清单看起来永远像好消息。**

| 情形 | 清单里的呈现 |
|---|---|
| **可修复缺失**（无权限 / 扩展未启用） | 待办条目（能力粒度），带影响指标计数与文字修复指引 |
| **结构性不适用**（无 slot / 角色拓扑不适用 / 版本不支持） | **不进清单**；仅在能力清单模块里显示为「不适用」并附原因（如「本实例为主库，无 replication slot」），措辞明确区别于「缺失」 |
| **查不到 / 检查失败** | **进清单，且排在最前**：`无法检查采集能力 —— 数据库不可达，以下 N 项状态未知`。**绝不静默按「具备」处理** |
| **确实全部就绪** | 显式正向空状态：`无待办 —— 所有可修复的采集能力均已就绪（最近检查 3 分钟前）` |

**三条约束：**

1. **模块永不隐藏。** 清单为空时不得把模块整块藏掉——否则用户分不清「没有缺失」和「这版没这功能」。
2. **正向空状态必须带最近检查时间。**「一切就绪」如果是三天前的结论，它就是假的。
3. **「查不到」不得降级为「就绪」。** 这是整个清单唯一的安全底线。

> **移交后续路线的硬约束**：采集侧必须能区分「结构性不适用」与「本该有却查不到（采集失败）」，否则真故障会被误判为不适用而静默。

#### 跨实例聚合

**MVP 不建跨实例的配置缺失聚合页**——它无处安放（顶层结构已收口为四个节点），硬塞会推翻 §3 刚定的页面树。改用两个几乎免费的替代：

- 实例列表增加 `配置缺失 N` **灰色正交标记**（与 `已忽略 N` 同一层、同一视觉语言），**不影响健康、不参与排序权重**；
- 全局筛选增加**「存在配置缺失」**一维，点进去是需要处理的实例子集。

按能力跨实例聚合的页面记入 §11 可延后清单。

### 4.8.2 暂停采集

#### 形态

**实例级布尔开关。** 不做定时暂停、批量操作、按指标粒度暂停。

#### 作用面：停到评估层

**暂停 = 停采集 + 停评估**，通知随之自然消失（没有评估就没有状态迁移，也就没有通知触发点）。

> 否决「只停采集、不停评估」：评估还在跑，无数据即按 `02` §3.4 连续 2 周期进 `NO_DATA`，而 `NO_DATA` 仍算一条未恢复告警、仍参与健康归并——实例照样非绿，功能等于没做。

#### 与维护窗口的界限（两句话）

- **维护窗口** = *我知道这段时间它会抖，别吵我，但数据我还要* → 继续采集、继续评估、只压通知。事后可回看那段时间发生了什么。
- **暂停采集** = *这台现在没有可信数据可采，整体退出监控视野* → 停采集、停评估。那段时间**没有数据**，事后也回看不了。

由此得到干净的域划分：**维护窗口属告警域（告警管理员写），暂停属采集域（平台管理员写）。**

#### 对健康与告警的影响

- 主状态直接是「已暂停」，**override 一切归并结果**（§7.1）。
- 存量未恢复告警**冻结**，解冻**不回放**且延续同一告警实例（`02` §4.4）。
- **暂停实例永不产生告警。**
- 数据状态显示为「已暂停」（§7.2）——暂停期间图表必须显式说「已暂停」，**不得**显示「采集失败」或「数据库不可达」，否则用户排查半天才发现是自己按的。

#### 入口与权限

- **采集管理页的采集配置模块 = 唯一管理面**，暂停 / 恢复按钮只在这里。
- 实例列表与实例总览为**只读标记**，可跳转，不在此处操作。
- 写权限归**平台管理员**（继承采集配置的权限判定）。

#### 护栏：防止暂停变成被遗忘的盲区

这是暂停唯一的真实风险，且比「忽略」危险得多——忽略只藏一条告警，**暂停让整台实例从监控里消失**。

- **留痕**：操作人 + 时间**必录**（系统自动），原因**选填**（自由文本）。
  > 与「忽略原因必填」的分歧是刻意的：**忽略是悄悄发生的**，别人看不出，所以必须逼出理由；**暂停是响亮的**——整台实例变灰、主状态改写、列表里一眼可见，本身就在追问「这谁干的」。
- **被动提醒，不做自动恢复**：
  - 实例列表的「已暂停」标记**带时长**，超过 **7 天**转警示色；
  - 导航角标显示已暂停实例计数（§3.2）。
- **硬约束：只提醒、不升级为告警。** 若暂停实例反过来产生告警，等于暂停不生效。
- **不做自动到期恢复**——它会在你没准备好的时候突然开始告警，比忘记恢复更危险。

### 4.9 告警设置（平台级）

#### 页面目标

管理跨实例的告警配套对象。区内四页：

| 页面 | 内容 |
|---|---|
| **通知渠道** | **邮件服务**（单例 SMTP 表单 + 测试发送）与 **Webhook 目标**（列表增删改 + 测试请求）**同页两区块**；承载各渠道失败摘要，渠道条目可展开最近 N 条失败记录（时间、目标、原因、重试次数） |
| **联系人** | 联系人列表 + 联系人组（一层，无嵌套） |
| **通知策略** | 策略列表与编辑（联系人组、渠道、严重级别过滤、`repeat_interval`、触发 / 恢复开关）；默认策略唯一、不可删除 |
| **维护窗口** | 生效中 / 未开始 / 已结束列表，创建（可多选实例）、编辑、提前结束、删除 |

> 邮件与 Webhook 形态不对称（单例配置 vs 多条目标）在**页内用两个区块**表达，不上升为两个页面——它是同一概念（出口）的两种形态，且拆页会把失败可见性劈成两半。

#### 维护窗口的两处入口，职责严格不对称

- **平台级「维护窗口」页 = 唯一管理面**（列表、创建、编辑、提前结束、删除）。
- **实例工作台只有两件事**：实例总览上的只读维护状态标记；一个「新建维护窗口」快捷入口，打开**同一张表单**、仅预填当前实例。
- **工作台不承载列表、编辑、删除。**

理由：创建高频且天然带实例上下文，管理低频且天然跨实例。只做平台页会逼运维在「我要重启这台」的时刻跳出工作台重新找回实例；只做工作台入口则「现在全平台有哪些维护窗口在生效」无处可答。

**数据只有一份，写入路径只有一条表单**——因此不可能长出第二套作用域与过期语义。

```text
→ 返回总览或进入事件 / 会话详情
```

成功标准：

- 用户能判断实例是否在线。
- 用户能判断数据是否新鲜。
- 用户能看到是否有未恢复告警。
- 用户知道下一步看标准监控、会话阻塞还是采集管理。

- 从告警跳转到标准监控时自动定位触发时间。
- 从标准监控跳转到会话与阻塞时继承时间范围。
- 会话详情**不展示 SQL 文本**，只提供 PID 等原生定位信息（§4.5）。

## 7. 统一状态模型

### 7.1 实例健康

**统一律：实例健康是「未恢复告警」的一个视图，不是第二套判定。** 健康不引入任何独立于告警的判定通道、阈值或权重。

#### 合并模型：可解释的最坏状态归并

实例健康 = 全部参与归并的未恢复告警中**最坏的那一个**，按全序取最大值。**不做数值加权评分。**

> 权重对用户不可解释、阈值无法辩护；告警本身已带三档严重级别，再叠一层权重等于把同一件事排两次序。列表页的核心动作是「筛出该看的实例」——最坏归并直接可筛，评分只能筛区间。「多种问题同时存在」由主状态 + 计数 + 正交标记表达，信息量高于一个混合分数。

#### 主状态：四档归并 + 已暂停 override

| 主状态 | 判定 |
|---|---|
| **严重** | 存在参与归并的 `critical` 未恢复告警 |
| **警告** | 存在参与归并的 `warning` 未恢复告警 |
| **未知** | 该实例**至今没有任何一次成功采集** |
| **正常** | 有过成功采集，且无参与归并的 critical / warning 未恢复告警 |
| **已暂停** | **override** —— 用户主动暂停采集，压过一切归并结果 |

判定顺序一句话：*已暂停 → 直接「已暂停」；否则有 critical/warning 未恢复告警 → 取最高级别；否则从未成功采集 → 未知；否则 → 正常。*

对外命名**直接复用严重级别的词**（`严重` / `警告`）。列表列头为「实例健康」，tooltip：*最高未恢复告警级别*。同词呈现使单一来源模型在 UI 上自证。

#### 单一来源

健康**只**由该实例的未恢复告警派生。实例连通性、Agent 状态、采集新鲜度**不作为独立健康输入**——它们经 `02` §6 的三条不可停用内置规则进入告警，再进入健康。

> 多路输入会双重计数同一事实，且两条路径的阈值与滞回不一致（内置规则走连续次数与滞回恢复，直连通道没有），会出现「健康已变红但告警还在 PENDING」这类用户无法解释的自相矛盾。单一来源天然满足「无需猜权重」：**点开状态就是那条告警**。

内置规则的严重级别可被用户修改，健康敏感度随之变化——这是特性而非缺陷：用户调级别即是在声明「这事对我多重要」，比平台硬编码权重更诚实。下限约束见下。

#### `info` 不改变主状态

- `critical` → 严重；`warning` → 警告；**`info` → 不改变主状态**。
- 未恢复的 `info` 告警以计数徽标呈现，可在全局筛选中按「存在 info 告警」单独筛出，仍在告警列表、仍按通知策略通知。

> info 规则天然常亮（如「连接数超 60%」这类观察项）。若染色，列表长期没有绿色，「正常」档在真实环境几乎不出现，健康随即丧失分辨力。

**附带约束**：`02` §6 的三条内置采集状态规则严重级别**不得低于 `warning`**。否则把「数据库不可达」改成 info → 数据库挂了列表仍全绿，而 `NO_DATA` 本身不通知——静默事故换了个入口。

#### 「未知」的边界

- 唯一入口 = **从未成功采集**（新接入、连接信息填错、监控账号未建）。
- 退出条件 = **首次成功采集**，此后**永不再回到未知**。之后的失联全部由三条内置规则的告警承担。
- **排在告警档位之下、正常之上。** 不做「数据不可信压顶」——那会擦掉已知问题。实例失联时，其下已 FIRING 的告警必须继续把实例染红，而非变灰。
- 因此「未知」是**一次性、单调的开局状态**：实例一生中最多经历一次，无需阈值与滞回。

#### 正交标记

主状态只回答「多该看」，正交标记回答「为什么」。标记**不改变主状态，可与任意主状态共存**：

| 标记 | 含义 |
|---|---|
| `无数据` | 该实例存在处于 `NO_DATA` 的未恢复告警 |
| `维护中` | 实例当前落在维护窗口内（仅压通知，不影响状态与可见性） |
| `近期恢复` | 最近 **24 小时**内有告警恢复；点击直达该实例告警历史 |
| `已忽略 N` | 存在 N 条已忽略的未恢复告警 |
| `配置缺失 N` | 存在 N 项可修复的采集能力缺失（§4.8.1） |

> **「已恢复」不是健康状态**：其余各档描述**此刻**，它描述**过去**。作为独立档位会立刻产生无解问题——恢复多久之后变回正常？任何时长都是拍脑袋，且它与「正常」争夺同一批实例。降为 24 小时标记后，时长猜错只影响一个提示的显隐。

#### 处置状态与压制对健康的影响

| 情形 | 是否影响健康 |
|---|---|
| **已确认** | **否**。确认 = 停止重复通知；问题还在烧，实例仍按级别染色 |
| **维护窗口** | **否**。不影响评估、状态与可见性；仅加 `维护中` 标记 |
| **`FIRING → NO_DATA`** | **是**，按进入前的严重级别继续参与归并（仍计一条未恢复告警），另加 `无数据` 标记。不因失联降级或变灰 |
| **已忽略** | **退出健康归并** |
| **已恢复** | **否**。只作 24h `近期恢复` 标记 |
| **已暂停** | **override**，主状态直接为「已暂停」；存量告警冻结 |

**「忽略」退出健康归并**——已忽略的告警不参与主状态计算、不计入 C/W/I 计数、不出现在归因行；但**仍在告警列表可见、仍继续评估、仍走重复通知**。

> 两种处置由此有了互不重叠的作用面：**确认 = 别再通知我；忽略 = 这不该算作实例的健康问题**。若忽略不产生任何可见后果，用户填了必填原因码却什么也没换来，该按钮很快无人使用；而「误报」若无法让实例从红变绿，列表将长期挂红，用户随即停止相信健康状态——单一来源模型一旦被不信任，整个设计价值归零。

**防滥用护栏**：必填原因码、自动记录操作人与时间、`AlertEvent` 永久留痕（`02` §4.3）；加上两条 UI 约束——卡片**始终显示 `已忽略 N` 灰色计数**（**绿色永不等于「什么都没有」**），且全局筛选可按「含已忽略告警」筛出。忽略可随时切回确认 / 未处置，代价可逆。

#### 「不适用」与「配置缺失」不进入健康

- **结构性不适用**（无 replication slot、角色 / 拓扑不适用、版本不支持）：对应规则**不评估、不产生告警实例**（既不 FIRING 也不 NO_DATA），对健康**零影响**，实例不因此变「未知」。仅在指标 / 模块层面表达——图表位显示「不适用」占位（§7.2），实例总览对应摘要模块整块灰显或隐藏。
  > 不适用是结构性事实（这台是主库，没有 slot 可看），不是故障，永远不会自行变好。若产生 `NO_DATA`，每台主库都将永久挂着一批「无数据」标记，标记随即失去信号价值。
- **可修复的配置缺失**（无权限 / 扩展未启用）：同样不产生告警、不影响健康，集中到采集管理页的待办清单（§4.8.1），并在实例列表以 `配置缺失 N` 标记呈现。

### 7.2 数据状态

| 状态 | 说明 |
|---|---|
| 加载中 | 请求未完成 |
| 暂无样本 | 指标可用，但当前尚无样本 |
| 当前时间范围无数据 | 换时间范围可能有数据 |
| 数据过期 | 最近样本超出新鲜度阈值 |
| **已暂停** | 用户主动暂停采集，期间无新样本。**不得**显示为「采集失败」或「数据库不可达」 |
| 采集失败 | 采集任务失败 |
| 数据库不可达 | 数据库连接失败 |
| Agent 离线 | Agent 指标不可用 |
| 无权限 | 监控账号权限不足。**去向：采集管理页的配置缺失待办清单**（§4.8.1） |
| 功能未启用 | 扩展、日志或采集功能未开启。**去向：同上** |
| 版本不支持 | 当前 PG 版本不支持。**不产生告警实例，不影响健康** |
| 不适用 | 当前角色或拓扑不适用。**不产生告警实例，不影响健康**；措辞须明确区别于「缺失」 |

### 7.3 告警状态

与告警模型保持一致，**五档**：

| 领域值 | UI 中文 |
|---|---|
| `OK` | 正常 |
| `PENDING` | 待持续 |
| `FIRING` | 告警中 |
| `NO_DATA` | 无数据 |
| `RECOVERED` | 已恢复 |

**没有第六档。** `SUPPRESSED` 不是状态——压制是告警实例上的**正交标记**（`02` §3.5、§4.1）：

| 标记 | UI 中文 | 来源 |
|---|---|---|
| `maintenance` | 维护中 | 维护窗口 |
| `acked` | 已确认 | 用户确认 |
| `paused` | 已暂停 | 实例采集暂停（冻结） |

标记显示在状态**旁边**，不是状态标签本身。

## 8. 角色与权限边界

**三档全局角色**，严格包含关系：

| 角色 | 边界 |
|---|---|
| **只读运维** | 所有观察面全可见，零写权限 |
| **告警管理员** | 只读 + 告警域全部写（规则、告警设置四页、确认 / 忽略） |
| **平台管理员** | 告警管理员 + 平台域写（采集配置、暂停采集、实例接入、Agent 绑定、用户与角色） |

**不做能力勾选式的自由组合**——组合式权限在 MVP 规模下是纯复杂度。

**不做实例级授权，角色是全局的。** 引入它会连带拽出实例分组 / 项目 / 归属对象，以及全局告警页按权限过滤、维护窗口可选实例范围等一串新决策。

> **显式让步**：§4.5 中「定位信息跟随实例监控查看权限」在不做实例级授权的前提下**退化为「跟随全局只读权限」**——任何登录用户可见全部实例的会话 PID 等定位信息。单租户运维团队内可接受，但不得隐去不说。

### 8.1 权限表达统一律：可见性不收窄，写能力收窄

**所有角色都能看见全部配置页内容**；无写权限时控件置灰并说明所需角色，**不隐藏入口**。

理由：

1. §1.4「空状态必须解释原因」是全文档立身原则，隐藏入口是它的反面——一个不解释自己为什么不在的功能，比一个明说「你不能改」的功能更让人困惑。
2. 只读运维排障时必须能回答「这条告警为什么没通知到我」——需要看到规则绑了哪条策略、策略绑了哪个组、组里有没有他、渠道最近是否失败。而渠道失败可见性恰恰在渠道配置页（§4.9），藏起来等于只留给管理员，最需要它的人反而看不到。
3. 私有化单租户下隐藏式权限无安全收益，只有支持成本。

**唯一例外 —— 凭据类字段**：SMTP 密码、Webhook 密钥 / 签名头**一律掩码，任何角色（含平台管理员）都不可读明文**；有写权限者可覆写、不可读取。凭据泄露不可逆，而「读回明文」在运维上没有必要——要换就重填。

### 8.2 写权限矩阵

| 对象 | 只读运维 | 告警管理员 | 平台管理员 |
|---|:--:|:--:|:--:|
| 全部观察面（实例 / 指标 / 会话 / 事件 / 告警 / 采集状态） | 看 | 看 | 看 |
| 告警规则增删改启停 | — | 写 | 写 |
| 通知渠道 / 联系人 / 通知策略 | — | 写 | 写 |
| 维护窗口（创建 / 编辑 / 提前结束） | — | 写 | 写 |
| 告警确认 / 忽略 | — | 写 | 写 |
| 采集配置 | — | — | 写 |
| **暂停 / 恢复采集** | — | — | 写 |
| 实例接入 / Agent 绑定 / 用户与角色 | — | — | 写 |

采集管理页除「采集配置」模块外的全部模块（配置缺失待办、采集总状态、Agent 状态、连接与权限检查、扩展能力、指标采集状态）**全员只读可见**——「为什么这个指标没数据」必须在平台上答得出来。

### 8.3 敏感能力

以下能力需要特殊权限或首版不开放：

| 能力 | R1 处置 |
|---|---|
| 查看完整 SQL 文本 | **不存在** —— 平台不承载 SQL 文本（§4.5） |
| 查看敏感客户端信息 | 跟随全局只读权限 |
| 修改采集配置 / 暂停采集 | 平台管理员 |
| 修改告警规则 | 告警管理员 |
| 绑定或替换 Agent | 平台管理员 |
| cancel query | **首版不开放** |
| terminate session | **首版不开放** |
| 批量终止会话 | **首版不开放** |

> 原草案的「数据库管理员」角色已删除：其两项专属能力——「查看更完整会话信息」被 §4.5 清空，「cancel / terminate」本节自己就写了首版不开放。**一个语义为空的角色只会被误选。** 等 cancel / terminate 真正进入路线时再作为新角色引入。

## 9. 与指标字典的依赖

信息架构依赖指标字典提供：

- 指标 ID
- 指标名称
- 指标定义
- 单位
- 聚合方式
- 采集频率
- 数据来源
- 是否需要 Agent
- 是否需要扩展
- 所需权限
- 适用角色
- 缺数语义
- 是否可告警
- **是否可生成事件** —— 语义收窄为「**该指标的告警是否派生事件**」，由固定的「哪些告警类型派生事件」清单驱动，而非指标独立可生成事件（§4.6）

典型影响：

- 标准监控图表来自指标字典。
- 实例总览摘要来自 P0 指标。
- 告警规则可选指标来自可告警指标。
- 指标不可用提示来自指标前置条件。
- 采集管理的受影响指标来自指标依赖关系。

## 10. 与告警模型的依赖

信息架构依赖告警模型提供：

- 告警规则
- 当前告警实例
- 告警历史事件
- 恢复记录
- 确认 / 忽略记录（含忽略原因码）
- 通知记录
- No Data 状态与原因
- **维护窗口标记与确认状态**（压制来源只有维护窗口、确认、已暂停三种）
- 规则版本快照
- 触发现场快照（适用时）

告警详情需要至少关联：

```text
实例 ID
指标 ID
告警规则 ID
告警实例 ID
触发时间范围
触发值
阈值
规则版本
通知记录
采集状态
处置状态
触发现场快照引用
```

告警详情中的会话 / 阻塞现场由 `02` §3.10 的触发现场快照提供——**只在首次进入 `FIRING` 时采集一次**，事后不可能重新采集。
