## 0. 一句话结论

**离线 tar 包 + 自建最小 PostgreSQL 17（socket-only、零 TCP 端口）+ 平台自分发的静态 Agent（不自升级）；amd64 与 arm64 双架构、每架构各自 glibc 下限；升级只备控制面、回滚靠备份不靠 down 迁移；时钟同步与磁盘容量是安装期硬检查。**

贯穿全票的取向与 [T5](05-backend-code-structure.md) / [T6](07-api-contract-and-codegen.md) / [T7](08-frontend-stack-and-ui.md) 一致，是同一个动作在交付面的执行：**把规范做成结构，而不是做成约定。** 落到本票是四处——

- 自带 PG 不开 TCP 端口 ⇒ **端口冲突与外部连入结构性不可能**（D5）；
- socket 上 peer 认证 ⇒ **配置里根本不存在 PG 密码**（D5）；
- Agent 无下行通道 ⇒ **自升级机制写不出来**（D7）；
- 时钟偏移在安装期拒绝 ⇒ **「装好了就是没数据」这类模糊运行期故障，前移成安装期的明确失败**（D11）。

## 1. D1 · 交付物形态：离线 tar 包，不走容器

**结论：离线安装包**——Go 静态二进制（前端已 `go:embed`）+ 自建的 PostgreSQL 可重定位目录 + 安装脚本 + systemd unit。装完是宿主机上两个 systemd 服务。**否决容器镜像包。**

**理由**

1. **容器路线直接违反地图 Notes 第 2 条。**「客户装了 Docker/Podman」在私有化、信创环境里恰恰是最不能假设的一条：安全规范禁止容器运行时、或只有一台无外网裸机，都是常态。把「不依赖客户环境」这条最硬的约束，押在一个客户可能根本不允许安装的运行时上，等于把它换成了最软的假设。
2. **自建 PG 二进制的痛点是构建期的，不是交付期的**（见 D2/D3）：它发生在我们自己的机器上，一次性解决；容器的依赖发生在客户机器上，每次交付都要重新谈。
3. **可见性即可运维性。** tar 包让「自带 PG」在文件系统里是可见的（一个 `pgsql/` 目录、一个数据目录、一个 unit）；容器会把它藏进镜像层，排障时交付团队要先 `docker exec`。地图定的是交付团队运维，这份成本仍在我们身上。

**第三条路线（二进制内嵌纯 Go 存储）已被 [T2](04-metric-storage-model.md) 消灭**——选定自带 PostgreSQL 后，进程外的 PG 是硬需求。

**推翻条件**：目标客户群被证实为「普遍已有容器平台且禁止裸机装服务」，则本条翻转。届时代价是重做安装/升级脚本，不是重做架构。

## 2. D2 · 自带 PostgreSQL 自建，且 `configure` 面写死

**结论：从源码自建**，产出可重定位的 `pgsql/` 目录随包分发。否决取用 EDB 的免安装二进制，否决剥离发行版 rpm/deb 重打。

**理由**

1. **剥离发行版包**等于把某个发行版的依赖假设整包带进来，同时失去包管理器这唯一的好处（我们本就不用它），且 rpm 路径是绝对的，可重定位性仍要自己补。
2. **EDB 二进制 vs 自建的真正差别不是省事，而是依赖面的可控性。** 第三方 tar 为通用性会带上 ICU、Perl、Tcl、OpenSSL 等一堆共享库；我们需要的自带 PG 只干一件事——在本机 socket 上给平台自己用。自建能把依赖面收到最小，直接减少「客户机器上少一个 `.so`」这类交付事故。
3. **升级路径可控**：升 PG 小版本对我们只是重跑一次构建，不必等第三方发布（见 D9）。

**`configure` 面（属交付契约，不是实现细节）**

| 选项 | 为什么 |
|---|---|
| `--without-icu` | ICU 在 PG16+ 是默认排序提供者；**ICU 版本变化会让索引排序失效**，对整包升级是雷。统一用 libc provider + `C` locale——平台库里全是英文标识符与时间戳，不需要本地化排序 |
| `--without-openssl` | 自带 PG 只在 unix socket 上，不对外（D5）。[T3](https://github.com/liumingjian/dbs-monitor/issues/21) 的强制 TLS 管的是 Agent → 服务端那条链路 |
| `--without-readline` / `--without-perl` / `--without-python` / `--without-tcl` | 用 `psql` 的交互体验换零依赖 |
| 保留 zlib（静态链） | `pg_dump` 压缩要用，而备份是升级回滚的前提（D9） |

**显式接受的代价：我们成为自己那份 PostgreSQL 的发行方。** CVE 要自己跟、自己重编、自己出补丁包，走整包升级流水线（D9）。这条进交付团队的常态职责，不是一次性成本。

> **收口增补 2026-08-05：职责去向登记。** 自研 PG 的 CVE 跟踪、补丁判断与重编排期由 **R3 发布闭环的交付团队**负责，落地载体是发布手册和发布 workflow 的构建元数据；R2 不指定个人或值班岗位。

## 3. D3 · 双架构：`amd64` + `arm64`，每架构各自一条 glibc 下限

**结论：平台端与 Agent 端均支持 `linux/amd64` 与 `linux/arm64`。信创环境 arm64 服务器占比更高，平台端 arm64 是硬需求，不是可选项。**

**glibc 下限按架构分别定，不取统一值**

| 架构 | 构建容器 glibc | 覆盖 |
|---|---|---|
| `linux/amd64` | **2.17**（CentOS 7） | 老 CentOS 7 至最新发行版 |
| `linux/arm64` | **2.28**（openEuler 20.03 / RHEL8 系 arm64） | 麒麟 V10、统信 UOS、openEuler 全线 |

**理由**：两个世界的 glibc 起点天然不同。arm64 强行要求 2.17，只能去养一个已 EOL、且没有任何真实客户运行其上的 CentOS 7 arm64 构建环境——付出真实痛苦换零覆盖；amd64 抬到 2.28 则直接丢掉仍然真实存在的 CentOS 7 机器。两个下限各自贴着各自世界的实际起点，是唯一不浪费的口径。

**原生构建，不用 qemu 交叉模拟**：PG 自建要跑 `make check`，qemu 下慢到不可接受，且模拟层的差异会把「构建期通过、真机上炸」的问题推迟到现场暴露。Go 侧交叉编译天然可行（`CGO_ENABLED=0`），痛点只在 PG。

**不做发行版清单，只承诺 glibc 下限 + 架构。** 清单一旦写出，「不在清单上」就会被读成「不支持」，而我们的依赖面极窄（静态 Go + 最小 PG），发行版差异几乎不可见。要写进交付文档的是**依赖面**，不是发行版名字。

### 3.1 对 [T11](https://github.com/liumingjian/dbs-monitor/issues/29) 的实测门槛分级（避免矩阵翻倍）

| 架构 | 实测范围 |
|---|---|
| `amd64` | **T11 全量**：RT-C §7 门槛 T1/T2/T3；**R3 发布门槛**再加 PG13–17 集成矩阵 |
| `arm64` | **冒烟 + 一次容量抽样**：端到端切片全绿 + `pg_total_relation_size` 复核 |

理由：性能门槛判定的是**存储模型选型**（窄表 + 原生分区）是否成立，这是架构无关的结构性结论；arm64 需要验证的是「能跑、数字不离谱」。**arm64 抽样与 amd64 偏离超过一个量级，才升级为全量复跑。**

### 3.2 T11 与 R3 的交付边界

T11 的 walking-skeleton 验收只判断选型与首启地基是否成立：原生 amd64 的 RT-C 全量门槛、真实构建、离线 tar、安装和首启行为。升级/回滚脚本及 PG13–17 被监控库集成矩阵不阻塞 T11 resolve，统一延期为 R3 的发布门槛。

R3 必须补齐并实测：`upgrade.sh`、控制面备份与恢复回滚流程，以及 PG13/14/15/16/17 五个真实库上每个采集 Task 的列名、类型和行数形状矩阵。R3 交付前不得把 T11 的 walking-skeleton 包宣称为完整生产升级包。

## 4. D4 · 自带 PG 钉死 17，全产品只此一个版本

**结论：PostgreSQL 17。不给客户选版本，不支持接管客户既有的 PG 实例。**

先厘清一处易混：**自带 PG 的版本与被监控 PG 的版本无关**。[T4](06-metric-dictionary-and-collection-plan.md) 已把**被监控**端定为 PG13–17、PG12 接入即拒；本条定的是**平台自己**那一台。

**理由**

1. **「只有一个版本」比「选哪个版本」更重要。** 一旦允许接管客户既有 PG，[T2](04-metric-storage-model.md) 的全部结论立即失效——分区预建、`date_bin` 粒度、`DROP` 滚动删除、goose 启动自动迁移，全都建立在「这个库归平台独占」之上。共用客户的库意味着要处理别人的扩展、别人的备份策略、别人的 DBA 在半夜 `ALTER`。整包交付的全部价值就是把这些变量消掉。
2. **17 而非 18**：18 尚不足一年，而我们要的是数年不动的地基；T2 用到的能力（`date_bin` ≥14、原生分区、`generate_series` 造数）17 全有，18 不带来任何我们需要的东西。信创发行版的配套生态也更常见 17 一代。
3. **17 而非更保守的 15/16**：既然是自建二进制、不依赖发行版仓库，「保守」换不来兼容性收益，只换来更早的 EOL（PG 17 社区支持至 2029 年）。

**两条边界**

- **小版本（17.x）跟随整包发版**，不给客户单独打 PG 补丁的通道。
- **大版本升级（17→18+）是一次显式的迁移工程，不隐含在整包升级里。** `pg_upgrade` 或 dump/restore 需要独立流程与停机窗口，绝不能被启动时的自动迁移悄悄触发。这同时是对 T5「启动自动跑 goose 迁移」的边界声明：**goose 管 schema，不管 PG 大版本。**

## 5. D5 · 运行形态：socket-only，零 TCP 端口，peer 认证

**结论**

| 项 | 结论 |
|---|---|
| 安装根 | `/opt/dbs-monitor/`：`bin/`、`pgsql/`、`data/`（PG 数据目录，**安装时可指定到独立盘**）、`run/`（socket）、`certs/`（T3 自签 CA 与服务端证书） |
| 运行身份 | 专用系统用户 `dbsmon`，**不复用 `postgres`**——平台机上可能已有别人的 PG，抢用户是自找麻烦 |
| 监听 | 自带 PG **只监听 unix domain socket（`/opt/dbs-monitor/run/`），完全不开 TCP 端口** |
| 认证 | socket 上 `peer`，`pg_hba.conf` 除该条外全 `reject`；平台进程与 PG 以同一个 `dbsmon` 用户运行 |

**这一条一次性消掉了票里的两个问题，且不是靠「配置写对」**

1. **端口冲突结构性消失**：整个交付物只占用一个端口（平台 HTTPS）。同机上有别人的 PG 跑在 5432 完全无关。
2. **自带 PG 被外部连上结构性不可能**：不是靠 `listen_addresses = 'localhost'` 写对，而是它根本不在网络上。
3. **平台配置里不存在 PG 密码**——少一个秘密，就少一个 [T13](https://github.com/liumingjian/dbs-monitor/issues/31) 要回答的问题。

**显式接受的代价（移交 T13）**：平台与 PG 同用户，意味着**平台进程被攻破 ≈ 拿到 PG 数据目录的读权限**，即拿到全部密文。但这一点在「密钥与密文同机」的前提下无论如何都成立（T13 的威胁模型将正面处理「拿到整台服务器的人防不住」），改成两个用户只是安全剧场，还要多配 `pg_ident` 映射。**本票不假装解决它，明确移交。**

## 6. D6 · 自举：接受不完美，但不许说谎

**问题**：[T5](05-backend-code-structure.md) 已定「运行期配置全在库里，DB 挂了平台完全不可运行」。单套私有化部署下，「谁监控监控系统」没有完美解。本条定的是**接受何种不完美，以及不完美的表现形式**。

**结论（四条）**

1. **DB 不可达时 HTTP 层照常起来，返回明确的「平台自身故障」页**，而不是白屏、502 或「暂无数据」。理由直接来自 R1：空状态必须解释原因（IA §1.4）。这条不变式对平台自身同样成立——**把「平台挂了」渲染成「没有数据」是本系统最严重的一类谎言，与假 `NO_DATA` 是同一个错误。**
2. **本地通知快照文件**：平台在启动时、以及每次通知渠道配置变更时，把最小通知配置（渠道地址 + 凭据密文）写一份到 `/opt/dbs-monitor/` 下。DB 连续不可达超过阈值时，用它发出「平台自身不可用」告警，恢复后发恢复通知。
   > **与 T5「UI 能改的不进配置文件」的关系**：这份文件**不是配置源，是库的只读派生缓存**。平台永远不从它读取运行期行为，只在「库已不可读」这一条路径上用于发通知。真相源仍然唯一。**此例外不得被引用为「配置可以外置」的先例。**
3. **两个 systemd unit 各自 `Restart=always`，平台不 `Requires` PG**，只在启动时重试等待。`Requires` 会让 PG 启动失败连带把平台拖下线，而我们恰恰需要平台在 PG 挂时活着去报告这件事。
4. **不做平台自身的高可用/主备，不做第二套监控栈监控本套。** 成本与「50 实例单套平台」的规模基线完全不成比例，且会毁掉整包交付的简单性。

**残余风险（不掩盖）**：**整台平台机宕机时上述机制一起失效，无人告警。** 唯一真解是外部另有东西在探测这台机器，那超出本路线终点——已记入地图 **Out of scope**（平台自身的外部存活探测 → 由客户既有基础设施监控或未来另起路线承担），并写入交付文档，交付时须明确告知客户。

## 7. D7 · Agent 由平台自身分发，非 root 运行，绝不自升级

**结论**

1. **平台自分发**：实例接入页展示一条安装命令，脚本从平台 HTTPS 拉取对应架构的二进制 + 自签 CA，写 systemd unit，令牌落 `/etc/dbs-monitor-agent/token`（`0600`，属专用非特权用户）。
   > 关键论据：**这条网络路径必然是通的**——Agent 存在的前提就是它能 push 到平台（T3：单端点、强制 TLS）。若库主机连不到平台，装上 Agent 也没有意义。因此「从平台下载」不引入任何新的连通性假设，这是它优于「交付团队手工拷贝」之处。整包 tar 内本就带两个架构的 Agent 二进制，手工拷贝 + 手工写 unit 始终可用，作为文档中的 plan B，不作主线。
2. **安装需 root（写 systemd unit），运行不需要 root。** RT-D 已确认 P0 主机指标读全局 `/proc` 不需要 root。**这个区分必须写进交付文档**——「监控 Agent 要 root」是客户安全评审最常卡住的一条。
3. **Agent 绝不自升级。** 这不是偏好，是 T3 的结构性后果：**T3 已定死无下行通道**，任何自升级机制都需要平台把「该升级了」推给 Agent，那就是下行通道，会撕开 T3「令牌只写边界不开口」的结论。**升级 = 重跑一次安装命令**（可脚本化批量重跑）；T3 的「服务端先升、Agent 后升、向后兼容一个大版本、过老拒收但不静默」把滞后窗口兜到一个大版本这么宽，人工重跑完全来得及。

### 7.1 版本口径：编译期同源，运行期容一个大版本差

[T5](05-backend-code-structure.md) 定「Agent 与服务端强制同版本」（共享 `internal/api` 生成物），[T3](https://github.com/liumingjian/dbs-monitor/issues/21) 定「向后兼容一个大版本」。二者表面冲突，实为两个时刻：

- **编译期同源**：Agent 与服务端从同一次构建产出，不存在混搭编译；
- **运行期容差**：已部署的旧 Agent 在服务端升级后仍被接收一个大版本，过老拒收但不静默。

## 8. D8 · 首次启动：三项人工输入，其余全自动

**自动（一条安装命令内完成）**：`initdb` → 生成自签 CA 与服务端证书 → 写两个 systemd unit → 启动 → goose 迁移自动执行（T5）→ 平台 HTTPS 可访问。

**必须是人的三项**

| 输入 | 为什么不能自动 |
|---|---|
| 数据目录路径（默认 `/opt/dbs-monitor/data`） | 只在需要单独挂盘时改，有默认值 |
| **平台对外访问地址**（IP 或域名） | **无法自动推断**：自签证书的 SAN 必须包含 Agent 将要连的那个地址，而机器上有几张网卡、客户从哪个地址访问，只有运维知道。猜错的表现是 Agent 全部 TLS 校验失败，而 T3 定死了无跳过开关——**这里猜错就是死路**。宁可安装时问，也不要在 50 台 Agent 装完后才发现 |
| 初始管理员口令：**随机生成并打印一次** | 否决内置默认口令（`admin/admin` 那类在任何客户安全评审里都判不合格，且几乎必然有客户不改）；否决首次访问设置向导（留下**任何人抢先访问即得管理员**的窗口，在客户内网中不是理论风险） |

**到第一张图**：接入一个实例（连接串 + 凭据，只有客户有，不可自动化）→ 一个采样周期内出图。

### 8.1 Agent 的信任引导：安装命令内嵌 CA 指纹

Agent 首次连平台时机器上还没有 CA，而拉取脚本本身就走 HTTPS。**结论：平台页面展示的安装命令内嵌 CA 指纹（`--ca-fingerprint sha256:…`），脚本拉到 CA 后先校验指纹再信任。**

- **全程不需要任何 `-k` / `--insecure`**，与 T3「强制 TLS、无跳过开关」严丝合缝；
- 信任根落在「运维从平台 UI 复制的那条命令」上，是一次干净的**带外传递**，而不是「第一次连上的就信」。

## 9. D9 · 升级：只备控制面，回滚靠备份不靠 down 迁移

**流程**：停平台（**PG 保持运行**）→ 备份 → 替换文件 → 启动 → goose 自动迁移。
**PG 小版本升级** = 替换 `pgsql/` 目录后重启（同大版本 ABI 兼容，无需 `pg_upgrade`）。大版本升级见 D4，是独立工程。
**迁移失败即拒绝启动**：非零退出 + 明确日志，**绝不带着半个 schema 对外提供服务**——与 T5「关停宁可拒 push 也不接半个事务」是同一条纪律的两端。

### 9.1 备份只备控制面，不备 `metric_sample`

**结论：升级前的自动备份只覆盖控制面（实例、凭据密文、告警规则与状态、用户等），排除时序样本表。**

**理由**

1. **量级差**：T2/RT-C 推算时序 30 天含索引 12–45 GB，控制面是 MB 级。
2. **后果差是决定性的**：45 GB 的 `pg_dump` 会让「每次升级自动备份」在现实中被跳过（太慢、盘不够），最终退化成文档里一句没人执行的话；**MB 级备份能做到每次升级无条件自动执行，秒级完成**。
3. **代价明说**：**回滚会丢失升级窗口内的时序数据，且是有意为之。** 可接受的理由是——时序样本不是账本，保留期本就只有 30 天，丢几分钟监控点可恢复；而丢失控制面（凭据、规则、告警状态）是不可恢复的灾难。**用一个可容忍的损失，换一个真的会被执行的备份。**

### 9.2 回滚：装回旧二进制 + 恢复控制面备份

**`migrations/` 只写 up，不写 down。**

down 迁移属于「写了但从来没测过、却在真正需要它的那个凌晨第一次运行」的代码——那是最糟糕的首次执行时机。回滚流程写死为**装回旧二进制 + 恢复控制面备份**。

> 这条同时给 [T9](https://github.com/liumingjian/dbs-monitor/issues/27) 提供一条可机械检查的规则：`migrations/` 下出现 down 语句即判红。

## 10. D10 · 资源基线与安装前置检查

**前提（不掩盖）：以下数字全部是推算，无一手实测。** RT-C 自己已标注这一点，[T11](https://github.com/liumingjian/dbs-monitor/issues/29) 的四条实测项正是为产生真数字。**本条定的不是数字，而是数字怎么表达、安装脚本拿它做什么、真值何时回写。**

| 项 | 交付规格（**推算，待 T11 实测确认**） | 安装脚本行为 |
|---|---|---|
| 磁盘 | **≥ 200 GB 独立数据盘** | **不足即硬拒绝**（留 `--force` 逃生舱 + 明确警告） |
| 内存 | **≥ 8 GB（推荐 16）** | 不足只警告 |
| CPU | **≥ 4 核** | 不足只警告 |

**为什么是 200 GB**：时序 30 天推算 12–45 GB，取上界 45，其余留给 WAL、临时文件、备份、日志与增长余量。这个数让 **RT-C 的门槛 T2 自洽**——那条门槛判定「30 天全量是否 > 交付规格磁盘的 30%」，45/200 = 22.5%，落在门槛内。若定 100 GB，等于在交付规格上主动把自己顶到门槛线，实测一跑就自己击穿自己。

**为什么两类项处置不同**：磁盘不足对 PG 是**致命且不可优雅降级**的失败，且会在交付后几周才发作，那时现场已无人；CPU/内存不足的表现是慢，不是崩，而 POC/演示环境常常就是一台小虚机，硬拒绝会挡住自己的售前。

**真值回写路径**：T11 实测完成后，用实测值替换交付文档中的推算值。**本票的数字带「推算」标签，不假装是结论**，避免被后续会话当作既定事实引用。

> **真值回写（2026-08-05，兑现本节预写的回写路径）**：T11 原生 Linux amd64 门槛实测（`docs/validation/t11-linux-amd64-progress.md`）：30 天全量 30 个分区共 **49,112,432,640 bytes（≈49.1 GB）= 200 GB 交付磁盘的 24.556%**——替换上文「取上界 45」的推算；RT-C 门槛 T2（30 天全量 > 交付磁盘 30% 则推翻）**PASS**，200 GB 交付规格与「不足即硬拒绝」行为不变。内存 / CPU 基线仍为推算，无实测。

**明确移交，不在本票解决**：**运行期的磁盘水位保护**（盘将满时是告警、自动缩短保留期、还是拒绝写入）归地图迷雾中的「平台自身的可观测性」，且与 [T12](https://github.com/liumingjian/dbs-monitor/issues/30) 的背压语义相邻；在此草率定一条很可能与那边冲突。

## 11. D11 · 时钟同步是一等交付前置检查项

**结论**：Agent 安装脚本在安装时自检本机与平台的时钟偏移（安装时它正要连平台，顺手取一次响应时间戳比对），**偏移超 ±5s 即拒绝安装**并打印修复指引；交付文档把「被监控主机与平台机时钟同步」与磁盘/内存/CPU 并列为前置条件。

**理由**

1. [T3](https://github.com/liumingjian/dbs-monitor/issues/21) 定死 **Agent 时间戳偏移 > ±30s 即拒收并报 `error`**（防止未来时间戳骗过 `NO_DATA`）。这意味着客户主机没跑 NTP，Agent 就采不上数据，**表现却是「Agent 装好了、服务起来了、就是没数据」**——最难排查的一类故障。
2. **把运行期的、症状模糊的失败，前移成安装期的、症状明确的失败**——与 T6 把接口漂移前移成编译错误、RT-D 选 sqlc 把 SQL 错误前移到生成期，是同一条原则。多写十行检查，省掉一次现场排查。
3. **安装门槛（±5s）严于运行门槛（±30s）**：装的那一刻恰好卡在 29s 是没有意义的通过，它离失败只差一次时钟漂移。安装门槛严一档，留出漂移余量。
