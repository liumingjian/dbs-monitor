## 0. 为什么需要这份文档

三份规格文档在 R1 合稿时就地升为 v1.0，只保留**结论**。但 R1 的十项决策中，有若干**被否决的方案**是「看起来很自然、后续路线极可能无意中重新引入」的那一类：

- 健康状态的**加权评分**（ADR-08 否决）；
- `Silence`（静默）对象（ADR-07 删除）；
- `SuppressionPolicy`（根因抑制）对象（ADR-07 删除）；
- **实例级授权**（ADR-09 划出）；
- 告警的 `SUPPRESSED` **状态**（ADR-07 降为正交标记）。

这些东西从规格里删干净之后，**缺席本身不解释自己**。本文档是它们唯一的墓志铭。

## 1. 研究输入（决策所依据的事实）

两项研究先于决策完成，其结论是硬事实，不是选择。

### RI-A · PostgreSQL 指标可得性与版本矩阵

出处：[RT-A · PG 指标可得性与版本矩阵](https://github.com/liumingjian/dbs-monitor/issues/2)，findings 在分支 `research/rt-a`（`docs/research/pg-metric-availability/findings.md`）。

| 事实 | 内容 |
|---|---|
| 复制延迟口径 | WAL 字节数（`pg_wal_lsn_diff`）跨 PG12–17 稳定、恒非 NULL、主备两侧可算；`*_lag` 字段实为同步提交延迟，空闲即 NULL；`now() - pg_last_xact_replay_timestamp()` 在主库空闲时虚高 |
| Slot 健康字段 | `wal_status` / `safe_wal_size` 自 **PG13** 起可用 |
| 无 slot 的返回 | `pg_replication_slots` 无槽时返回**空集**，不是 0 行 |
| 容器分母 | cgroup 场景下 CPU/内存百分比的分母必须用 limit，不能用宿主机总量 |
| `pg_monitor` 覆盖面 | 覆盖统计视图读取；**不含**装扩展、统计 reset、业务表数据读取 |
| 版本差异 | PG12→13 备库列改名（`received_lsn` → `flushed_lsn`） |

### RI-B · 慢查询数据源

出处：[RT-B · pg_stat_statements 与慢查询数据源](https://github.com/liumingjian/dbs-monitor/issues/3)，findings 在分支 `research/rt-b`（`docs/research/slow-query-sources/findings.md`）。

| 事实 | 内容 |
|---|---|
| 唯一稳定基线 | 受限权限 / 不可重启数据库的前提下，`pg_stat_activity` 采样是唯一始终可用的慢查询数据源 |
| `pg_stat_statements` | 需 `shared_preload_libraries` + 重启 + `CREATE EXTENSION`，平台不能自行启用；只能作为**机会性**增强 |
| 日志 / `auto_explain` | 需改配置或重启，且日志采集链路成本高，延后 |

### ADR-01 · 性能事件的定位与平台级边界

**原始问题**（`03` §12 原 I1 / I2 / I3 / I8）：

1. 平台首页是否直接采用实例列表，还是需要独立 Dashboard。
2. 全局性能事件是否进入首版，还是只做实例级性能事件。
3. 全局告警是否首版必须，还是先从实例级告警开始。
8. 性能事件和告警是否共享确认 / 忽略语义。

**结论**

- **性能事件 = 轻量 · 仅实例级 · 告警派生。** 选定类型的告警（锁等待/阻塞链、长事务、复制延迟、临时文件突增等）进入 `FIRING` 时顺带派生一条实例级事件。事件在告警之上只叠加三样东西：原因摘要 + 建议动作（按事件类型的知识模板）、证据链聚合、事件类型分类。
- **零第二套评估引擎**：不做独立事件规则，不做事件规则编辑 UI。
- **全局告警进 v1（精简版）**：跨实例「当前告警」+「告警历史」两个列表，复用实例级告警详情页。
- **全局性能事件不进 v1**；**平台首页 = 实例列表**。
- **确认/忽略 = 共享 · 单一状态 · 归属告警。** 事件继承并展示它；事件页即便提供确认动作，也是写回那条告警。

**理由**

事件与告警若各有一套评估规则，用户就要维护两套阈值、面对两套状态机，而它们描述的是同一件事。让事件成为告警的派生物，"平台识别出了什么"这一产品价值得以保留，第二套引擎的成本被完全消除。确认状态只有一份，是这一选择的直接推论——两份状态必然分叉。

**否决了什么**

| 被否决 | 为什么 |
|---|---|
| 性能事件作为一等公民（独立规则 + 独立页面 + 与告警并列） | 需要第二套评估引擎与第二套状态机，MVP 成本不成比例 |
| 「有性能事件但没有配置告警」的场景 | 它正是独立事件规则的唯一理由，随之推后至 post-MVP |
| 独立 Dashboard 作为首页 | 实例列表本身就是运维的首屏工作对象；聚合大盘在实例数量少时是空壳 |
| 全局性能事件 | 事件仅实例级的直接推论 |
| 事件与告警各自独立的确认状态 | 同一异常会出现「事件已确认但告警未确认」，用户无法解释 |

**出处**：[T1 · 核心概念与平台边界](https://github.com/liumingjian/dbs-monitor/issues/4)

### ADR-02 · 指标口径

**原始问题**（`01` §10 原 M1 / M2 / M3 / M4 / M5 / M7 / M8）：

1. 监控账号默认权限是否要求 `pg_monitor`。
2. 主动探针是否复用连接，还是每次新建连接。
3. CPU / 内存口径是否以宿主机、容器 cgroup 还是数据库进程为准。
4. 连接数是否默认排除监控账号连接。
5. TPS 是否按实例汇总还是按 database 维度保留。
7. 复制延迟优先采用时间延迟还是 WAL bytes 延迟。
8. 无 replication slot 时，slot 指标展示为 0 还是不适用。

**结论**

| 项 | 结论 |
|---|---|
| **M1 监控账号权限** | 硬性基线 = `pg_monitor` + `LOGIN` + 每个被监控库 `CONNECT`。权限不足的指标以显式「无权限」状态降级，不显示为 0 |
| **M2 主动探针** | 每周期**全新**「建连 + 认证 + `SELECT 1`」；`reachable = true` 语义 = 「新客户端此刻能连上」 |
| **M3 CPU/内存** | 口径 = 相对实例**实际可用资源**的百分比。MVP 假定 PG 独占宿主机/VM，分母 = 宿主机/VM 总量；内存用 working-set（扣除可回收 page cache） |
| **M4 连接数** | 分层：`pg.connection.total` **计入**监控账号（与 `max_connections` 对账）；`active` / `idle_in_transaction` / 长事务 / 锁等待 / 阻塞会话默认**排除**监控账号自身后端，靠固定 `application_name` 识别 |
| **M5 TPS 维度** | 实例级汇总为唯一规范口径与告警口径；per-database 下钻延后 |
| **M7 复制延迟** | 规范口径与**告警口径 = WAL 字节数**（`pg_wal_lsn_diff`，取 replay 位点）；时间延迟仅作辅助展示，空闲/NULL 时不告警 |
| **M8 无 slot** | 无复制槽 ⇒ **不适用**（不评估、不告警）；槽存在且已追平 ⇒ **真实 0** |

**理由**

- M1：无 `pg_read_all_stats` 时，普通角色在 `pg_stat_activity` 中只能看到自身会话——阻塞分析、连接分解、复制视图全部**静默失效**。静默失效比明确报错危险得多。
- M2：复用连接会在 `max_connections` 耗尽或认证回归时仍报健康，掩盖真实不可用。可用性探针的全部价值就在于它模拟真实客户端。
- M3：「可用资源百分比」才回答「实例是否受限」；working-set 避免冷缓存被误读为内存压力。
- M4：`total` 需与真实容量对账，所以必须计入自己；异常信号不得被采集自身污染或自触发告警，所以必须排除自己。同一个词在两处含义不同，是刻意的。
- M5：控制序列基数与 UI 复杂度；目标场景不是普遍的「一实例多活跃库」。
- M7：见 RI-A——时间 lag 字段在空闲时为 NULL 或虚高，用它做告警口径必然误报。
- M8：`pg_replication_slots` 无槽时返回空集，「0」是编造出来的数字。`01` §1.3 明令区分真实 0 与不适用。

**否决了什么**

| 被否决 | 为什么 |
|---|---|
| 「仅数据库进程」的 CPU/内存口径 | 回答不了「实例是否受限」，且 PG 多进程模型下归并口径本身有歧义 |
| 容器 / cgroup 感知口径 | MVP 假定独占部署；见 §3「划出 R1」 |
| 单独实现「权限降级档位」 | 一个功能残缺的降级模式需要平台全域适配，成本远高于要求装机时授权 |
| 无 slot 时显示 0 | 与「槽已追平」的真实 0 不可区分，直接违反 `01` §1.3 |
| 时间延迟作为复制告警口径 | 空闲即 NULL、主库空闲时虚高（RI-A） |

**出处**：[T2 · 指标口径决策](https://github.com/liumingjian/dbs-monitor/issues/6)

### ADR-03 · 告警评估与恢复语义

**原始问题**（`02` §9 原 A1 / A2 / A6 / A8 / A9）：

1. MVP 是否同时支持 `consecutive_count` 和 `for_duration`，还是先只支持连续次数。
2. 恢复阈值是否首版必填，还是可选。
6. 告警规则修改后，未恢复的告警实例是否继续按旧规则评估，还是按新规则重算。
8. 告警严重级别是否固定为 critical / warning / info，还是支持自定义。
9. 告警模板是否允许用户修改默认阈值并保存为自定义模板。

**结论**

- **A1 持续判定**：只支持 `consecutive_count`，不支持 `for_duration`。UI 同时展示连续次数、评估周期及约合时长。
- **A2 恢复条件**：每条规则必须有明确恢复条件。有序数值告警**必须显式配置独立恢复阈值**，形成滞回区间；布尔/枚举状态告警用明确反状态恢复。恢复同样采用连续次数，默认继承触发次数。
- **A6 规则修改**：保存产生新规则版本。未恢复实例保持同一生命周期、实例 ID 和首次触发时间；从**下一次**评估起采用新版本，并重置未完成的连续计数；**不回放历史数据**。
- **A8 严重级别**：固定 `critical / warning / info` 三档，顺序固定。UI 可本地化为「严重 / 警告 / 提示」，领域值不变。
- **A9 模板**：内置模板只读，可随平台版本升级。基于模板创建规则时复制默认值形成**独立规则**，创建后不跟随模板更新，记录来源模板与模板版本。

**理由**

- A1：`window` 负责样本聚合、`consecutive_count` 负责持续判定，职责已经清晰。两套持续语义并存必须回答「同时配了怎么办」，而它对首版毫无收益。
- A2：单一阈值附近的波动会造成反复触发和恢复——这是告警系统最常见的失败模式，且用户往往察觉不到是配置问题。强制滞回把这个坑堵死在配置阶段。
- A6：新配置的用途通常正是纠正一条错误或无法恢复的旧规则；但立即重算会让一次「保存」直接制造状态变化与通知，用户不会预期一个配置动作产生这种后果。
- A8：稳定的等级语义是全局统计、排序、筛选、健康状态和通知策略的共同基础。组织术语差异用展示映射解决，不动领域枚举。
- A9：模板负责平台推荐值，规则负责用户配置。

**否决了什么**

| 被否决 | 为什么 |
|---|---|
| `for_duration` | 与 `consecutive_count` 语义重叠；组合规则是纯复杂度 |
| 恢复阈值可留空、按触发阈值隐式反向恢复 | 抖动风险，且用户不会意识到自己选了它 |
| 规则保存后立即重算 / 回放历史 | 一次配置保存制造突发状态变化并重写历史 |
| 未恢复实例继续按旧规则评估 | 无法用新配置救回一条卡死的告警 |
| 自定义严重级别（增删改名重排） | 全局排序、健康归并、通知过滤全部依赖稳定全序 |
| 「另存为自定义模板」/ 自定义模板库 / 模板共享 | 引入模板所有权、权限、版本传播、删除引用、升级冲突一整套第二资产管理问题；复制已有规则即可满足首版复用 |

**出处**：[T3 · 告警评估与恢复语义](https://github.com/liumingjian/dbs-monitor/issues/5)

### ADR-04 · 慢查询数据源与增强监控范围

**原始问题**（`01` §10 原 M6 / M9 与 `03` §12 原 I6）：

6.（`01`）慢查询数量的 MVP 数据源是否采用日志、活动会话推断，还是延后。
9.（`01`）增强监控是否与标准监控共用采集数据，还是单独高频采集。
6.（`03`）增强监控是否首版作为标准监控的时间粒度选项，还是后续独立页面。

**结论**

- **慢查询进入 R1 MVP**，产品语义为「长时间运行 SQL 的**实时采样与留痕**」，不承诺完整慢查询审计。
  - `pg_stat_activity` 采样为始终可用的基线：只统计采样时**仍在执行且已超过阈值**的 SQL，页面明确提示可能漏掉采样间隔内已结束的查询。
  - DBA 已启用 `pg_stat_statements` 时，机会性提供 Top SQL 聚合增强；平台不自行安装或启用扩展。
- **标准监控与增强监控是并列页签**（复刻阿里云），不是同一页面的粒度选项。两者边界由页面角色、指标组织和诊断控件共同构成，而非仅采样频率——阿里云标准监控本身也有 5 秒粒度。
- **增强监控页签始终可见**，不设用户手动启停的产品状态；能力不足时局部降级并显示原因，不隐藏整个模块。R1 基线复刻已取证的阿里云配置：**最近 30 分钟 / 5 秒粒度 / 平均值聚合 / 两列布局**，提供指标管理、时间选择、聚合方式、布局切换、指标含义与详情。
- **慢查询页面边界**：标准监控展示慢查询数量趋势，增强监控展示 5 秒粒度趋势；支持从图表下钻到采样记录；**不新增独立「慢 SQL 分析」模块**。

**本票同时确立了 R1 后续的默认决策原则**（已写入地图 Notes）：**阿里云优先、差异驱动澄清，而非机械照抄。** 对调研中有可靠证据的功能范围、信息架构、页面划分、指标组织、控件与交互，第一版默认复刻；只重点讨论私有化部署限制、PostgreSQL 能力差异、明显超出 MVP 成本或与目标冲突的部分。云厂商特有的计费、套餐、DAS 品牌概念和内部实现不复刻。

**理由**

慢查询是运维排障的核心诉求，完全不做会让平台在最需要它的场景失声；而基于 RI-B，`pg_stat_activity` 采样是唯一不依赖重启和扩展的路径。把产品语义诚实地定为「采样」而非「审计」，能力边界与实现能力就此对齐——**平台不承诺它做不到的事**，这比功能多寡更重要。

**否决了什么**

| 被否决 | 为什么 |
|---|---|
| 慢查询整体延后 | 排障核心诉求，缺失代价过大 |
| 日志采集 / `auto_explain` / 执行计划 / 完整历史捕获 | 需改配置或重启，私有化环境下不可控（RI-B） |
| 平台自行安装或启用 `pg_stat_statements` | 平台不应持有目标库的 DDL 权限 |
| 增强监控作为标准监控的时间粒度选项（`03` §11 原倾向） | 与已取证的阿里云设计不符；两者差异不止于频率 |
| 用户手动启停增强监控 | 引入一个需要解释代价与生命周期的产品状态，而 MVP 无计费语义支撑它 |
| 独立「慢 SQL 分析」模块 | 越出 MVP 边界，且在无 SQL 文本的前提下（ADR-06）内容空洞 |

**出处**：[T4 · 慢查询数据源与增强监控范围](https://github.com/liumingjian/dbs-monitor/issues/7)

### ADR-05 · 告警处置与触发现场快照

**原始问题**（`02` §9 原 A5 / A10 与 `03` §12 原 I7）：

5.（`02`）告警确认是否需要备注和责任人字段。
10.（`02`）是否需要为每个告警保存触发时的会话 / 阻塞快照。
7.（`03`）会话列表是否需要保存历史快照，还是只展示当前瞬时状态。

**结论**

- **确认**：自动记录操作人与时间，备注**可选**；**不设责任人**。
- **忽略**：自动记录操作人与时间，**原因必填**（原因码：`已知问题，暂不处理` / `误报` / `重复告警` / `影响可接受` / `其他`；选「其他」时补充说明必填）。
- 确认与忽略**共享一个当前处置状态，可相互切换**。`AlertInstance` 只存最后一次处置摘要，历次操作由 `AlertEvent` 永久保留。两种处置均**不触发恢复、不停止评估、不停用规则**。
- **触发现场快照**：仅对会话/阻塞现场能直接解释原因的告警（活跃连接过高、`idle in transaction` 过多、长事务、锁等待/阻塞会话过多），且只在告警实例**首次进入 `FIRING`** 时采集**一次**。每份快照最多 100 个会话，超限时优先保留直接命中对象与完整阻塞链，并记录原始匹配数与截断状态。
- **会话与阻塞页只展示当前瞬时状态**，不提供任意历史时间点、周期快照回放或历史会话搜索。触发现场快照是 MVP 唯一的触发式历史子集，**不形成通用会话历史能力**。

**理由**

确认应当足够快捷，否则值班人员不会用；忽略会降低关注度，必须留下可审计依据——两者的字段要求刻意不对称。触发现场往往在用户打开详情前就消失了，触发式快照以极小代价保住关键证据；而全量周期性保存会同时增加数据库查询压力、高基数存储量和敏感数据暴露面。

**否决了什么**

| 被否决 | 为什么 |
|---|---|
| 责任人 / 分派 / 转派字段 | 引入完整工单分派语义，超出基础告警 MVP |
| 忽略原因选填 | 一个不需要理由的「让它消失」按钮会被滥用 |
| 通用会话历史（周期性快照回放、历史会话搜索） | 存储量与采集压力都是数量级增长，而排障价值集中在告警触发那一刻 |
| 对所有告警类型采集快照 | 主机资源、复制、WAL 类告警与会话现场无诊断关系，采了也没人看 |
| 持续/重复采集快照 | 首次触发的现场才是原因，后续采集只是同一问题的余波 |

**出处**：[T5 · 告警处置与触发现场快照](https://github.com/liumingjian/dbs-monitor/issues/8)

### ADR-06 · SQL 文本展示与脱敏边界

**原始问题**（`03` §12 原 I10）：

10. SQL 文本脱敏规则由平台统一处理，还是由采集端处理。

**结论**

**R1 MVP 不承载 SQL 文本。** 平台不展示原始 SQL、脱敏 SQL、归一化 SQL 或截断摘要；不提供「查看原文」、SQL 复制、SQL 内容搜索或 SQL 导出；**不保存 SQL，也不维护平台标识到 SQL 文本的映射**。

改为使用 PostgreSQL 原生定位信息，不设计统一的平台 SQL ID：

- **长查询采样记录**（`pg_stat_activity` 下钻）展示：会话 **PID**、`query_start`、`sampled_at`、数据库、数据库用户。
- **查询统计排行**（`pg_stat_statements`）展示：**queryid**、数据库、数据库用户、统计区间。
- 两类标识语义独立，不用「SQL ID」统称，也不承诺二者可关联。
- 定位信息跟随实例监控查看权限；均为**尽力而为的后台排查线索**，页面须提示标识可能因查询结束、PID 复用、统计重置、条目淘汰、扩展状态或 PG 大版本变化而失效。
- 页面命名回避「慢 SQL 明细」「Top SQL 明细」等暗示可查看 SQL 内容的说法。查询统计排行须区分：未启用 / 权限不足 / 暂时不可用 / 统计已重置 / 区间内无记录——**不可用不得表现为空表或「暂无数据」**。

**理由**

私有化部署场景下，SQL 文本是客户数据资产中最敏感的一类，而脱敏是**不可能做对的**：任何基于解析或正则的脱敏都会在某些语句上失效，而失效一次就是一次真实泄露。选择不接收 SQL，整个问题类别随之消失——不需要脱敏算法，不需要特权查看角色，不需要为导出/复制/搜索分别定义规则，也不需要在存储层保护它。代价是用户必须凭自身数据库权限自行排查，而在单租户运维团队场景下，用户本来就有那个权限。

**否决了什么**

| 被否决 | 为什么 |
|---|---|
| 展示脱敏后的 SQL | 脱敏无法保证正确；一次失效即泄露 |
| 展示完整 SQL + 特权角色控制 | 把不可逆的泄露风险押在权限配置正确性上 |
| 展示截断摘要 | 截断不是脱敏，SQL 前 80 字符经常正好包含字面量 |
| 平台统一的 SQL ID 与 SQL 文本映射表 | 「不保存 SQL」的直接推论——有映射就是保存了 |
| 按 PID / queryid 的专门搜索能力 | 这两个标识都是易失的，搜索会暗示它们是稳定引用 |

**连带影响**：`03` §8.1 的「查看完整 SQL 文本」敏感能力随之消失，这也是 ADR-09 删除「数据库管理员」角色的原因之一。

**出处**：[T6 · SQL 文本展示与脱敏边界](https://github.com/liumingjian/dbs-monitor/issues/9)

### ADR-07 · No Data、维护窗口、压制与通知集成边界

**原始问题**（`02` §9 原 A3 / A4 / A7）：

3. No Data 是否生成独立告警实例，还是作为已有告警状态。
4. 维护窗口期间是否生成告警但不通知，还是完全暂停评估。
7. 联系人、联系人组、通知渠道是否由本平台管理，还是对接外部通知系统。

**贯穿全票的统一律：压制只影响通知。不影响评估、不影响状态、不影响页面可见性。**

**结论**

- **A3 · No Data 是已有告警实例的状态**，不是独立实例；去重键仍为「规则 × 资源」。`NoDataPolicy` 只保留 `ignore` 与 `mark_no_data`。进入 `NO_DATA` 的门槛为**连续 2 个评估周期缺数**，平台固定，规则级不可配。
  - **统一流转原则：缺数不推进任何状态转换，并清零正在累计的未完成计数。**
  - `FIRING → NO_DATA` 时告警实例 ID、首次触发时间与生命周期全部保留，**仍计为一条未恢复告警**——不得让「数据库不可达」把已知问题从健康状态里擦掉。
  - 长期挂起的 `NO_DATA` 不做基于时长的自动关闭；仅在实例从平台移除时连带关闭。
- **A4 · 维护窗口期间继续评估**，正常生成和更新告警实例与历史，**只压制通知**。窗口结束**不补发**、不排队重放、不发摘要；仍未恢复的告警交由重复通知在下一个 `repeat_interval` 自然接管。窗口内的告警与历史带**维护窗口标记**，使事后可区分「维护造成的」与「真出事的」。`MaintenanceWindow` 削到最小：实例级作用域（可多选实例）+ 起止时间 + 原因。
- **压制模型**：`SUPPRESSED` **从状态机移除**，告警状态收敛为五档 `OK / PENDING / FIRING / NO_DATA / RECOVERED`；压制改为告警实例上的**正交标记**。
- **A7 · 平台自管「谁收」，不自管「怎么送」**：渠道只做 **Webhook**（通用出口）与**邮件 SMTP**（唯一原生渠道，保证平台不依赖外部系统也具备独立告警能力）。联系人模型仅一层（联系人 + 联系人组，无嵌套）。`repeat_interval` **必填**，默认 1 小时，范围 15 分钟–24 小时。通知每次尝试留痕，失败固定 3 次指数退避后记为终态失败。
- **缺数的通知责任归属**：`NO_DATA` 本身**不产生通知**（一次实例失联会让其下全部规则同时进入 `NO_DATA`，逐条通知即为几十条）。作为对冲，**三条采集状态内置规则默认启用、不可删除、不可停用**：数据库不可达、Agent 离线、数据过期。它们是普通规则，走完整的 ADR-03 语义，阈值/严重级别/通知策略均可改，受限的只是「存在与启用」。

**理由**

- No Data 作为独立实例，会在同一规则同一资源上制造两条记录，破坏去重与健康归并。
- 「缺数清零计数」使 `consecutive_count` 的「连续」保持字面成立；代价是宁可晚告警也宁可晚恢复——方向一致，且一句话可解释。
- 「暂停评估」需要回答三个问题：冻结在哪个状态、结束后计数从零起步造成多长的发现延迟、窗口内数据缺失导致事后无法复盘。「继续评估 + 压通知」全部规避，且窗口内数据完整可查。
- 不补发避免窗口结束瞬间集中轰炸淹没真正的新问题；其代价由「重复通知不可关闭」兜住。
- 三条内置规则是全票唯一限制用户自由之处，用以堵死「`NO_DATA` 不通知 + 采集状态规则被关掉 = 数据库挂了平台一声不吭」这一唯一可能造成静默事故的组合。

**否决了什么**

| 被否决 | 为什么 |
|---|---|
| **`Silence`（静默）对象** | 止吵已被两个已有机制覆盖：计划内未发生 → 维护窗口；已发生正在处理 → **确认**（正式定义为「停止该告警实例的重复通知」）。保留它等于让「确认」和「静默」两个作用相同的按钮并存，还要维护两套过期与解除语义 |
| **`SuppressionPolicy`（根因抑制）对象** | 草案举的两个例子在本模型下已提前解决：实例不可达 / Agent 离线时派生规则采不到数，进入 `NO_DATA` 而非 `FIRING`，本就没有通知可抑制。真正需要抑制的是**指标间因果**（CPU 打满→连接堆积→TPS 跌），需要因果图或表达式，草案自身已明确首版不做 |
| **`SUPPRESSED` 作为告警状态** | 与 `NO_DATA` 的区别是决定性的：`NO_DATA` 表示「无法判定」，状态机确实走不下去；压制表示「判定了，只是不打扰」，判定结果完好。做成状态，`FIRING` 被压制后即丢失「它还在烧」这一事实，健康状态无从计算、解除后回到何处亦无定义 |
| `fire_no_data`（缺数本身触发告警） | 缺数的告警通路由采集状态指标的普通规则承担，从而复用完整语义，而非另开旁路 |
| `recover_on_no_data`（缺数视为恢复） | 会把「数据库挂了」表现成「告警恢复了」 |
| No Data 门槛复用 `consecutive_count` | 后者定义为「异常持续」语义；「几次缺数算缺数」是采集健壮性参数，用户没有判断依据 |
| 维护窗口「是否生成告警」开关 | 收敛为固定「生成」；一个没人能说清后果的开关不是灵活性 |
| 维护窗口结束补发 / 摘要 | 集中轰炸淹没真正的新问题 |
| 维护窗口的 `repeat_rule`、规则级/标签级/实例组级作用域 | 削到实例级已覆盖真实场景；作用域维度是复杂度的主要来源 |
| 短信 / IM / 电话原生适配 | 私有化环境下各家网关与 IM 差异过大，逐个适配是无底洞；一律走 Webhook |
| 值班排班 / 轮值 / 升级路由 / 按级别分渠道路由 / 通知分组 | 完整通知平台的能力，不是数据库监控 MVP 的 |
| `max_repeat_count` 与「不重复」选项 | 两者都会造成未恢复告警永久静音，抽掉「窗口结束不补发」所依赖的前提。**吵是设计的一部分，止吵的唯一正确动作是「确认」** |
| 「通知失败本身产生告警」 | 递归——该告警的通知同样可能失败 |

**出处**：[T7 · No Data、维护窗口、抑制与通知集成边界](https://github.com/liumingjian/dbs-monitor/issues/10)

### ADR-08 · 实例健康状态模型

**原始问题**（`03` §12 原 I4）：

4. 实例总览中的健康状态如何加权：告警、事件、采集状态、指标异常各占什么权重。

**这个问题的前提被否决了——不加权。**

**贯穿全票的统一律：实例健康是「未恢复告警」的一个视图，不是第二套判定。**

**结论**

- **可解释的最坏状态归并**：实例健康 = 全部参与归并的未恢复告警中最坏的那一个，按全序取最大值。
- **单一来源**：健康只由未恢复告警派生。实例连通性、Agent 状态、采集新鲜度**不作为独立健康输入**——它们经 ADR-07 的三条内置规则进入告警，再进入健康。这三项在实例列表中保留为**独立展示列**，不参与健康计算。
- **主状态**（经 ADR-10 修订为「四档归并 + 已暂停 override」）：

  | 主状态 | 判定 |
  |---|---|
  | **严重** | 存在参与归并的 `critical` 未恢复告警 |
  | **警告** | 存在参与归并的 `warning` 未恢复告警 |
  | **未知** | 该实例至今没有任何一次成功采集 |
  | **正常** | 有过成功采集，且无参与归并的 critical/warning 未恢复告警 |
  | **已暂停** | override，见 ADR-10 |

- **`info` 不改变主状态**，以计数徽标呈现，可单独筛选，仍在告警列表、仍按通知策略通知。**附带约束**：三条内置采集状态规则的严重级别不得低于 `warning`。
- **正交标记**（不改变主状态，可与任意主状态共存）：`无数据` / `维护中` / `近期恢复(24h)` / `已忽略 N` / `配置缺失 N`（后者见 ADR-10）。
- **「已忽略」退出健康归并**——不参与主状态、不计入计数、不出现在归因行；但仍在告警列表可见、仍继续评估、仍走重复通知。
- **列表行信息契约固定为三层**：主状态 → 归因行（最坏那条告警的规则名 + 当前值）→ 计数与标记。实例总览复用同一主状态与归因行。
- **结构性「不适用」与「配置缺失」均不产生告警、不影响健康**；前者只在图表/模块层显示占位，后者集中到采集管理页的待办清单（见 ADR-10）。

**理由**

- 权重对用户不可解释、阈值无法辩护；告警本身已带三档严重级别，再叠一层权重等于把同一件事排两次序。列表页的核心动作是「筛出该看的实例」——最坏归并直接可筛，评分只能筛区间。
- 多路输入会双重计数同一事实，且两条路径的阈值与滞回不一致，会出现「健康已变红但告警还在 PENDING」这类用户无法解释的自相矛盾。单一来源天然满足「无需猜权重」：**点开状态就是那条告警**。
- `info` 规则天然常亮（如「连接数超 60%」这类观察项）。若染色，列表长期没有绿色，「正常」档在真实环境几乎不出现，健康随即丧失分辨力——这是权重之外另一种把列表变成噪声的方式。
- 「忽略退出健康」使两种处置有了互不重叠的作用面：**确认 = 别再通知我；忽略 = 这不该算作实例的健康问题**。若忽略不产生任何可见后果，用户填了必填原因码却什么也没换来，该按钮很快无人使用；而「误报」若无法让实例从红变绿，列表将长期挂红，用户随即停止相信健康状态——单一来源模型一旦被不信任，整个设计价值归零。

**否决了什么**

| 被否决 | 为什么 |
|---|---|
| **数值加权评分** | 权重不可解释、阈值无法辩护、与已有的严重级别重复排序；评分只能筛区间，不能筛出「该看的」 |
| 「异常」「告警中」两个健康状态（`03` §7.1 原枚举） | 在单一来源模型下是同一件事；且与告警详情页的级别词对不上，用户需自建映射 |
| 「已恢复」作为健康状态 | 其余档描述**此刻**，它描述**过去**；作为独立档位会立刻产生无解问题——恢复多久之后变回正常？任何时长都是拍脑袋，且它与「正常」争夺同一批实例。降为 24 小时正交标记后，时长猜错只影响一个提示的显隐 |
| 「数据不可信压顶」（失联时健康变灰） | 会擦掉已知问题，直接违反 ADR-07 的「不得让数据库不可达把已知问题从健康状态里擦掉」。实例失联时其下已 FIRING 的告警必须继续把实例染红 |
| 连通性 / Agent / 新鲜度作为独立健康输入 | 双重计数；两条路径语义不一致 |
| `info` 参与染色 | 列表长期无绿色，健康丧失分辨力 |
| 「未知」可反复进入 | 定为一次性、单调的开局状态：唯一入口是从未成功采集，退出条件是首次成功采集，此后永不再回。无需阈值与滞回，规则简单到无需文档 |

**出处**：[T8 · 实例健康状态模型](https://github.com/liumingjian/dbs-monitor/issues/11)

### ADR-09 · 平台级配置入口与权限边界

**原始问题**（`03` §12 原 I9）：

9. 采集配置是否允许普通用户修改，还是仅平台管理员可见。

（ADR-07 创造了通知渠道、联系人与联系人组、通知策略、维护窗口四类需要管理界面的对象，而 `03` §3 首版页面树中不存在任何平台级配置入口——本决策同时收口这一缺口。）

**结论**

- **新增顶层区「告警设置」**，首版页面树从三个顶层节点变为四个：实例列表 / 全局告警 / 实例工作台 / **告警设置**。区内四页：通知渠道、联系人、通知策略、维护窗口。命名刻意收窄为「告警设置」而非「系统管理」，把边界钉死在这四类对象上。
- **维护窗口并存，但职责严格不对称**：平台页为**唯一管理面**（列表/创建/编辑/提前结束/删除）；实例工作台只有只读维护状态标记 + 一个「新建维护窗口」快捷入口（同一张表单，仅预填当前实例）。
- **通知策略绑定 = 全局默认 + 规则覆盖**：默认策略有且仅有一个、不可删除；规则级单选一个策略；覆盖即替换，非叠加；规则列表与编辑页必须**回显生效策略名**。
- **角色收敛为三档全局角色**（严格包含关系）：只读运维 → 告警管理员 → 平台管理员。
- **权限统一律：可见性不收窄，写能力收窄。** 所有角色都能看见全部配置页内容；无写权限时控件置灰并说明所需角色，**不隐藏入口**。**唯一例外是凭据类字段**——SMTP 密码、Webhook 密钥/签名头一律掩码，任何角色（含平台管理员）都不可读明文；有写权限者可覆写、不可读取。
- **通知失败可见性加一层「推」**：在「通知渠道」页签上显示**导航角标**。角标不是告警——不进状态机、不产生告警实例、不发通知、不影响实例健康。

**理由**

- 渠道、联系人是跨实例单例，挂进实例工作台会让「实例 A 的通知渠道」这种读法成立，而它不成立（改一次影响全平台）；挂进「全局告警」则把纯观察面变成观察+配置混合体。
- 维护窗口两处入口的不对称是有依据的：**创建高频且天然带实例上下文，管理低频且天然跨实例**。只做平台页会逼运维在「我要重启这台」的时刻跳出工作台重新找回实例；只做工作台入口则「现在全平台有哪些维护窗口在生效」无处可答。
- 通知策略采用默认+覆盖的**决定性依据是 ADR-07 自己**：三条内置规则不可删除、不可停用。若采用「规则必选策略」，装机瞬间这三条规则要么无通知归属（正是要堵死的静默事故），要么被强绑一条系统预置策略——那已经是默认策略，只是模型上不承认，于是「它能不能删」无解。
- 「可见性不收窄」有三条依据：`03` §1.4「空状态必须解释原因」是全文档立身原则，隐藏入口是它的反面；只读运维排障时必须能回答「这条告警为什么没通知到我」，而 ADR-07 恰恰把失败可见性放在渠道配置页，藏起来等于只留给管理员，最需要它的人反而看不到；私有化单租户下隐藏式权限无安全收益，只有支持成本。

**否决了什么**

| 被否决 | 为什么 |
|---|---|
| 命名为「系统管理」的顶层区 | 会变成实例接入、用户管理、License 等无关物的堆放处 |
| 四类对象分散挂到已有页面 | 跨实例单例挂进实例工作台是错误的读法；挂进全局告警会混淆观察面与配置面 |
| 邮件与 Webhook 各占一页 | 它是同一概念（出口）的两种形态，拆页会把失败可见性劈成两半 |
| 工作台承载维护窗口的列表/编辑/删除 | 会长出第二套作用域与过期语义 |
| 「规则必选通知策略」 | 三条不可删除的内置规则在装机瞬间无通知归属 |
| 规则多绑策略 / 策略路由 | 等于把已排除的按级别路由从后门放回 |
| **「数据库管理员」角色** | 在 MVP 已无任何专属能力：「查看更完整会话信息」被 ADR-06 清空，「cancel / terminate」`03` §8.1 自己就写了首版不开放。**一个语义为空的角色只会被误选**；等 cancel/terminate 真正进入路线时再作为新角色引入 |
| 能力勾选式的自由权限组合 | MVP 规模下是纯复杂度 |
| **实例级授权（数据权限）** | 会连带拽出实例分组/项目/归属对象，以及全局告警按权限过滤、维护窗口可选实例范围等一串新决策，全在 R1 终点之外 |
| 凭据明文回显（哪怕仅限管理员） | 泄露不可逆，而「读回明文」在运维上没有必要——要换就重填 |
| 全局「通知记录」查询页 | 记录已随告警详情逐条可查，再开一个全局查询面 MVP 不值 |

**显式让步（必须写进规格，不得隐去）**：ADR-06 的「跟随实例查看权限」在不做实例级授权的前提下退化为「跟随全局只读权限」——任何登录用户可见全部实例的会话 PID 等定位信息。单租户运维团队内可接受。

**残留风险（显式接受）**：导航角标仅在有人登录时起作用；若邮件全挂且无人登录仍无人知晓。真正兜底的是邮件与 Webhook 双通道并存。

**出处**：[T9 · 平台级配置入口与权限边界](https://github.com/liumingjian/dbs-monitor/issues/12)

### ADR-10 · 采集管理页职责补全（暂停采集 + 配置缺失待办）

**原始问题**：无对应的草案待确认项。本决策收口 ADR-08 与 ADR-09 留下的两个悬空依赖——ADR-08 把「已暂停」定为健康主状态之一，但首版 IA 中不存在任何进入该状态的入口；ADR-08 把「配置缺失」交给采集管理页集中呈现，但未定其页面形态。

**共同判据：采集管理页承担「让实例安静」和「让实例可信」两件事，而这两件事都必须留下可见的代价。**

**结论 · 暂停采集**

- **MVP 提供暂停，最小形态**：实例级布尔开关。不做定时暂停、批量操作、按指标粒度暂停。
- **作用面停到评估层**：暂停 = 停采集 + 停评估；通知随之自然消失。
- **与维护窗口的界限**（两句话，已写进规格）：
  - **维护窗口** = *我知道这段时间它会抖，别吵我，但数据我还要* → 继续采集、继续评估、只压通知。事后可回看。
  - **暂停采集** = *这台现在没有可信数据可采，整体退出监控视野* → 停采集、停评估。那段时间没有数据，事后也回看不了。
- **「已暂停」是 override，不参与最坏归并**——ADR-08 的五档全序在此修订为「**四档归并 + 已暂停 override**」。
- **存量未恢复告警冻结**：状态原地保留在按下暂停的那一刻，不再迁移，不发任何通知；仍在告警列表可见，带「已暂停」正交标记。**解冻不回放**：条件仍满足则延续**同一条**告警实例继续 FIRING（不新建），不满足则走正常恢复流程。暂停期间的空窗不产生 `NO_DATA`。
- **归属采集配置，平台管理员可写，采集管理页为唯一管理面**。由此得到干净的域划分：**维护窗口属告警域（告警管理员写），暂停属采集域（平台管理员写）**。
- **护栏**：操作人 + 时间必录，原因**选填**；实例列表的「已暂停」标记带时长，超过 **7 天**转警示色；导航角标显示已暂停实例数。**只提醒、不升级为告警**——若暂停实例反过来产生告警，等于暂停不生效。**不做自动到期恢复**。

**结论 · 配置缺失待办清单**

- **独立模块，置于采集管理页最顶部**，是全页唯一可执行的模块（其余五个都在陈述事实）。
- **条目 = 能力粒度**（`缺少 pg_monitor 角色 —— 影响 6 项指标`），可展开列出受影响指标；每条带一句**文字修复指引**，**不带一键修复按钮**——平台没有、也不该有目标库的 DDL/DCL 权限。
- **不建跨实例聚合页**；改为实例列表的 `配置缺失 N` 正交标记 + 「存在配置缺失」筛选维度。真正的按能力跨实例聚合页记入延后清单。
- **三态展示契约（绝不报假绿）**：

  | 情形 | 清单里的呈现 |
  |---|---|
  | 可修复缺失（无权限 / 扩展未启用） | 待办条目（能力粒度），带影响指标计数与文字修复指引 |
  | 结构性不适用（无 slot / 角色拓扑不适用 / 版本不支持） | **不进清单**；仅在能力清单里显示为「不适用」并附原因，措辞明确区别于「缺失」 |
  | **查不到 / 检查失败** | **进清单，且排在最前**：`无法检查采集能力 —— 数据库不可达，以下 N 项状态未知`。**绝不静默按「具备」处理** |
  | 确实全部就绪 | 显式正向空状态：`无待办 —— 所有可修复的采集能力均已就绪（最近检查 3 分钟前）` |

  三条约束：模块**永不隐藏**；正向空状态**必须带最近检查时间**（「一切就绪」如果是三天前的结论，它就是假的）；「查不到」不得降级为「就绪」。

**理由**

- 暂停的必要性来自一个维护窗口盖不住的场景：实例下线待回收、计划内长时间停机、迁移/重建。维护窗口「继续评估、只压通知」，所以这些实例照样进 `NO_DATA`、照样算一条未恢复告警、照样在列表里非绿。**维护窗口让人耳根清净，没让列表干净**，而长期挂红的僵尸实例是 ADR-08 整个模型的价值前提（用户必须相信健康状态）最典型的杀手。
- 「让用户手工删实例」不成立：删实例丢历史数据，用户不敢删，于是回到挂红。
- 留痕要求与 ADR-05「忽略原因必填」的分歧是刻意的：**忽略是悄悄发生的**——一条告警从视野里消失，别人看不出，所以必须逼出理由；**暂停是响亮的**——整台实例变灰、主状态改写、列表里一眼可见，本身就在追问「这谁干的」。
- 待办清单用能力粒度而非指标粒度，是因为**能力粒度对应用户能执行的动作单元**（装一个扩展、授一次权）。指标粒度的清单会把同一个修复动作重复若干遍，而「影响几项指标」这个说服力最强的数字，恰恰只有聚合之后才存在。
- 三态契约中的第三态是最危险的：**一个空清单看起来永远像好消息**。数据库不可达时平台根本不知道扩展装没装，此时清单若显示为空，页面就在说「一切就绪」，而真相是「我们什么都没查到」。

**否决了什么**

| 被否决 | 为什么 |
|---|---|
| 不提供暂停、删除「已暂停」档 | 悬空档位；且真实场景明确存在，维护窗口盖不住 |
| 「只停采集、不停评估」 | 评估还在跑，无数据即进 `NO_DATA`，仍算一条未恢复告警，实例照样非绿——功能等于没做 |
| 暂停时把存量告警**强制关闭为 `RECOVERED`** | 这是谎报——条件根本没恢复，只是不看了。连带两个错误后果：恢复通知会发出一批假恢复；「近期恢复(24h)」标记会给这台实例挂上「刚刚好转」的暗示。历史被污染，事后复盘看不出真相 |
| 解冻时新建告警实例 | 解冻瞬间制造假的「新告警」风暴 |
| 暂停的定时/批量/按指标粒度形态 | 批量会立刻拽出选择态、批量确认、部分失败回执一整套交互，而真实场景里一次暂停一台是常态 |
| 暂停原因必填 | 暂停本身高度可见，强制填写边际收益低而阻力真实 |
| 自动到期恢复暂停 | 会在你没准备好的时候突然开始告警，比忘记恢复更危险 |
| 为暂停发明新的权限维度 | 归进采集配置即自动继承 ADR-09 已定的权限判定 |
| 待办清单做成「指标采集状态」模块的筛选视图 | 粒度对不上——那是指标粒度，待办需要能力粒度 |
| 按能力跨实例聚合的配置缺失页 | 它**无处安放**：ADR-09 刚把页面树收口成「实例工作台 + 告警设置区」，跨实例的采集视图哪边都不属于，硬塞会推翻刚定的结构或逼出一个新顶层区。用实例列表标记 + 筛选以零新页面解决 80% 的问题，只把「按能力批量修」推后 |

**出处**：[T10 · 采集管理页职责补全](https://github.com/liumingjian/dbs-monitor/issues/13)

## 4. 四条跨文档不变式

合稿一致性检查围绕以下四条展开。后续路线修改任何一份规格时，应先确认不破坏它们。

1. **告警状态五档，压制是正交轴。** `OK / PENDING / FIRING / NO_DATA / RECOVERED` 是全部状态；维护窗口、确认、已暂停均为**正交标记**，不是状态。（`02` §3.5 / §3.8 / §4.1、`03` §7.3 必须一致）
2. **实例健康 = 未恢复告警的最坏归并 + 已暂停 override，单一来源。** 不存在第二条判定通路。（`03` §4.1 / §4.2 / §7.1 必须一致）
3. **三档全局角色，可见性不收窄、写能力收窄，凭据永不回显。** （`03` §8 / §8.1、以及各页面职责中的权限描述必须一致）
4. **三条采集状态内置规则不可删除、不可停用，严重级别下限 `warning`。** （`02` §3.4 / §6、`03` §7.1 必须一致）
