# 32 · 外部平台库形态下的平台存储水位与写保护

> 出处：[拆 #124 前置核对：开放票冲突裁定与修订清单 #125](https://github.com/liumingjian/dbs-monitor/issues/125)，承 [投产化 delta spec #124](https://github.com/liumingjian/dbs-monitor/issues/124) 拆票前的决策缺口。
> 定位：补齐 [18](18-v1-delivery-boundary-bs-binary.md) / [30](30-external-postgres-prerequisites.md) 把平台库移到客户主机后，[14](14-platform-observability-and-diagnostics.md) D4「磁盘三级水位 + 紧急拒写」失去保护对象的问题。本文只改定 T14 D4 的水位来源与保护动作，不重议平台健康四态、非递归边界或样本保留承诺。
> 输入边界（不重议）：[14](14-platform-observability-and-diagnostics.md) D2–D4；[18](18-v1-delivery-boundary-bs-binary.md) D2/D8；[26](26-data-and-recovery-gate.md) D6；[30](30-external-postgres-prerequisites.md) D3.3/§10.2；`AC-09-S1`、`AC-09-F5`、`AC-09-F6`。
> 状态：v1.0，2026-08-15 冻结。要推翻其中任何一条，应新开决策记录，不在此原地改写。

## 0. 一句话结论

**平台库容量与 server 本机盘是两条互不相干的水位：平台库以 `pg_database_size(current_database())` 除以部署期容量预算，紧急时拒写新样本；server 本机盘只保护诊断包、本地通知快照与 debug 日志等本机大体量写入面，绝不阻断样本。两条水位各自配置、各自进健康快照；样本侧「绝不自动删旧分区、绝不缩短 30 天保留期」保持不变。**

---

## 1. D1 · 一条水位拆成两个保护对象

[14](14-platform-observability-and-diagnostics.md) D4 把「磁盘使用率」「拒写新样本」「保护存储」连成一条链。这条链只在平台库与 server 共用本机盘时成立；[18](18-v1-delivery-boundary-bs-binary.md) D2 已把平台库移到客户主机，[30](30-external-postgres-prerequisites.md) D3.3 又明确平台普通角色看不到客户主机的可用空间。

因此水位拆成两条：

| 线 | 事实 | 保护对象 |
|---|---|---|
| A · 平台库容量 | 平台库已用容量占部署期预算的比例 | 客户 PG 上的样本存储 |
| B · server 本机盘 | server 主机可见的本地文件系统使用率 | 平台本机诊断与兜底能力 |

两条线不互相推导。server 本机盘满不能证明平台库容量紧张，平台库容量紧张也不能触发本机文件回收。

## 2. D2 · 分级、滞回与采样节拍

两条线都采用预警 80% / 临界 90% / 紧急 95%，回落须越过 2 个百分点的滞回带，并随既有 60 秒健康快照节拍采样。

A、B 两条线各自拥有一套独立的部署期阈值与滞回配置，不进用户 UI。相同默认值只表示默认策略一致，不表示两个事实源共用配置或状态。

## 3. D3 · A 线事实源与健康投影

A 线使用 `pg_database_size(current_database())` ÷ 部署期配置项「平台库容量预算」。平台库的 database 名由配置给出，`dbsmon` 是固定 schema 名。预算由客户按 [30](30-external-postgres-prerequisites.md) §10.2 第 6 条的容量依据填写，不从 server 本机盘推算，也不编造平台库主机的剩余空间。

该事实追加为 [14](14-platform-observability-and-diagnostics.md) D2 的第十个健康子系统 `platform_db_capacity`（API 枚举 `PLATFORM_DATABASE_CAPACITY`）：

- 正常为 `OK`；
- 预警 / 临界为 `DEGRADED`；
- 紧急为 `FAILED`。

这是枚举追加。第七项 `disk` 的位次与名称不动。

## 4. D4 · A 线紧急档保护样本存储

平台库容量进入紧急档后拒写**新样本**。拒写必须表现为对应 Task 失败与 collection-source integrity watermark 停摆，细因明确为「平台库容量紧急水位」，不得把样本静默丢弃。

处置留痕、配置等控制面小体量写入豁免，避免平台在最需要操作时把自己锁死。平台不额外制造目标告警；数据过期等派生规则按既有缺数语义自然工作。

## 5. D5 · 容量预算未配置时不猜

容量预算允许为空。未配置时：

- `platform_db_capacity` 为 `UNKNOWN`，总态依 [21](21-v1-acceptance-entries-a.md) 的 `AC-09-F6` 绝不为 `OK`；
- 不拒绝 server 启动；
- 不编默认容量；
- 不执行样本拒写。

`UNKNOWN` 表示「缺少判定所需事实」，不能被压成 `OK`，也不能用保守拒写冒充已知的紧急事实。

## 6. D6 · B 线只保护 server 本机写入面

B 线就是 [14](14-platform-observability-and-diagnostics.md) D2 既有第七项 `disk`，事实为 server 本机文件系统使用率。预警 / 临界映射 `DEGRADED`，紧急映射 `FAILED`。

紧急时停止本机大体量写入面：诊断包生成、本地通知快照、debug 级日志。样本仍写入外部平台库，不因本机盘水位被拒绝。

## 7. D7 · 本机产物回收必须有界且可见

平台可以自动回收本机产物，但每类回收都必须有显式上限配置，并产生可枚举的平台事件，绝不静默删除。诊断包与本地通知快照分别由 #75 / #83 提供「可列举、可删除单份」的窄接缝；回收策略只由替代票 #126 承载。

systemd journal 不在平台回收范围内，继续由 journald 的轮转限额管理。

## 8. D8 · 矩阵只改写既有两条

不新增验收条目：总数保持 104、硬底保持 101、`n-a` 保持 5、允许 `pending` 的普通加深保持 2、`exceptions` 保持 `[]`。

1. `AC-09-S1` 从七事实源改为**穷尽列举十项**，一次接住 `keyring`、`tls` 与 `platform_db_capacity` 三项追加，并把「自带 PG」改为外部平台库。
2. `AC-09-F5` 保留原八个断言点，只把触发手段从「调低本机盘紧急阈值」改为「调低平台库容量预算至当前占用之下」，失败细因与健康源随之改为 `platform_db_capacity`。

## 9. D9 · 样本侧两条禁区无条件保留

无论 A 线还是 B 线进入什么级别，平台都**绝不自动删除旧分区、绝不自动缩短 30 天保留期**。这两条是 [14](14-platform-observability-and-diagnostics.md) D4 中不依赖部署形态的承诺，本文不推翻。

## 10. D10 · 非递归边界不变

两条水位都是平台自身运行事实，继续只走 journal、本地通知快照与诊断 API，不创建目标告警实例、不写成目标侧 `NO_DATA`。A 线拒写造成的真实缺数由既有 Task 状态、完整性水位与派生规则表达，不另造一套告警语义。

## 11. D11 · 票据处置

原 #74 的四条主体中，事实源与保护动作均依赖「自带 PG + 平台可见数据盘」，整票前提失效，不以追加长修订继续实施。#74 关闭，由 #126「平台库容量水位与本机盘水位保护」承载本文实现，并 blocked-by #73 的四态快照框架。

## 12. 否决记录

| 被否决 | 理由 |
|---|---|
| 继续用 server 本机盘水位拒写样本 | 样本在外部平台库；该动作保护不了触发源所在的盘 |
| 以 `pg_database_size` 冒充客户主机可用空间 | 它只给已用容量，不给文件系统剩余空间；会制造假绿门 |
| 容量预算缺失时编一个默认值 | 客户存储配额未知，默认值没有事实依据 |
| 容量预算缺失时保守拒写或拒启动 | `UNKNOWN` 已是冻结语义；拒写会把缺配置升级成数据中断 |
| 本机紧急水位自动删样本分区或缩保留期 | 静默破坏 30 天保留承诺，且不解决外部平台库容量问题 |
| 平台自行清理 journal | journal 的轮转归 journald；重复实现会产生两个互相竞争的保留策略 |
