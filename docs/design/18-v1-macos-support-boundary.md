# 18 · v1 macOS 支持边界

> 出处：[v1 macOS 支持边界：arm64、macOS 版本与最低承诺 #99](https://github.com/liumingjian/dbs-monitor/issues/99)（地图 [#98](https://github.com/liumingjian/dbs-monitor/issues/98) 子票）。
> 定位：冻结 v1 首发的操作系统、运行架构与“支持 macOS”的最低验收语义。PostgreSQL 交付形态、构建发布路线及既有 Linux 发布票的处置分别由地图 #98 的其他子票决定，本文不展开。
> 状态：2026-08-10 冻结。本文是对 [`09`](09-packaging-and-deployment.md) 与 [`15`](15-ci-and-release-pipeline.md) 中 Linux 双架构发布边界的后续决策；v1 首发范围冲突时以本文为准。

---

## 0. 一句话结论

**dbs-monitor v1 的唯一原生交付目标是 macOS 14.0 及以上版本的 Apple silicon（`darwin/arm64`）；不承诺 Intel macOS、`darwin/amd64`、universal binary 或经 Rosetta 2 运行。所谓“macOS 上适配运行”同时覆盖源码开发、原生 CI 验证、干净机安装和交付物运行，四项缺一不可；Linux 与所有 amd64 目标均不进入 v1 发布验收。**

## 1. D1 · 唯一支持元组：`darwin/arm64` + macOS 14.0

| 维度 | v1 承诺 |
|---|---|
| 操作系统 | macOS，最低版本 **14.0** |
| CPU / ABI | Apple silicon，原生 **arm64**（Go 目标 `darwin/arm64`） |
| 交付组件 | v1 随产品交付、在宿主机执行的 server、Agent，以及后续选定的 PostgreSQL 运行形态 |
| 浏览器与被监控库 | 浏览器客户端兼容性不由宿主 CPU 边界定义；远端 PostgreSQL 的宿主 OS 也不因本决策改变 |

`14.0` 是固定的 v1 最低版本，不采用“当前版本往前 N 代”这类会随时间漂移的表述。v1 发布时已经存在且不低于 14.0 的 macOS 大版本，必须各自在原生 arm64 环境完成 §2 的发布验收后才进入支持清单；v1 发布后出现的新 macOS 大版本不自动获得承诺，可在相同验收通过后的 v1 补丁版本中加入。

选择一个 OS/架构元组，是为了让首发的构建、安装和运行证据闭合在同一目标上。把最低版本下探到 Apple silicon 的全部历史版本，或同时维护两个 CPU ABI，都会扩大兼容矩阵，却不增加 v1 的核心产品能力。

## 2. D2 · “macOS 上适配运行”覆盖四类场景

| 场景 | v1 最低承诺 | 足够的验收证据 |
|---|---|---|
| 源码开发 | 支持在目标元组上安装仓库声明的工具链与依赖，执行日常检查并构建 server/Agent | 原生 arm64 主机上 `make check` 与本机构建通过 |
| CI | 发布候选必须经过目标元组上的原生执行；不是每个 PR job 都必须迁到 macOS | 原生 arm64 macOS runner 留下与候选提交对应的成功记录 |
| 安装 | 发布交付物可在一台干净的受支持 Mac 上按正式文档完成安装，不要求 Rosetta 2 | 按后续交付决策完成干净机安装与首次启动验收 |
| 交付运行 | v1 的宿主侧组件均以原生 arm64 运行，完成启动、重启、健康检查和核心端到端冒烟 | 对最终交付形态进行原生运行验收；仅有交叉编译成功不算 |

四类场景共同构成“支持”。开发机上一次 `make check` 通过，不能单独证明可安装或可交付；Linux runner 交叉编译出 `darwin/arm64` 二进制，也不能替代原生运行证据。CI 的具体触发、runner、资产、签名和公证策略不在本票决定。

## 3. D3 · 明确不承诺的 macOS 形态

- **Intel macOS / `darwin/amd64`：不承诺。** 不构建、不发布，也不纳入缺陷修复或回归矩阵。
- **Universal binary：不承诺。** v1 只产出 arm64 目标，不把两种 Mach-O 架构合并为单一资产。
- **Rosetta 2：不承诺。** 即使某个组件偶然可经转译运行，也不构成受支持路径或验收证据。
- **低于 macOS 14.0：不承诺。** 能启动属于偶然兼容，不据此扩大支持边界。

以上是 v1 的产品边界，不是对未来版本的永久否决。新增任一目标都必须先开新的决策记录，并补齐该目标从构建到交付运行的完整证据。

## 4. D4 · Linux / amd64 从 v1 验收中排除

- v1 发布清单、发布门、安装文档与支持矩阵只允许 §1 的 `darwin/arm64` 元组；不得把 Linux 或任何 amd64 资产列为 v1 必交物。
- 既有 Linux amd64/arm64 打包脚本、workflow、验证记录和 walking-skeleton 产物是历史工程资产，不因本文删除，也不再构成 v1 完成条件或发布阻塞项。
- 为静态兼容性保留的 Linux 交叉编译可以继续作为非发布检查，但通过或失败均不得被表述为 v1 Linux 支持证据；是否保留这些检查由后续实施票处理。
- “Linux/amd64 不支持”只描述 dbs-monitor 交付物的宿主目标，不禁止 v1 通过 PostgreSQL 协议监控运行在 Linux/amd64 上的远端数据库。需要宿主 Agent 的能力则只在 §1 支持元组内承诺。

这一区分避免两种误读：不把旧 Linux 证据冒充当前发布承诺，也不把交付宿主边界错误扩大成被监控 PostgreSQL 的宿主限制。

## 5. 否决与延后记录

| 被否决 / 延后 | 为什么 |
|---|---|
| macOS 11 起覆盖全部 Apple silicon 系统 | 扩大 OS 回归矩阵；v1 没有必须支持旧系统的产品需求 |
| Intel macOS 与 arm64 同时首发 | 增加第二套原生构建与运行证据，且会继续牵引 amd64 依赖 |
| universal binary 作为“一个包支持两种 Mac” | 仍需两套完整验证，单文件不减少支持成本 |
| 用 Rosetta 2 兜底 Intel 组件 | 转译路径不是原生 arm64 交付，故障归因与性能边界不清 |
| 用交叉编译代替原生 macOS CI / 运行验收 | 只能证明编译，不能证明安装、启动和运行 |
| 签名、公证、分发渠道、安装器细节 | 属构建与发布路线，不由支持元组决策提前规定 |
| PostgreSQL 的本机、容器或外置形态 | 属运行与 PostgreSQL 交付路线，不由本票决定 |

## 6. 交给下游

| 下游 | 必须承接的边界 |
|---|---|
| PostgreSQL 交付形态决策 | 所选形态必须能在 macOS 14.0+ arm64 干净机完成安装和原生交付运行验收 |
| macOS 构建、验证与发布路线 | 只把 `darwin/arm64` 作为 v1 发布目标，并为 §2 四类场景建立可追溯证据 |
| 既有 Linux 发布票处置 | 从 v1 必交物和阻塞条件中移除 Linux 与 amd64，不把历史证据删除或改写 |
