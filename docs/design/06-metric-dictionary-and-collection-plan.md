## 0. 本文档要解决的问题

R1 把指标字典交付为一份**人读的 v1.0 规格**，并显式把「机器可读配置载体」划给 R2（决策索引 M10）。落到实现，要回答的其实是四个互相纠缠的问题：

1. 字典住在哪里，谁能改它；
2. 采集到底以什么为单位发生（字典按指标组织，采集不按指标发生）；
3. 「前置条件」怎么从散文变成能驱动 ADR-10 三态契约的东西；
4. 标准监控与增强监控的采样分层，落到采集管线是一条还是两条。

本文档的取向与 [T5](05-backend-code-structure.md) 一致：**优先选结构性保证**（编译器或测试会拦下违规），而不是写在文档里靠人记住的纪律。

## 1. 载体形态：口径与计划参数分家

字典不是一个整体，它有两半，可变性完全不同：

| 半边 | 内容 | 谁能改 | 住哪儿 |
|---|---|---|---|
| **口径**（不可变半） | 指标 ID、类型、单位、维度、SQL / 探针、差分与 reset 规则、前置条件、是否可告警 | 只有发版 | **Go 声明，编译进二进制**（L1 `internal/metric`） |
| **计划参数**（可变半） | 任务采样周期、暂停/恢复采集、是否启用 Agent 指标 | 平台管理员在 UI 改 | **库表** |

### 1.1 口径半为什么不外置成 YAML / 不入库

1. **口径半里装的是代码，不是配置**——SQL、差分规则、前置条件谓词。外置成 YAML 只会逼出一个 mini-DSL 和它的解释器（条件表达式、谓词求值），把编译器能查的错误变成运行时才炸的错误。这与 R2 终点的核心命题（后续会话靠编译器反馈判断自己写对了）直接冲突。
2. **可编辑载体没有消费者**——§7 已定用户不能自定义指标，「不发版就能改」这个唯一好处没人消费，却要付出升级合并、漂移、校验三份代价。
3. **整包交付下，编译进二进制是唯一不需要回答「升级时怎么合并用户改动」的形态。**

### 1.2 代价

改一个指标口径必须发版，口径无法在客户现场热修。这是有意接受的：**口径是契约，热修口径本来就该走发版。**

### 1.3 计划参数为什么在库里

承 [T5](05-backend-code-structure.md) §8.1「UI 能改的不进配置文件，运行期配置只在库里」——同一个值同时可在配置文件与 UI 配置，必然要回答「听谁的」。

## 2. 字典文档与载体的关系：三分，不是二选一

`01-pg-mvp-metric-dictionary.md` 是 R1 结束时**冻结的 v1.0 规格**，且它的字段有一半不是机器消费的——「定义」「缺数语义」「UI 展示」「关联事件」「采集成本」是写给人看的**理由**，生成器写不出来。

因此：

1. **Go 声明是运行时的唯一源。** 采集器、能力探测、告警可用性判定一律读它；代码里不得出现第二处指标常量。
2. **R1 字典文档保持冻结，不被生成覆盖。** 它承载「为什么是这个口径」，是 R3–R6 会话读的东西。
3. **两者的交集由一条测试锁住，而不是靠人复核。**

### 2.1 §3 一致性测试（强制）

一条 Go 测试解析字典 **§3「P0 指标总览」表**（格式规整、可解析），比对四列：

- 指标 ID 全集
- 标准监控 是/否
- 增强监控 是/否
- 是否可告警 是/否/视情况

任何一侧多一个、少一个、或标记不一致 ⇒ `go test` 红。

它拦下的正是几十个会话里最容易悄悄发生的两种漂移：**文档说有但没实现**、**实现了但字典没登记**。它只锁 §3 那张表、不锁 §4 明细散文，因此不脆。

> 该测试进 [T9](https://github.com/liumingjian/dbs-monitor/issues/27) 的强制测试清单。

### 2.2 「已实现口径」附录（生成物）

Go 声明另生成一份 `docs/design/01-appendix-implemented.md`（**生成物入库**），列出每个指标实际的 SQL、前置条件、所属任务与周期。它是给 R3+ 会话看的「代码现在到底怎么采的」，与 R1 的「为什么该这么采」互补。

漂移检查并入 [T6](https://github.com/liumingjian/dbs-monitor/issues/24) 的「生成物入库 + 验证闭环里 diff」统一机制，不另造一套。

> **收口增补 2026-08-05：未兑现登记。** T11 尚未落地完整指标字典与采集任务，因此该附录目前不存在，也未纳入生成物清单；R3 实现指标字典时一并生成。当前不把它冒充为已有证据。

## 3. 采集计划的建模单元 = 采集任务

### 3.1 为什么不是指标

字典按指标组织（32 个 P0 指标各一张卡），但**采集不按指标发生**：

| 一次查询 | 同时产出 |
|---|---|
| `pg_stat_database` | `pg.tps`、`xact.commit_per_sec`、`xact.rollback_per_sec`、4 个 `tuples.*`、2 个 `temp.*` — 共 9 个指标 |
| `pg_stat_activity` | 连接三档、长事务两个、锁等待、阻塞会话、长查询 — 共 7 个指标 |

若载体的一等公民是指标，采集器就得为 9 个指标发 9 次同样的查询，或者在代码里偷偷去重——后者意味着「哪些指标共用一次查询」**只存在于实现里，字典管不着**，正是本票要消灭的东西。

### 3.2 双表模型

```text
Task {
  ID                如 pg.stat_database
  Kind              probe | sql | agent-derived
  SQL               一条语句（Go 常量，见 §5）
  Requires          []CapabilityID（见 §4）
  Interval          采集周期（单一，见 §6）
  Yields            行/列 → (指标 ID, 维度) 的映射
}

Metric {
  ID / 类型 / 单位 / 维度 / 计算方式（原始|差分|比率|状态映射）
  EnhancedCandidate bool   ← 展示候选资格，不是周期（见 §6.3）
  Alertable         bool
}
```

两表由指标 ID 关联。

### 3.3 恰好一次产出测试（强制）

一条测试保证：**每个字典指标恰好被一个任务产出。**

- 漏产 ⇒ 该指标永远无数据，且没人会发现；
- 重复产出 ⇒ 两个真相源。

> 该测试进 [T9](https://github.com/liumingjian/dbs-monitor/issues/27) 的强制测试清单。

### 3.4 三条随之成立的结论

1. **采样周期是任务的属性，不是指标的属性。** 同一次查询产出的指标必然同周期。字典 §7 按指标类型给的粒度建议要在任务层归并；若两个建议粒度不同的指标挤进同一任务，**取快的那个，或拆任务**。
2. **差分状态挂在任务的一次快照上。** 字典 §6 规则 2/3（reset 判定、不跨过长缺口）要求基于同一次采样的前后值；T2 已定「差分在写入侧完成、只存速率不存累计值」。任务是那个「一次快照」的自然边界。
3. **Agent 的 7 个 `host.*` 没有服务端 `Task`。** 承 [T5](05-backend-code-structure.md) §3.2（Agent 编译期固定、不读字典），它们在服务端侧只作为 `Metric` 声明存在，供告警与展示消费口径。

## 4. 前置条件 = 封闭能力枚举

字典里的前置条件目前是散文（「可读取 `pg_stat_activity`；需 `pg_monitor`」）。要驱动 ADR-10 的三态契约，它必须机器可判定——而**三态的粒度不是指标，是能力**：ADR-10 定死待办条目形如「缺少 `pg_monitor` 角色 —— 影响 6 项指标」。

### 4.1 能力声明

```text
Capability {
  ID        如 role.pg_monitor / ext.pg_stat_statements / topo.has_slot
  Class     fixable | structural     ← 决定它进不进配置缺失待办清单
  Probe     判定它的探测语句/表达式
  FixHint   可修复时的文字修复指引
  NAReason  结构性不适用时的原因文案（「本实例为主库，无 replication slot」）
}
```

`Class` **挂在能力上，不挂在指标上**：`role.pg_monitor` 恒为 `fixable`，`topo.has_slot` 恒为 `structural`。三态分类因此是**声明的**，不是每个采集点现场判断的。

### 4.2 「影响 N 项指标」是算出来的

沿 `Task.Requires` 反向索引即得。**不存在第二张映射表**，也就不会漂移。

### 4.3 能力状态是四档

`PRESENT / MISSING / NOT_APPLICABLE / UNKNOWN`

第四档来自 [T1](https://github.com/liumingjian/dbs-monitor/issues/19) D4（探测失败整轮覆写 `UNKNOWN`），也正是 ADR-10 点名的最危险的一态——**空清单看起来永远像好消息**。

### 4.4 硬纪律：不得靠查询报错反推能力缺失

权限错、网络错、语法错在错误里长得像，猜错的方向恰好是 ADR-10 禁止的「静默按具备处理」。

- **能力只由 [T1](https://github.com/liumingjian/dbs-monitor/issues/19) D4 的 5 分钟探测循环判定**；
- 采集失败就只是采集失败，不改写能力表；
- 采集编排每轮读能力表，**任一 `Requires` 不为 `PRESENT` 即不执行该任务**，并把该原因作为它全部产出指标的空状态原因（承 [T5](05-backend-code-structure.md) §7.1「12 种空状态是值不是 error」，`Unavailability` 码表定义在 OpenAPI）。

### 4.5 分层约束

[T5](05-backend-code-structure.md) 把探测循环 `capability/` 放在 **L2**，字典在 **L1** `metric/`。因此**能力枚举这个纯数据类型定义在 L1**（与字典同住），L2 的探测循环 import 它。反过来会让 L1 依赖 L2，`arch_test.go` 必炸。

## 5. 版本矩阵与采集 SQL

### 5.1 支持矩阵：PG13–17

RT-A 查明的版本差异总共两条，**且两条都卡在 PG12→13 这一刀上**：

| 差异 | 影响 |
|---|---|
| 备库列改名 `received_lsn` → `flushed_lsn` | 复制指标在 PG12 上需另一条 SQL |
| `wal_status` / `safe_wal_size` 自 PG13 起才有 | `pg.replication_slot.*` 健康字段在 PG12 上缺失 |

**决策：被监控 PG 支持矩阵定为 PG13–17，PG12 及更低版本接入即拒**（明确拒绝并说明原因，不做半支持）。

依据：PG12 已于 2024-11 停止官方支持；为一个 EOL 版本养变体机制，代价不在写那条 SQL，而在**让「版本变体」成为字典的常驻概念**——此后每张卡都要回答「我有没有版本分支」。

> 这是一条 R1 没有的**项目级约束**，会渗到 [T8](https://github.com/liumingjian/dbs-monitor/issues/26)（安装前置检查）与 R6（实例接入的拒绝流程）。

### 5.2 不建变体机制

支持矩阵切掉 PG12 后，**P0 指标在 PG13–17 内没有已知的版本差异**。因此：

1. **载体里每个 Task 只有一条 SQL，没有 `Variants` 字段。** 今天建一个零使用者的变体机制，只会让全部任务从此都要回答「我有没有版本分支」——R1 决策索引反复否决的正是这类「为想象中的未来预先冻结结构」。
2. **版本门槛不进能力枚举，进接入校验。** 它对所有任务一视同仁，做成 `Requires` 只会在每条任务上重复一遍。（`Class: structural` 仍保留，服务于拓扑类能力；P0 里只是没有版本类的实例。）

### 5.3 演化点（写给未来的会话）

**当支持矩阵首次跨越一条真实的版本差异**（例如未来纳入 PG18 且它改了某视图），才引入：

- `Task.Variants []{VersionRange, SQL}`，选择在采集编排里按实例版本进行；
- 版本类能力（`Class: structural`）加回枚举，用于「低版本根本没有该指标」的情形。

两种性质要分开处理：**同一指标不同取法** ⇒ `Variants`（指标 ID 不变，字典层看不见差异）；**低版本没有该指标** ⇒ 版本类能力 ⇒ 显示「不适用/版本不支持」，不进待办，不产生 `NO_DATA`。

**禁止的三种就地凑合**：SQL 里塞 `CASE WHEN` 做版本分支、运行时拼接动态 SQL、在 Go 里散落 `if version >= N`。

### 5.4 采集 SQL 走 pgx 直连，不走 sqlc

[T5](05-backend-code-structure.md) §4 的 sqlc + `DBTX` 结构是围绕**平台自带库**建的。采集 SQL 打的是**被监控库**——一份我们不拥有、不迁移、只读的 `pg_catalog` 统计视图。

**决策：采集 SQL 以 Go 常量声明在 `Task` 里，用 pgx 直接执行。**

| 理由 | 说明 |
|---|---|
| sqlc 需要 schema 才能校验 | 被监控库的「schema」是跨 5 个大版本的 `pg_stat_*` 视图，喂不进去；RT-D 明确把 sqlc 解析覆盖面列为无一手数据的缺口 |
| 共用 `DBTX` 会污染 T5 的不变式 | 「领域包拿到 `DBTX` 就没能力 `BeginTx`」之所以成立，是因为 `DBTX` 只指一个库；让它同时指两个库，这句话不再有确定含义 |
| 收益本就薄 | 采集查询结果就是几行数值，`pgx.Query` + `CollectRows` 够用 |

### 5.5 对价：PG13–17 集成测试矩阵（强制）

放弃生成期校验必须付对价，否则 SQL 拼写错误要到客户现场才炸。

对 **PG13、14、15、16、17 各起一个真库**，把每个 `Task` 的 SQL 实跑一遍，断言**列名、类型、行数形状**与 `Task.Yields` 的声明一致。

- 这条测试是 §5.4 成立的前提，不是可选项；
- 它比单测慢，**多半进不了 [T9](https://github.com/liumingjian/dbs-monitor/issues/27) 那条「快到每次改动都愿意跑」的闭环**，需要分层：快闭环跑单测，矩阵进 CI；
- 本地开发环境需能起 5 个 PG 版本 —— [T9](https://github.com/liumingjian/dbs-monitor/issues/27) 定「一条命令起干净环境」时要吃下这条。

T11 的 walking-skeleton 验收不包含这条矩阵。它保留为 R3 发布门槛：R3 必须在五个真实 PG 版本上执行每个采集 Task，并断言列名、类型和行数形状；T11 resolve 不把矩阵结果冒充为已完成证据。

### 5.6 连接类型不可互换

被监控库的连接与平台自带库的连接**在类型上不可互换**（如 `TargetConn` 之于 `db.DBTX`），让「把采集 SQL 误发到平台库」或反之**写不出来**。

这不算新增接缝——[T1](https://github.com/liumingjian/dbs-monitor/issues/19) D3 预留的 `pgconn.Dialer` 已在 T5 的五个白名单接缝之内。

## 6. 标准监控与增强监控：共用一条管线

### 6.1 事实基线

R1 §4.4 把「持续采集 vs 按需采集、管线共用还是独立」显式留给实现层，但钉死了体验：**页签始终可见、不设用户启停、基线为最近 30 分钟 / 5 秒粒度**。

P0 共 32 个指标，其中 27 个标 `增强监控=是`。关键是 §3 已把采集单元定为**任务**而非指标，这让高频的代价远小于直觉：

| 项 | 数值 |
|---|---|
| 服务端采集任务（探针 / `pg_stat_database` / `pg_stat_activity` / 复制 / slot / 2PC / 角色） | 约 7 条 |
| 全按 5s 跑时单实例查询压力 | 约 **1.4 次查询/秒** |
| 50 实例存储量（RT-C 口径 ~35 序列/实例、52 字节/点） | 约 **25M 点/天**，30 天约 **40 GB** |

40 GB **低于 RT-C 自定的门槛 T2**（30 天全量 > 100 GB 或 > 磁盘 30% 才需推翻存储选型）。**「全按最细粒度常采、一张表、一个保留期」这条最笨的路，在本基线下买得起。**

### 6.2 决策

1. **每个任务只有一个采集周期**，取值为其产出指标所需的最细粒度。有增强需求的任务 ⇒ 5s；纯标准任务（`agent.status`、磁盘剩余、2PC、复制角色）保持 30–60s；字典 §7 里 5m 那类保持 5m。
2. **不建第二套高频管线、不分层保留、不降采样、不双写。**
3. **标准 vs 增强的区分只在展示层**：增强页读原始点，标准页由后端 `date_bin` 聚合上去——正是 T2 已定的「图表粒度由后端算并回传」。**采集层完全不知道有这两个页签存在。**

### 6.3 `增强监控=是` 的含义钉死

它是**展示候选资格**（`Metric.EnhancedCandidate`），**不等于采集周期**。周期是 `Task.Interval` 这个独立字段。

两者从此不互相绑架：§2.1 的一致性测试比对的是候选资格，改周期不会让它红。

### 6.4 采样周期可调与护栏

采样周期归平台管理员可调（IA §4.8「采集配置」），调的是**任务的周期**，**下限 5s**。

### 6.5 被否决的两条

| 方案 | 否决理由 |
|---|---|
| 按需驻留（打开增强页才起高频，到期自动停） | 恰好在你需要复盘刚才那 5 分钟时没有历史，而那正是增强监控存在的理由；且 R1 已排除用户启停 |
| 两套管线 / 两级保留（5s 短保留 + 标准长保留） | 现在就为一个未被实测证实的容量问题付结构复杂度（第二张表、双写、跨表查询路由），正是 T2 立的规矩反对的 |

### 6.6 代价

约 40 GB 里有相当一部分是「30 天前的 5 秒粒度数据，没人会看」。**这是拿磁盘换结构简单**，且换来的简单是真的：没有第二张表、没有双写、没有跨表查询路由。

若 [T11](https://github.com/liumingjian/dbs-monitor/issues/29) 实测击穿 RT-C 门槛，按 [T10](https://github.com/liumingjian/dbs-monitor/issues/28) 第 6 点回改——**那时才引入保留分层**。

> **交给 T11**：存储基线由 15M 点/天修正为 **~25M 点/天、30 天 ~40 GB**。
> **交给 [T12](https://github.com/liumingjian/dbs-monitor/issues/30)**：「50 实例 × 约 7 任务 × 5s」是并发与限流模型的输入基线。

## 7. Agent 采集计划的下发内容

[T3](https://github.com/liumingjian/dbs-monitor/issues/21) 已定「无下行通道，采集计划经 push 响应体捎带」；[T5](05-backend-code-structure.md) §3.2 已定 Agent 指标集编译期固定、不读字典。两条一夹，留给「计划」的空间极小——但要显式收口，否则后续会话会顺手往那个响应体里塞东西。

### 7.1 决策：只有 `report_interval_sec`

| 候选字段 | 结论 | 理由 |
|---|---|---|
| 采哪些指标 | **不下发** | Agent 指标集编译期固定，服务端说了不算；下发一份 Agent 无法执行的清单只会造出第二个真相源 |
| 暂停开关 | **不下发** | 见 §7.2 |
| `report_interval_sec` | **下发** | T3 定死「上报周期强制 ≤ 评估周期」，而评估周期只有服务端知道 |

### 7.2 暂停是纯服务端语义，Agent 全程不知情

直觉上暂停采集该告诉 Agent 别推了。**但 T3 定了「心跳即 push 本身」——Agent 一停推，暂停在数据上就退化成 Agent 离线**，而 R1 要求暂停期间不转 `RECOVERED`、不产生告警，离线则要产生。

因此：

- Agent 照常 push，服务端收下心跳（`agent.status` 保持 `online`）；
- 服务端**不写样本、不评估**；
- 「暂停」与「离线」在数据上永远可区分。

### 7.3 服务端直连侧没有「下发」

计划就在服务端进程内，从编译期字典（§1）+ 库里的周期配置（§1.3）读出即可。

### 7.4 扩展路径

将来真要加字段，走 OpenAPI 加字段 + T3 的「服务端先升、Agent 后升、向后兼容一个大版本」，**不另开通道**。

## 8. 可扩展性边界

「用户不能自定义指标」这句话拦不住后续会话顺手做进去，因为它不知道界线在哪。三条线写死：

### 8.1 不可扩展（只能发版）

新增指标、修改指标口径、修改任何采集 SQL、新增采集任务。

理由不只是范围——**它会把 §1 整个翻过来**：可自定义就必须有外置载体、DSL、校验器、版本化迁移，本文档 §1–§5 的结论全部不成立。

### 8.2 可配置的，且只有这三项

严格等于 IA §4.8「采集配置」模块的内容，**仅平台管理员可写**：

1. 任务采样周期（下限 5s）
2. 暂停 / 恢复采集
3. 是否启用 Agent 指标

> 告警规则与阈值由用户配置是 R1 已定的独立能力，不属于「自定义指标」，不受本节约束。

### 8.3 单独禁死：用户自定义 SQL 探针

这条不只是范围问题，是**安全问题**：监控账号持 `pg_monitor`，字典 §1.4 明确基线不含业务表读取；允许用户填任意 SQL 等于把这份权限出借给任意语句，且平台无法保证它不拖垮被监控库。

**哪怕将来做自定义指标，这条也应单独再决策。**

### 8.4 落地方式

§8.1–§8.3 三条线点名交给 [T9](https://github.com/liumingjian/dbs-monitor/issues/27) 写入 `CLAUDE.md` 的禁止清单。**「不能做」的约束只有出现在会话每次都读的地方才有效**，埋在设计文档第 8 节等于不存在。

## 10. 否决记录

| 方案 | 否决理由 |
|---|---|
| 字典外置为 YAML / JSON 随包分发 | 口径半装的是代码；必然长出 mini-DSL 与解释器，把编译期错误变成运行期错误（§1.1） |
| 字典整体入库可编辑 | 唯一好处（不发版就能改）没有消费者；换来升级合并、漂移、校验三份代价（§1.1、§8.1） |
| R1 字典文档整篇由载体生成 | 文档一半字段是写给人看的理由，生成器写不出来；会把冻结的规格降级成一张贫瘠的表（§2） |
| 载体是文档的副本，靠人工同步 | 在几十个会话的规模下等于没有同步（§2.1） |
| 指标为采集的一等公民，共用查询由采集器自行去重 | 「哪些指标共用一次查询」只存在于实现里，字典管不着（§3.1） |
| 前置条件留作任务内的自由谓词 | 三态的粒度是能力不是指标；「影响 N 项指标」将退化为第二张手工维护的映射表（§4.1、§4.2） |
| 采集器靠查询报错反推能力缺失 | 猜错的方向恰好是 ADR-10 禁止的「静默按具备处理」（§4.4） |
| 现在就建 `Task.Variants` 版本变体机制 | P0 零个使用者；会让每张卡从此都要回答「我有没有版本分支」（§5.2） |
| SQL 内 `CASE WHEN` / 动态拼接 / 散落 `if version >= N` | 生成期与测试期都查不出来，是版本适配最容易写歪的三种形态（§5.3） |
| 采集 SQL 也走 sqlc | 被监控库的 schema 喂不进 sqlc；共用 `DBTX` 会让 T5 的「领域包无能力开事务」失去确定含义（§5.4） |
| 增强监控按需驻留 | 恰好在需要复盘时没有历史；R1 已排除用户启停（§6.5） |
| 高频短保留 + 标准长保留两级分层 | 为未经实测证实的容量问题预付结构复杂度（§6.5） |
| 向 Agent 下发暂停开关 | Agent 停推会让「暂停」在数据上退化成「离线」，两者语义相反（§7.2） |
| 开放用户自定义 SQL 探针 | 等于把 `pg_monitor` 权限出借给任意语句（§8.3） |
