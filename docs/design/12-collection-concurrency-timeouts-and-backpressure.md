# 采集并发、超时与背压模型 v1.0

> 目标：在 50 个实例、每实例约 7 个服务端采集任务、任务周期最低 5 秒的基线下，定死服务端直连采集的调度、连接、超时、背压、退避、能力探测份额与自观测边界。
> 决策票：[T12 · 采集并发限流、超时与背压](https://github.com/liumingjian/dbs-monitor/issues/30)。
> 输入边界：[T1 · 系统组件拓扑与两条采集通路的职责边界](https://github.com/liumingjian/dbs-monitor/issues/19)（PG 指标一律服务端直连；探针每周期新建连接）、[T2 · 时序存储选型与指标数据模型](04-metric-storage-model.md)（每实例事务、采集状态与样本同一真相源）、[T4 · 指标字典的机器可读载体与采集计划](06-metric-dictionary-and-collection-plan.md)（任务是一等公民、最低周期 5 秒、能力探测独立）、[T5 · 后端代码结构与模块边界](05-backend-code-structure.md)（`pgconn.Dialer` 是唯一采集连接接缝）、[T6 · API 契约组织与代码生成流水线](07-api-contract-and-codegen.md)（封闭 `Unavailability` 码表）。
> 状态：v1.0。后续路线要推翻其中任何一条，应新开决策记录，不在此原地改写结论。

## 0. 一句话结论

**中央调度器按 `(instance, task)` 调度并确定性错峰；探针与普通查询各有独立执行通道，普通查询每实例复用一条连接，探针每次新建连接；所有执行有硬期限，过载只保留最新到期意图、不排队补历史；探针永不退避，普通任务显式指数退避；能力探测有保留份额且按实例原子覆写；每任务状态持久化，来源新鲜度取“全部当前义务均满足”的完整性水位。**

这套模型只承诺两件事：健康时买得起地图给定的采样频率；不健康时，每一次自我保护都留下可解释的事实。它不承诺在目标库持续缓慢或平台资源不足时仍无损采集。

## 1. 术语与调度单位

### 1.1 `TaskRun`，不是“全平台一轮”

`TaskRun` 是一个采集任务对一个实例在某个到期时间产生的一次执行义务：

```text
TaskRun = (instance_id, task_id, due_at)
```

50 个实例不组成一个同步屏障，也不存在“第 N 轮必须等全部实例结束”。每个 `TaskRun` 独立准入、独立超时、独立记录结果。一个实例失败不得让其余 49 个实例的调度停下。

样本时间取实际观测时间，不伪装成 `due_at`。未执行的 `TaskRun` 不写 0、`null` 或占位时间点；`null` 已被 [T6 · API 契约组织与代码生成流水线](07-api-contract-and-codegen.md) 保留给“采到了但不可计算”，不能拿来表达调度器没运行。

### 1.2 三类工作

| 类别 | 内容 | 调度性质 |
|---|---|---|
| 可用性探针 | 新建连接、认证、`SELECT 1` | 关键周期任务；独立执行槽，永不退避 |
| 普通查询 | 指标字典中的 SQL Task | 每实例串行；失败可退避 |
| 能力探测 | 5 分钟能力快照 | 与普通查询共享实例连接槽，但有全局保留份额 |

Agent push 不进入本模型。它由 Agent 自己的上报周期与服务端 HTTP 准入约束，不能与服务端直连查询共用一个“采集 worker 数”。

## 2. D1 · 中央调度 + 每实例双执行槽

### 2.1 并发骨架

采用中央到期调度器，不为每个实例建立一个永久调度 goroutine，也不按实例静态分片。

每实例最多同时存在：

1. 一个可用性探针；
2. 一个非探针数据库操作（普通查询或能力探测）。

因此一个慢普通查询不能阻塞同实例的可用性探针；同实例的普通任务彼此串行，不会由监控系统自己制造连接尖峰。MVP 不设“每主机”上限：配置中的 host/address 不是可靠的物理主机身份，同一地址可能是代理或集群入口，实例才是平台拥有的稳定资源边界。

### 2.2 公平与错峰

同一优先级按实例公平轮转，不能让一个高频实例占满全部准入机会。初始相位由 `(instance_id, task_id)` 稳定散列到任务周期内：

- 重启后相位稳定，避免每次启动重新制造随机尖峰；
- 5 秒边界不会同时唤醒 50 个实例；
- 调整全局并发上限不改变任何任务的采样周期。

### 2.3 全局默认上限

| 通道 | 默认 | 可调范围 | 配置位置 |
|---|---:|---:|---|
| 可用性探针 | 32 | 1–50 | 部署期配置，重启生效 |
| 非探针数据库操作 | 32 | 1–50 | 部署期配置，重启生效 |

这两个值不进入 UI。它们是平台进程的资源边界，不是产品采集计划；UI 只配置 [T4 · 指标字典的机器可读载体与采集计划](06-metric-dictionary-and-collection-plan.md) 已授权的任务周期。

**探针 32 的推导**：50 实例、5 秒周期、单次最坏 3 秒，稳态所需并发约为 `50 / 5 × 3 = 30`。取 32，使全部地址都表现为网络黑洞时仍能维持周期语义。

**普通查询 32 的推导**：全任务均为 5 秒的上界约 60 次查询/秒；平均耗时 500ms 时所需并发约 30。超过这个延迟后，系统应进入本票定义的显式背压，而不是无限放大目标库连接数。

## 3. D2 · 探针与普通查询是双连接生命周期

### 3.1 可用性探针

探针每次绕过连接池，完成以下完整过程后立即关闭物理连接：

```text
connect -> authenticate -> SELECT 1 -> close
```

这不是可优化掉的开销。ADR-02 M2 对 `reachable=true` 的定义就是“新客户端此刻能连上”；复用池连接会掩盖 `max_connections` 耗尽、认证配置回归和新连接 TLS 失败。

### 3.2 普通查询

每实例维护一个懒创建的目标库连接池：

```text
MinConns = 0
MaxConns = 1
application_name = dbs-monitor
```

连接跨普通任务复用。实例地址、数据库名、用户名或凭据版本变化时，旧池失效并排空；下一次任务按新配置重建。探针与普通池共享同一凭据来源和既有 `pgconn.Dialer` 接缝，不新增第六个架构接缝。

固定 `application_name` 是 ADR-02 M4 的前提：`pg.connection.total` 计入监控连接以便与 `max_connections` 对账，active / 长事务 / 锁等待等异常信号则排除监控自身后端。

### 3.3 “双事实”是刻意保留的语义

当 `max_connections` 耗尽或认证配置刚刚回归时，可能同时出现：

- 新探针失败，`reachable=false`；
- 已建立的普通池连接仍能采到有效指标。

两个事实都必须保留。探针失败不关闭仍可用的普通连接，也不丢弃其样本；普通查询成功也不能把探针结果改回 true。`reachable` 不是“监控系统手里是否碰巧还有一条可用旧连接”，更不是“数据库整体健康”。

## 4. D3 · 超时层级与故障隔离

### 4.1 不设全平台整轮超时

全平台没有同步“整轮”，故没有一个能把 50 个实例一起取消的 round deadline。期限只落在一次 `TaskRun` 及它内部的目标库阶段。

### 4.2 默认期限

| 工作 | 期限 | 结果语义 |
|---|---|---|
| 可用性探针 | 目标库阶段总计 3 秒；建连与认证最多 2 秒，`SELECT 1` 使用剩余时间 | 失败或超时写 `reachable=false`，公开原因为 `DB_UNREACHABLE` |
| 普通任务 | `min(task.interval × 80%, 10s)`；5 秒任务即 4 秒 | 不写样本，公开原因为 `COLLECTION_FAILED`，控制面保留 timeout 细因 |
| 能力快照 | 每实例整份快照 10 秒 | 失败时提交整份 `UNKNOWN` 快照；平台库写失败时由快照新鲜度投影为 `UNKNOWN` |

普通任务期限覆盖连接池获取、必要时建连、查询与结果读取。客户端 context deadline 与 PostgreSQL `statement_timeout` 同时设置：前者保证 worker 归还，后者保证取消包丢失时目标库也会自行终止 SQL。超时后的连接状态若不确定，直接从池中淘汰。

目标库结果持久化仍遵守 [T2 · 时序存储选型与指标数据模型](04-metric-storage-model.md) 的平台库事务边界。平台库写失败不能倒因为 `DB_UNREACHABLE`；它是平台自身故障，样本与采集状态同事务回滚。

### 4.3 错误分类边界

- 探针的建连、认证或 `SELECT 1` 未在期限内完成：`DB_UNREACHABLE`；
- 普通查询超时、SQL 执行失败或结果解码失败：`COLLECTION_FAILED`；
- 调度器未执行探针：不是 false，而是缺数 + `COLLECTION_FAILED`；
- 查询错误不得反推能力缺失。能力只由独立探测循环写入，继续遵守 [T4 · 指标字典的机器可读载体与采集计划](06-metric-dictionary-and-collection-plan.md) §4.4。

`Unavailability` 码表不新增“超时”码。[T6 · API 契约组织与代码生成流水线](07-api-contract-and-codegen.md) 已定 `COLLECTION_FAILED` 包含执行失败与超时，具体原因文本属于控制面。

## 5. D4 · 背压只保留最新到期意图

### 5.1 latest-only 合并

每个 `(instance, task)` 最多有一个执行中项和一个待执行意图，不建立历史 FIFO：

1. 到期时若可以准入，立即执行；
2. 若暂不能准入，保留一个最新待执行意图；
3. 新周期再次到达时，旧待执行意图过期，以最新 `due_at` 替换并记录 `SKIPPED_BACKPRESSURE`；
4. 若旧任务仍在执行，新周期同样只形成一个最新待执行意图，不允许同任务重叠。

过期采集即使以后补跑，得到的也是“现在”的值，伪装不成过去的观测。排历史队列只会在恢复后制造查询洪峰，并生成时间语义错误的数据。

### 5.2 三条禁止

1. **不补跑**：故障恢复后只运行最新意图；
2. **不自动降频**：调度器不得把管理员配置的 5 秒暗改成 30 秒；
3. **不造占位样本**：跳过不写 0、`null`、旧值或未来时间戳。

### 5.3 与 `NO_DATA` 的关系

被跳过的 `TaskRun` 是一次明确的缺数，不是目标数据库失败：

- 不更新任务成功时间，也不推进采集源完整性水位；
- 评估循环仍是唯一状态迁移者；连续两个评估周期缺数后照常进入 `NO_DATA`；
- 公开原因为 `COLLECTION_FAILED`，任务控制面细因为 `SKIPPED_BACKPRESSURE`；
- 被跳过的探针不得写 `reachable=false`，否则会把平台过载伪装成数据库不可达。

## 6. D5 · 探针永不退避，普通任务显式退避

### 6.1 目标库查询不做同周期立即重试

普通任务失败后不在同一个 `TaskRun` 内重新执行目标 SQL。连续两周期才进入 `NO_DATA` 已经提供瞬时故障容忍；立即重试会在数据库最脆弱时主动放大压力。

[T2 · 时序存储选型与指标数据模型](04-metric-storage-model.md) 的“缺分区后修复并重试一次”不受影响。那是平台库持久化的确定性修复，不是对目标数据库查询的重试。

### 6.2 退避规则

普通任务连续失败后的下次资格间隔为：

```text
1 × interval, 2 × interval, 4 × interval, ... , capped at 60s
```

- 连接或传输层失败：同实例全部普通任务共享连接级退避；
- SQL、解码或查询超时：只退避对应任务；
- 探针成功：立即清除该实例连接级退避，调度最新普通任务；
- 普通任务成功：清除自己的任务级退避；
- 退避期间每个到期义务仍记录为缺数，细因为 `BACKOFF`。

探针永不退避，持续不可达时仍按配置周期新建连接。否则 `reachable` 会从“此刻能否连上”退化成“最多 60 秒前能否连上”，直接改变 ADR-02 M2 的产品语义。

退避不是采样周期的新配置值：UI 仍显示管理员配置的原周期，控制面同时明确显示系统因连续失败而保护性退避。

## 7. D6 · 能力探测有保留份额，按实例原子覆写

能力探测与普通任务共享每实例 `MaxConns=1` 的查询池，不建立第三条目标库连接。全局非探针并发仍不超过 32：

- 有能力探测等待时，为它保留 `min(4, 非探针并发上限)` 个槽；默认配置下普通任务最多占 28 个；
- 没有能力探测等待时，普通任务可借用全部 32 个槽；
- 同实例当前任务结束后，到期的能力探测优先于新的普通任务，避免被 5 秒任务永久饿死；
- 50 个实例的 5 分钟能力周期同样确定性错峰。

4 个保留槽即使每个实例都耗满 10 秒，也约 125 秒即可覆盖 50 个实例，低于 5 分钟周期。

每实例能力探测是一份带 `observed_at` 的原子快照。整组探测全部成功才提交 `PRESENT / MISSING / NOT_APPLICABLE`；任一查询、超时或调度失败，都构造并提交该实例整份 `UNKNOWN` 快照及原因。

平台库事务失败时，系统不可能假装成功写入 `UNKNOWN`：本轮不提交任何半份快照，读取侧必须把超过 5 分钟有效期的旧快照投影为 `UNKNOWN`。因此旧 `PRESENT` 永远不能越过自己的 `observed_at` 冒充当前结果。普通采集错误仍不得替代能力探测。

## 8. D7 · 每任务状态与采集源完整性水位

### 8.1 为什么“任一任务成功”会说谎

[T2 · 时序存储选型与指标数据模型](04-metric-storage-model.md) 的 `instance_collect_state` 是每实例、每采集源一行；[T4 · 指标字典的机器可读载体与采集计划](06-metric-dictionary-and-collection-plan.md) 又让同一来源下的任务拥有独立周期。若健康探针每 5 秒成功就刷新来源 `last_success_at`，持续失败的 `pg_stat_activity` 任务会被永久掩盖，“数据过期”内置规则永远不触发。

### 8.2 持久化任务事实

控制面须持久化每个 `(instance_id, task_id)` 的至少以下事实：

- 最近到期、开始、结束与成功时间；
- 最近结果：`SUCCESS / FAILED / TIMED_OUT / SKIPPED_BACKPRESSURE / BACKOFF`；
- 连续失败次数与 `next_eligible_at`；
- 脱敏的错误 code/message。

进程重启不能把连续失败、退避或最近一次跳过洗掉。具体表名与 sqlc 查询属实现细节，但以上事实及唯一键不是可选项。

### 8.3 完整性水位

`collector.last_success_time` 精确定义为**采集源完整性水位**：只有该来源全部已启用且当前适用的任务，都成功满足了各自最近一次到期义务，水位才向前推进。

- 长周期任务尚未再次到期时，上次成功仍满足当前义务；
- 失败、超时、背压跳过或退避使该任务义务未满足，其他任务成功不能冲掉；
- 结构性不适用的任务不参与水位；
- `MISSING` 或 `UNKNOWN` 不是结构性不适用，受影响任务的当前义务仍未满足；
- 暂停实例直接投影为 `COLLECTION_PAUSED`，暂停空窗不产生 `NO_DATA`；
- 故障恢复后不补历史；全部当前义务重新满足时，水位恢复推进。

样本、任务成功状态和来源水位仍须遵守 [T2 · 时序存储选型与指标数据模型](04-metric-storage-model.md) 的事务不变式：只有有效样本成功提交，相关成功事实才可推进。

## 9. D8 · 自观测边界

### 9.1 当前票必须产出的运行事实

**持久化控制面**：D7 的每任务状态，供后续采集管理页展示最近结果、失败数、退避与受影响任务。

**状态变化事件**：任务从成功转为失败/超时/背压/退避及恢复时立即写结构化日志。日志可包含实例 ID、任务 ID、结果、耗时和错误码，严禁包含 DSN、用户名、密码、令牌或可还原凭据的错误文本。

**每 60 秒结构化汇总**：

- 探针与非探针的 capacity / active / pending；
- 调度延迟；
- success / failed / timeout / skipped_backpressure / backoff 计数；
- 按有限任务 ID 聚合的耗时分布；
- 连接池 active / idle / rebuild 汇总。

实例 ID 只进入状态变化日志和持久化控制面，不作为聚合统计的高基数标签。

### 9.2 明确不做

采集器自身运行事实不写入 `metric_sample`，不复用目标数据库的 `NO_DATA` 状态机，也不在本票新增用户可配置的平台自身告警。否则采集器会经自己负责的链路递归监控自己，平台库故障时仍可能把“观测通道坏了”表现成“没有问题”。

systemd journal 是 R2 已有的最低诊断出口。诊断 API、Prometheus 文本出口、平台自身告警、日志/指标保留与运行期磁盘水位保护，已成为独立决策问题，交给新路线票“平台自身运行可观测性与诊断出口”。

## 10. 关键场景验算

### 10.1 50 个实例全部地址黑洞

- 32 个探针槽按确定性相位持续执行，单次最多 3 秒；
- 普通任务进入连接级失败退避，最多 60 秒，避免约 300 个任务持续建连；
- 探针继续产生 `reachable=false`，普通指标按缺数进入 `NO_DATA`；
- 一个实例的超时不会取消其他实例。

### 10.2 `max_connections` 耗尽，但旧连接仍在

- 新探针失败，`reachable=false`；
- 旧普通池连接若仍可查询，样本继续提交；
- 两条事实分别进入各自序列/状态，不互相覆盖。

### 10.3 平台自身过载，探针没被调度

- 不写 `reachable=false`；
- 记录 `SKIPPED_BACKPRESSURE` 与缺数；
- 来源完整性水位停止推进，连续缺数按既有规则进入 `NO_DATA`；
- 周期不被暗改，恢复后只执行最新意图。

### 10.4 一个 SQL 长期超时

- 每次执行受 `min(80% interval, 10s)` 限制，并由数据库端 `statement_timeout` 兜底；
- 只退避该任务，其他普通任务和探针继续；
- 该任务未满足义务，来源完整性水位不能被其他成功任务推进。

### 10.5 能力探测部分成功

- 不提交部分 `PRESENT`；
- 整份当前快照覆写为 `UNKNOWN`；
- 若平台库事务失败，旧快照过期后由读取侧投影为 `UNKNOWN`；
- 依赖这些能力的任务不得靠普通查询错误猜状态。

---

## 11. 实现守卫

下游实现至少要用自动化测试锁住以下性质：

1. 同实例普通任务绝不重叠，探针可与普通任务并行；
2. 全局准入不超过配置上限，能力探测等待时能拿到 `min(4, 非探针并发上限)` 个保留槽；
3. 初始相位稳定且分散；
4. 一个实例超时不阻塞其他实例；
5. `TaskRun` 到期合并只保留最新意图，且每次跳过都有持久化结果；
6. 探针跳过不产生 `reachable=false`；
7. 普通任务退避封顶 60 秒，探针永不退避；
8. 查询 timeout 同时取消客户端等待并终止服务端 SQL；
9. 能力快照部分失败时整份 `UNKNOWN`，旧快照过期时也只能读成 `UNKNOWN`；
10. 任一当前任务未满足时，其他任务成功不能推进来源完整性水位；
11. 暂停空窗不产生 `NO_DATA`；
12. 日志字段不会包含凭据或完整连接串。

这些测试属于 R3 采集实现，不要求回改 walking skeleton。现有 `internal/collect.Service` 的串行 `RunOnce` 是 [T11 · Walking skeleton 实现](https://github.com/liumingjian/dbs-monitor/issues/29) 刻意保留的薄实现，不是本决策的并发先例。

## 12. 否决记录

| 被否决 | 为什么 |
|---|---|
| 每实例永久 goroutine | 把调度、连接生命周期和实例数绑死，仍需另造全局准入与公平层 |
| 按 host 限流 | host/address 不是可靠的物理资源身份，会对代理、集群入口和同机多实例做出错误归并 |
| 探针与普通查询共用一个实例槽 | 一个慢查询会阻止“新客户端此刻能否连接”的关键事实按周期产生 |
| 探针走普通连接池 | 掩盖连接耗尽和认证回归，直接破坏 ADR-02 M2 |
| 普通任务每次新建连接 | 在 50 实例 × 约 6 普通任务的基线下制造无价值的认证与 TLS 压力 |
| 全平台同步轮次 | 一个慢实例拖住其余 49 个，失败域扩大到全平台 |
| 无界 FIFO / 故障后补跑 | 过去的瞬时值补不回来；恢复时只会制造查询洪峰和错误时间语义 |
| 自动降频 | 管理员配置与实际行为分裂，`NO_DATA` 门槛失去可解释性 |
| 跳过时写 0、`null` 或旧值 | 分别伪造真实 0、混淆“采到但不可计算”、掩盖缺数 |
| 普通任务立即重试 | 数据库最脆弱时放大压力；既有连续两周期门槛已提供瞬时容错 |
| 探针指数退避 | 把“此刻”退化成“上一回尝试时”，改变指标定义 |
| 能力探测与普通任务同优先级竞争 | 高频普通任务可使唯一能力事实源永久饥饿 |
| 能力快照部分提交 | 让同一时刻的能力清单混入两轮事实，空清单再次看起来像好消息 |
| 任一任务成功就刷新来源时间 | 健康高频任务会永久掩盖另一个持续失败任务 |
| 采集器自观测写回 `metric_sample` | 经被观测链路递归观测自己，平台故障时无法区分“没问题”与“看不见” |
