# Walking Skeleton 切片定义与验收标准 v1.0

> 目标：把地图 Destination 的一句话「一条真实指标能从采集穿到前端图表」变成**可执行、可验收、边界封闭**的定义——切哪一刀、切多深、凭什么算通过、一律不做什么、以及实测推翻选型时怎么办。
> 适用范围：[T11 · Walking skeleton 实现](https://github.com/liumingjian/dbs-monitor/issues/29) 的全部工作。
> 决策票：[T10 · Walking skeleton 切片定义与验收标准](https://github.com/liumingjian/dbs-monitor/issues/28)。
> 输入边界（不重议）：[T1 · 系统组件拓扑](https://github.com/liumingjian/dbs-monitor/issues/19)（PG 指标一律服务端直连、Agent 只采 OS + 心跳；评估独立循环错相位）、[T2 · 时序存储与数据模型](04-metric-storage-model.md)（窄表 + 按天分区、每实例一事务）、[T3 · Agent 上报协议](https://github.com/liumingjian/dbs-monitor/issues/21)（单端点、强制 TLS、令牌只写、±30s 时钟窗口）、[T4 · 指标字典与采集计划](06-metric-dictionary-and-collection-plan.md)（任务是一等公民、不得靠报错反推能力）、[T5 · 后端代码结构](05-backend-code-structure.md)（四层偏序、接缝白名单封闭为五个）、[T6 · API 契约与代码生成](07-api-contract-and-codegen.md)（双 schema、`x-required-role`、绝对时间、封闭 13 码）、[T7 · 前端技术栈](08-frontend-stack-and-ui.md)（AntD 6 + ECharts 6 + TanStack Router、三个状态桶）、[T8 · 打包与部署](09-packaging-and-deployment.md)（离线 tar、自带 PG 17、首启三项输入）、[T9 · AI 开发护栏](10-ai-guardrails-and-verification.md)（两层闭环、`make check` 全绿即完成、切片下限）。
> 状态：v1.0。后续路线要推翻其中任何一条，应新开决策记录，不在此原地改写结论。
> **本票只产切片定义。** 实现全部在 T11。

## 0. 一句话结论

**两条采集通路都走通（Agent 侧砍到最薄）；告警进骨架但只进一条硬编码规则、循环与事务边界为真；前端两级路由 + `validateSearch` + 一张经领域组件渲染的 ECharts 图；登录与鉴权进骨架；凭据明文存库并记为 R3 欠账；分区机制进骨架；端到端验收是快层的一条 Go 集成测试；九条禁止清单封闭范围；实测推翻选型按「决策票有没有预授权」二分，需要自己想替代方案就停下开新票。**

贯穿全票的取向：**骨架是选型的验证手段，不是提前开工 R3。** 判断某样东西该不该进骨架，唯一的判据是——

> **它是不是「只有跑起来才能被证伪」的东西？** 是，就进；能靠推演得出结论的，一律推到 R3。

## 1. D1 · 两条采集通路都走通，Agent 侧砍到最薄

**结论**：骨架同时走通**服务端直连**与 **Agent push** 两条通路。Agent 侧只做「必须靠运行才能证伪」的部分。

| Agent 侧 | 进骨架 | 理由 |
|---|---|---|
| 强制 TLS + 自签 CA、无跳过开关 | ✅ | 「无跳过开关」是 T3 的硬约束，装不上就是选型不成立，只能实测 |
| 令牌鉴权（随实例签发、只存哈希、只写不读） | ✅ | 鉴权自洽性只能实测 |
| 时间戳 ±30s 窗口拒收 | ✅ | 同上；且它与 `NO_DATA` 门槛共用时间轴 |
| 内存 5 分钟补报缓冲 | ❌ → R3 | 逻辑可推演，不跑也知道能不能成立 |
| 版本兼容协商（容一个大版本差） | ❌ → R3 | 同上 |
| 平台自分发 Agent 的安装流程（[T8](09-packaging-and-deployment.md)） | ❌ → R3 | 同上；T11 里手工拷二进制 |

**理由**

1. 地图 Notes 第 4 条把「无 Agent 实例」定为**一等场景**，原话是骨架「从第一天起支持两条通路」。只走一条 = 直接违反地图约束。
2. 两条通路里**结构性风险更高的是 Agent 那条**（跨主机、TLS、鉴权、时钟）。把它留到 R3 才第一次运行，与「纸面选型未经运行验证只是偏好」这条本路线的立论矛盾。
3. 但 T3 里真正需要运行才能证伪的只有上表前三项，其余是逻辑题。砍掉它们不损失验证价值，Agent 侧的增量收敛到「一个二进制 + 一次 HTTP POST」。

**代价**：T8 的「Agent 由平台自分发」这条决策在 R2 内不被实测，进禁止清单第 4 条与 R3 欠账。

## 2. D2 · 告警进骨架：一条规则，循环与事务边界为真

**结论**

| 做真的 | 不做（→ R4） |
|---|---|
| 一条**硬编码**阈值规则（对 `pg.connection.total`），`consecutive_count` 判定 | 规则 CRUD |
| 状态走通 `OK → PENDING → FIRING → RECOVERED` 与 `NO_DATA` | 规则版本快照 |
| **独立评估循环、与采集同频错相位**（[T1](https://github.com/liumingjian/dbs-monitor/issues/19)） | 通知渠道（**连 `notify.Channel` 接缝都不摆**） |
| **读样本与写告警状态同事务**（[T2](04-metric-storage-model.md) 不变式） | 告警处置、触发现场快照、压制 |
| 前端只在实例详情显示**当前告警状态一个字段** | 告警页 |

**理由**

1. 地图 Notes 否决 Prometheus 全家桶的**首要理由**就是「无一等 `NO_DATA`、无滞回恢复、停抓即自动 resolve」。这是本路线最贵的一条选型判断，**只能靠运行证伪**。不进骨架，它就永远是纸面。
2. T2 定死「读样本与写告警状态同事务 ⇒ 假 `NO_DATA` 结构上不可能」。骨架里没有告警状态写入，**这条不变式就没有产地**。
3. T1 定死「评估循环与采集同频**错相位**」（因 `NO_DATA` 是事件的缺席，推不动）。错相位是只有跑起来才会暴露竞态的设计。
4. 成本可控：T5 已保证状态机是**无时间纯函数**（R1 只有 `consecutive_count`、无 `for_duration`），单测便宜；真正需要骨架的只有循环与事务边界。

**滞回恢复（`RECOVERED`）明确进骨架**，代价是验收里要再造一次「越线又回落」的数据。理由：「停抓即自动 resolve 是规格禁止的假恢复」这句话不跑一次就永远是纸面。

## 3. D3 · 前端切片：两级路由 + 一张图 + 全 13 码空状态壳

**结论 · 做真的**

1. **两级路由**：`/instances`（列表）→ `/instances/$id`（详情）。时间范围 `?from=&to=` 走 `validateSearch`，**绝对 RFC3339**（[T6 D7](07-api-contract-and-codegen.md)）。
   > 这满足 [T9 §5.1](10-ai-guardrails-and-verification.md) 回写的**切片下限**（至少两级路由 + 一个 `validateSearch`），也是 T7 置信度最低那一票（TanStack Router）的先例产地。
2. **一张 ECharts 折线图**（`pg.connection.total`），**只能经 `unavailability` 必填的领域组件渲染**——T7「画了图却没处理空状态 = 编译错误」的唯一产地。不装 `echarts-for-react`。
3. **空状态壳覆盖全部 13 码**，逻辑只有一个 `switch` + `assertNever`，成本几乎全在文案表。
4. **AntD 6 布局 + 一张表格**。
5. **`openapi-react-query` + 轮询 + `dataUpdatedAt` 新鲜度判定**（T7 前端必测第三项）。

**后端在骨架里只真实产出 3 码**：`NO_SAMPLES_YET`、`NO_DATA_IN_RANGE`、`DB_UNREACHABLE`。其余 10 码由前端表驱动单测覆盖，不要求后端能造出来。

**理由**

- **全 13 码为什么不算加厚**：[T9 §3.4](10-ai-guardrails-and-verification.md) 把强制测试清单写成「**有对应项而无测试 = 未完成**」的登记表，而这一项的对应代码（那个组件）在骨架里就已经存在了。
- **AntD 为什么必须进**：T7 说 AntD 的**唯一推翻条件是实测交互卡顿**，T8 关心 `go:embed` 后体积——骨架是这两个数字**唯一的**测量点。不进骨架，那条推翻条件永远不会被执行。

**不做**：告警页、采集管理页、配置缺失待办页、实例接入向导、用户与角色页；三套状态词汇只用到「告警状态」一套，另两套不摆；视觉打磨、响应式、暗色。

## 4. D4 · 登录与鉴权进骨架，后端做真的、前端做最薄

**结论 · 做真的**

1. 会话 cookie + `SameSite=Strict`，同源（[T6 D10](07-api-contract-and-codegen.md) 否决 JWT，理由是吊销做不到）；
2. spec 上 `x-required-role` 声明 + **`operationId` 全覆盖测试**（[T9](10-ai-guardrails-and-verification.md) B 栏守卫的产地，作用是「把默认从放行翻成拒绝」）；
3. 首启随机生成管理员口令、**打印一次**（[T8](09-packaging-and-deployment.md)）；
4. 前端一个最简登录页 + **401 的全局处理**。

**不做**：用户 CRUD、角色切换、改密、找回密码。库里只种一个 `admin`。但 `x-required-role` 的**声明**必须写全每个端点——声明是纸面成本，漏写才是隐患。

**理由**（决定性的是第 4 条，不是第 2 条）

- **401 的处理路径不进骨架，前端所有页面要到 R3 才第一次遇到未认证态**。那是全局的、会触发大范围返工的东西，正是骨架该提前撞的墙。
- `x-required-role` 全覆盖测试若晚一轮才立，中间新增的每个端点都是在**无守卫状态**下写的。
- 「登录纯属产品功能、与验证选型无关」不成立：会话 cookie 是 T6 **显式否决 JWT** 的结论，属于选型。

## 5. D5 · 凭据明文存库，且骨架禁止出现任何加密抽象

**背景（本票发现的一处依赖冲突）**：骨架必须接入真 PG，就必须存一份连接凭据；但**凭据怎么存**正是 [T13 · 凭据加密存储、轮换与吊销](https://github.com/liumingjian/dbs-monitor/issues/31) 要回答的问题，而 T11 不被 T13 阻塞。

**先厘清一处易混**：R1 不变式 3 是「**凭据永不回显明文**」，**不是**「必须加密存储」。前者由 [T6](07-api-contract-and-codegen.md) 的**请求/响应双 schema** 在契约层结构性成立，与加密与否无关。**骨架不做加密不违反任何已定不变式。**

**结论**：骨架**明文存库**，附三条硬约束：

1. **禁止出现任何加密、密钥、封装格式相关的代码、接口或抽象**——防止实现会话「顺手替 T13 决定」。
2. **请求/响应双 schema 照做**：`password` 只在请求 schema 里存在，响应 schema 里**写不出来**。
3. T11 resolve 时必须把「明文存储」记进**交给 R3 的已知欠账**，并在 T13 resolve 时回写这一笔。

**被否决的两条**

- **给 T11 加 `blocked by T13`**：把 frontier 从三张压回两张，串行代价大，而技术上并无必要（见上一段）。
- **摆一个 `Sealer` 窄接口、明文实现、T13 后替换**：[T5](05-backend-code-structure.md) 把接缝白名单**封闭为五个**，并明令「一个实现只是假想接缝，其余一律直接 import 具体类型」。**违反已定决策，直接排除。**

**顺带定下**：骨架做一个**最简新建实例表单**（host / port / db / user / password），它是双 schema 的产地。与 T6「实例写端 R2 只做最小可用」一致。

> **T13 回写**：[凭据加密存储、轮换与吊销](13-credential-encryption-rotation-and-revocation.md) 已将这笔 R3 欠账收敛为版本化 AES-256-GCM 主密钥、独立 PG 凭据写入、Agent 显式登记及令牌生命周期。T11 的明文实现仍是已验收的 walking skeleton；R3 在生产发布声明前替换它，不回改或伪装 T11 的历史结论。

## 6. D6 · 分区机制进骨架

**结论**：[T2](04-metric-storage-model.md) 的**按天 UTC 分区、Go 循环每小时预建 7 天、`DROP TABLE` 滚动删除、写失败即修复重试一次**，四者全部做真的。

**理由**

1. 已被 T11 票面绑死：T11 并入的 RT-C 实测项里有一条是「实测钉死 PG 对 *no partition of relation found for row* 返回的 SQLSTATE（推测 `23514`，无一手确认）」——**没有分区表，这条测不了**。
2. 同理，RT-C 门槛 T1/T2（查询延迟、容量占比）的造数与 `pg_total_relation_size()` 逐分区求和都以分区存在为前提。
3. 成本是**一个循环**，很薄。

## 7. D7 · 验收标准

[T9 D6](10-ai-guardrails-and-verification.md) 把「完成」**直接定义为 `make check` 全绿**，D1 **否决三层**（「我该跑哪条」是判断题，模型在判断题上失败率远高于执行题）。本票据此把验收**尽量塞进已有的两层**，不新造第三条命令。

### 7.1 快层（`make check`）· 一条 Go 集成测试跑完整条切片

| # | 步骤 | 断言 |
|---|---|---|
| 1 | 起服务端 → 建实例（真 PG，compose 提供）→ 等 N 个采集周期 → 查 API | `points` 非空，且**不含 `?? 0` 式的假 0** |
| 2 | **把实例连接串改成不可达端口** | 依次出现 `DB_UNREACHABLE`；连续 2 周期后告警状态转 `NO_DATA` |
| 3 | 改回 | 状态转 `RECOVERED`（滞回恢复的实证） |
| 4 | 起 Agent（真 TLS、真令牌）→ push | `host.cpu.usage_percent` 落库 |
| 5 | 用错误令牌 push | 被拒 |
| 6 | 用偏移 >±30s 的时间戳 push | 被拒 |

**两处刻意的选择**

- **第 2 步用「改连接串」而不是 `docker stop`**：语义等价（连不上就是连不上），但**不需要 docker 权限、不需要 testcontainers**，秒级完成。
- **骨架的采集周期配 1s、评估周期 2s**：整条测试压进十几秒，[T9](10-ai-guardrails-and-verification.md) 的 90 秒预算守得住。

### 7.2 慢层（`make check-full`）· 一条 Playwright smoke

登录 → 实例列表 → 进详情 → 图上有点 → 改时间范围后 URL 与图同步（`validateSearch` 往返）。

放慢层的理由：它要**先构建前端**，与 90 秒预算冲突。这也回答了 [T7](08-frontend-stack-and-ui.md) 留下的「E2E 归 T10」。

### 7.3 人工验收（装不进机器的）

| # | 项 | 算不算「完成」 |
|---|---|---|
| 1 | 离线 tar 包在一台干净机器上装得起来；记下 `go:embed` 后的二进制体积 | ✅ 算 |
| 2 | 首启三项人工输入 + 随机管理员口令打印一次（[T8](09-packaging-and-deployment.md)） | ✅ 算 |
| 3 | AntD 的实测交互观感（[T7](08-frontend-stack-and-ui.md) 唯一推翻条件） | ❌ 不算，记入欠账 |

理由：1、2 验证的是本路线的地基——T8 的整包交付（「不依赖客户环境」），**装不起来等于选型没验证**。3 是主观判断，等 R3 有真页面时再看更有意义。

### 7.4 T11/R3 边界确认

以下两项不属于 T11 walking-skeleton 的 resolve 前置条件，正式延期到 R3：

1. **升级/回滚生命周期**：`upgrade.sh`、控制面备份与恢复、旧二进制回滚和升级后 healthcheck；
2. **PG13–17 集成矩阵**：五个真实被监控库上每个采集 Task 的列名、类型和行数形状断言。

T11 只验收离线 tar、首启三项输入、一次性管理员口令、socket-only PostgreSQL、真实构建和 RT-C 门槛。R3 交付前必须补齐上面两项，不能把 T11 的骨架包当作完整生产发布包。

## 8. D8 · 禁止清单（做了就是超范围）

地图 Notes 的原话：骨架「只做最薄的一条切片，**不预先摆放各模块空壳**」；预先冻结所有接口是 R1 决策索引反复否决的那类做法。

1. **指标只做三个**：`pg.availability.reachable`、`pg.connection.total`、`host.cpu.usage_percent`。R1 字典其余全部不实现，采集任务表里也**不预登记**。
2. **告警**：不做规则 CRUD、规则版本快照、通知渠道（连 `notify.Channel` 接缝都不摆）、处置、触发现场快照、压制。
3. **前端**：不做告警页、采集管理页、配置缺失待办页、实例接入向导、用户与角色页；不做视觉打磨、响应式、暗色。
4. **Agent**：不做自分发安装流程、不做内存 5 分钟补报缓冲、不做版本兼容协商。
5. **凭据**：不做任何加密、密钥、封装格式相关的代码或抽象（见 D5）。
6. **能力探测**：不做 5 分钟能力探测循环（骨架三个指标都**无前置条件**）。但 [T4 §4.4](06-metric-dictionary-and-collection-plan.md) 的硬纪律照旧生效——**禁止任何「靠查询报错反推能力缺失」的代码**。
7. **并发与背压**：不做 worker 池、限流、超时分层、背压、退避（归 [T12](https://github.com/liumingjian/dbs-monitor/issues/30)）。骨架接 1–2 个实例，**采集串行即可**。
8. **不预先摆放任何模块空壳。**
9. **不做降采样、长期留存、高可用、平台自身可观测性。**

### 8.1 为什么两个 PG 指标都留、不砍成一个

反方观点是 `pg.availability.reachable` 与 `pg.connection.total` 都走服务端直连、通路重复。**不砍**——ADR-02 M2 要求可用性探针**每周期全新建连、不可复用**，而 [T12](https://github.com/liumingjian/dbs-monitor/issues/30) 将来要讨论「其余指标查询是否复用长连接」。骨架里同时存在这两类，那个张力才**在代码里可见**；砍掉一个，T12 就要对着不存在的代码讨论。

## 9. D9 · 实测推翻选型时怎么办

T11 是 **AFK 票、由 Claude Code 执行**。不写死规则，执行会话遇到选型不成立时会**自己拍板**——而那些选型是整条路线花了九张票定下来的。

**判据（给执行会话的可执行版本）**

> 替代方案已经写在某张已闭票的文档里 ⇒ **一类，走就是了**。
> 你需要**自己想一个**替代方案 ⇒ **二类，停下**。

| 类 | 定义 | 动作 |
|---|---|---|
| **一类 · 门槛型** | 决策票**自己已写好**推翻条件与替代方案 | **不停、不开票**，直接按预写路径走；完成后回写决策文档与地图 gist |
| **二类 · 结构型** | 决策**没预见**的 | **必须停**：在 T11 记录现象与证据，**新开 `wayfinder:grilling` 票**挂地图，T11 改为 blocked by 它，交回 HITL |
| **三类 · 琐碎偏离** | 库小版本、API 参数名、目录微调 | 直接改，记进 T11 resolution 的「与决策票的偏离」 |

**已知的一类（预授权）**

- **RT-C / [T2](04-metric-storage-model.md) 三门槛**：查询延迟 P95 > 500 ms、容量占比 > 30% 或 > 100 GB、控制面事务 P95 劣化 > 2 倍 ⇒ 替代首选 **VictoriaMetrics**，**且须先满足反向门槛**——先证明 `NO_DATA` 能可靠区分「时序库不可用」与「无数据」。
- **[T7](08-frontend-stack-and-ui.md)**：AntD 的唯一推翻条件是实测交互卡顿；ECharts 的后备是 uPlot。

**已知的二类候选**（[T6](07-api-contract-and-codegen.md) / RT-D 自己点名的未实测项）

- 跨文件 `$ref` 的生成器支持；
- sqlc 对分区表的解析；
- goose 迁移锁语义。

**已闭的决策票一律不重开。** 修订走「新票 + 回写文档 + 更新地图 gist」——决策文档已合入 main、地图 Decisions-so-far 已引用它们，重开会让「已走过的路」变得不可信。
